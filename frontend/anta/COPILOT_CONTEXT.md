# ANTA - Copilot Context

## Product Purpose
ANTA is an offline-first Flutter app for tracking the things a person keeps coming back to — training sessions, spending, appointments, and the notes around them. Folders and markdown notes are the substrate; the money ledger, the calendar, and counters are built on top of them, all derived from or stored alongside note content rather than living in separate silos.

The app began as a training log, and that origin still sets the bar. When changing the app, optimize for capture in the middle of something else:
- Users should be able to record a value, a line, a transaction, or an event with minimal friction — mid-set, at a checkout, or between meetings.
- Editing must feel reliable when attention is elsewhere: no lost text, no surprising navigation, no heavy UI while typing.
- Organization should support real habits: folders for programs, projects, months, or topics; notes for sessions/templates/records; counters for global or per-note metrics.
- Offline data ownership matters. Preserve local SQLite data, backup/restore behavior, and future sync readiness.
- UI should be practical, touch-friendly, and quick to scan one-handed. Prefer clear controls, high contrast, stable layouts, and small but obvious status feedback.
- When two designs are otherwise equal, pick the one that survives one-handed use.

## Core User Workflows
- Create folders/subfolders for programs, routines, exercises, weeks, muscle groups, projects, or months.
- Create and edit markdown notes for sessions, templates, logs, measurements, spending, and history.
- Use custom markdown toolbar shortcuts for fast entry of headings, lists, checkboxes, tables, dates, and repeated structures.
- Record spending inline with money-ledger lines that fold into a running balance derived purely from note content.
- Track numeric progress with counters, including global counters and per-note counters with pinning and manual ordering.
- Plan and review with the calendar: categorized events, recurrence, computed holidays and fasting calendars, day summaries, note links.
- Search across notes and within the active note, including regex/whole-word options in the editor search overlay.
- Switch databases, export/import backups, and keep localized app text in English, German, and Romanian.

## Non-Negotiable Rules
- Use `AppLocalizations` for every user-visible string. Update `lib/l10n/app_en.arb`, `app_de.arb`, and `app_ro.arb` together, then run `flutter gen-l10n`.
- Do not hand-edit generated files such as `lib/database/database.g.dart` or generated localization Dart files.
- After changing Drift tables, DAOs, migrations, or database annotations, run `dart run build_runner build --delete-conflicting-outputs`.
- Keep generated schema/migration changes compatible with existing local user data. Add migrations instead of resetting storage.
- Do not add tests, new markdown files, broad refactors, or code comments unless explicitly requested.
- Preserve existing user data semantics: soft deletes, CRDT fields, positions, sort preferences, pinned counters, note assignments, and backup format compatibility.
- Keep changes focused and consistent with the local style. Avoid introducing new state-management, persistence, or navigation patterns without a strong reason.

## Current Stack
- Flutter app with Dart SDK `^3.10.4`, Material 3, and `flutter_lints`.
- State management: `flutter_bloc` with `Equatable` states/events.
- Persistence: Drift SQLite, `sqlite3_flutter_libs`, `path_provider`, `shared_preferences`.
- DI: `get_it` via `lib/core/di/injection.dart`.
- Editor/markdown: local `packages/re_editor` with a custom line-based markdown renderer (`lib/utils/line_based_markdown_builder.dart`).
- Search/debounce: `stream_transform`, FTS5, isolate-backed indexing utilities.
- Sharing/import: `share_plus`, `file_picker`.
- External links: `url_launcher` (markdown preview hyperlinks open via `LaunchMode.externalApplication`; only `http`, `https`, `mailto`, `tel` schemes are accepted).
- Localization: Flutter gen-l10n with locales `en`, `de`, `ro`.

## Architecture Shape
Follow the existing flow:

```text
Page/Widget -> BLoC -> Service -> Repository -> DAO -> Drift database
```

- BLoCs live under `lib/bloc/` and should stay thin: route events, manage loading/error states, and delegate business logic to services.
- Services in `lib/services/` own app workflows such as note storage, folder storage, search indexing, counters, settings, backup/restore, database switching, auto-save, and note positions.
- Repositories in `lib/repositories/` provide cached/reactive access over DAOs. Invalidate caches carefully after creates, updates, deletes, moves, and reorder operations.
- DAOs in `lib/database/daos/` own SQL/Drift details, transactions, soft deletes, pagination, FTS, and migrations support.
- Models in `lib/models/` generally use `Equatable`, `copyWith`, and JSON keys from `lib/constants/json_keys.dart`.
- Constants belong in `lib/constants/`. Prefer existing spacing, text style, icon size, settings key, and app constant files over magic values.

 **Marker contrast is a ratio, never a luminance delta (fixed 2026-08-23).** `CalendarDayBars` outlines a marker only when its contrast against `colorScheme.surface` falls below `_minContrastRatio` (1.6:1, WCAG `(L+0.05)/(L'+0.05)`, matching `MarkdownColorPalette._contrastRatio`). It used to compare raw luminance **deltas** against a 0.22 threshold, which means opposite things at the two ends of the scale — against white (lum 0.948) a 0.09 gap is an invisible 1.05:1, against a near-black surface (lum 0.007) the same gap is a readable 2.06:1 — so, tuned on white, it outlined **six of the twelve** built-in marker colours in dark mode (cardio, competition, measurement, birthday, other, fasting purple) and none in light, exactly backwards from the pale-colour case it exists for. The stroke is **1px `strokeAlignCenter`**, never the old `width: 0.5` inset: half a logical pixel is half a *device* pixel at dpr 1.0 (desktop), which paints as a washed-out grey smear rather than a line, and an inset border also ate a third of a 3px bar's fill; centred keeps the fill and its 0.5px overhang per side still fits inside the 1.5px inter-bar gap, so `stripHeight` is unchanged. `computeLuminance()` is memoized per colour (bounded 64, cleared wholesale) because the grid asks for one per marker per cell on every rebuild — the same "static probes only" discipline the 42-cell path lives under.

The read **cannot** live in the grid subtree: `ScaffoldState.build` strips the bottom inset before wrapping the body (`removeViewInsets(removeBottom: true)` whenever `resizeToAvoidBottomInset` is true), so `MediaQuery.viewInsetsOf(context).bottom` reads `0` inside the body forever — a wrapper there compiles, analyzes clean, and silently does nothing. `_KeyboardInsetProbe` therefore sits **above** the `Scaffold`, reads the inset in `didChangeDependencies`, and publishes a `ValueNotifier<double>` carrying the **raw inset** once per keyboard animation frame, which the page folds into a collapse flag only the grid's `ValueListenableBuilder` listens to; its `build` returns `child` unchanged, so an inset frame never rebuilds the Scaffold subtree and the panel half is untouched (tests assert `CalendarEvent.debugOccursOnCalls == 0` and `identical` `AgendaListView.rows` across a show+hide (the panel legitimately rebuilds for its inset padding, so widget identity is no longer the probe — the rows memo is), plus `DaySummaryResolver.debugDefaultsBuilds == 0`). `sameGridInputs`/`samePanelInputs` are untouched by the override. `onFormatChanged` is **nulled** while collapsed — table_calendar's own way to disable the vertical-swipe format gesture — so a swipe cannot rewrite the chosen format even when the user was already on week. **Keyboard-coupled motion (2026-08-25):** the height animation is owned by the page, not the package. `KeyboardInsetTracker` (lib/utils) folds each inset frame into two signals — a `collapsed` flag and a `progress` fraction — and `KeyboardCoupledSize` (lib/widgets, a `RenderShiftedBox` modelled on Flutter's `RenderAnimatedSize`) animates a **gap** added to the child's natural height. The child is **never** height-bounded: `table_calendar` redistributes a bounded height across its rows (`calendar_core.dart`'s `constrainedRowHeight`), so a plain `SizedBox` wrapper squashes the month into an accordion instead of collapsing it. On a child resize the gap is seeded to `oldChildHeight + oldGap - newChildHeight`, which keeps the painted height continuous across the frame the format flips, then relaxes to zero — measured, not computed, so it covers month↔week, user format toggles and 4/5/6-row month swipes with one mechanism. The collapse flag is **asymmetric on purpose**: true on the first *rising* inset frame, false on the first *falling* one, so the grid gives space back while the keyboard is still sliding away rather than after it (the old `> 0` threshold serialized ~250 ms of keyboard and then ~200 ms of grid). Coupled progress is `inset / peak` — the hide path divides by this cycle's observed peak, the show path by the peak **learned from the previous completed cycle this app run** — and falls back to a timed 250 ms `easeOutCubic` tween whenever there is no motion to couple to: the first open of a run, an inset that jumps 0→peak in one frame (Android < 30), or a coupled transition idle for 150 ms (an IME panel swap, a resume with a stuck inset, a learned peak that overshoots the real one). `formatAnimationDuration` is pinned to **1 ms, never `Duration.zero`** — a zero-duration `AnimationController` publishes its end value synchronously from inside `RenderAnimatedSize.performLayout`, which then re-dirties itself mid-layout and throws. The page's own 250 ms `AnimatedSize` (which exists for `_panelExpanded`) still tracks the new animator 1:1 after a single divergent frame (a test pins `<= 1`, so layering a second real tween fails loudly). The page sets `resizeToAvoidBottomInset: false`, so the body never shrinks and the `Column` structurally cannot overflow; `CalendarBottomPanel.build` reads `MediaQuery.viewInsetsOf` once (body reads work again with resize off) and threads `bottomInset` into all three panel modes as extra scrollable bottom padding, the FAB deliberately sits behind the keyboard, and a short-screen test pumps every frame of the collapse asserting no overflow (red if the flag is flipped back).

 **Event search is a parsed query, not a needle (2026-08-24):** `lib/utils/event_search_query.dart` owns the grammar — `EventSearchQuery.parse(raw, {localeName})` splits on whitespace, folds each token once through the shared `normalizeForSearch`, dedupes into `terms` (a repeated word is one constraint) capped at `maxTerms = 30` and addressed by an `int` bitmask, and groups them into `clauses` each carrying an optional `EventSearchDate`. `parse('')` returns the `const empty` — zero allocation, `satisfied` trivially true — so an empty query costs exactly what it did before. An occurrence on day `D` matches iff **every** clause is satisfied, and a clause is satisfied when either all its text terms appear in the title / the description resolved for `D` / the **localized category label** (clause-mates may be answered by different fields), **or** its date matches `D`. So `aug 26` returns everything on Aug 26 *plus* anything whose text holds both "aug" and "26"; `gym aug 26` requires both clauses. Dates parse from localized month names (`DateFormat.MMMM(locale).dateSymbols`, all four symbol lists, folded, punctuation-stripped, unique ≥3-char prefix, cached per locale), day+month in both orders (`aug 26` / `26 aug` / `26. august`), and ISO validated by a UTC round-trip — **never** `DateTime.tryParse` (rollover, same reason `fasting_schedule.dart:261` warns). Bare numbers, bare years and impossible dates (`2026-02-30`, `feb 30`, `aug 44`) degrade to plain text. **`EventAgenda` stays context-free**: the view resolves a `Map<String, String>` id→localized label and passes it in — a `Set` of matched ids cannot express *which* term a category answered, which AND semantics needs. Per-event state is one `_EventQueryMatch` (`base` = title|category, `template` folded **only** for what `base` left open, plus `varies`/`always`), so a title hit still costs no description fold, and `matchesQuery` is one map lookup plus an `always` short-circuit per (event, day); a live per-occurrence override still **replaces** the template contribution, empty included. The query is parsed once per rescan (`_syncQuery`, no-op when text+locale stand still) and category labels are re-resolved on `CalendarCategories.revision`, so a rename behind the panel's back is picked up. Holidays and fasting run the **same** clause test against their own localized labels instead of their old private `contains`, so all three layers agree on what "matches" means. **Search coverage, reach and language (2026-08-25):** the governing rule is now *if a row displays a piece of text, typing that text finds the row* — the scan used to fold only title|category|description while rows displayed recurrence patterns, times, "All day", priority words, regime names, "Public holiday" and cards titled "Holidays"/"Orthodox". `occurrencesInRange` gained a lazy `labelTextOf` closure (built by the view, so `EventAgenda` stays `AppLocalizations`-free), invoked **once per candidate event** and only when `base` has not settled the query, folded **before** the description so a label hit costs no description fold; `AgendaSearchText.forEvent` composes exactly what `EventSummaryProvider._subtitleFor` renders, and `EventAgenda.debugLabelFolds` pins the budget. `countLabel` ("Week 3", "26 years") is **knowingly excluded** — it is per-(event, day) and would break the `always` short-circuit every budget depends on. A non-empty query with no pinned custom range **auto-widens** the window to `maxRangeDays` (366): the reported "`lent` finds nothing" was never a string bug — English "Great Lent" contains "lent" — it was that search filtered the 30-day window instead of finding across the year. `_fastingMatches` folds the override **and** the period name (OR, never the display's `??`, which made renaming a period unsearchable), plus the tradition name (folded nowhere before, though it titles the summary card), the regime and the style description; `_recomputeHolidays` folds `dayBarPublicHoliday` + the `upcomingShowHolidays` card title once per scan. Cross-language terms come from **hidden localized keywords** (`FastingCalendar.traditionKeywordsOf` / `searchKeywordsOf`, nullable for minor periods) on the settings search's proven `swipeKeywords` pattern — matched, never rendered, each locale carrying the other languages' terms. On a **zero-result** query only, `FuzzyRank` (`lib/utils/fuzzy_rank.dart` — the vocabulary bar's 4-tier prefix › word-start › substring › subsequence scorer, extracted unchanged and now shared, `VocabularyMatcher` delegating to it) ranks a catalogue of titles, category labels, enabled traditions/periods and the window's holidays into up to three "did you mean" chips that replace the query. Fuzziness **suggests only** — the filtering grammar stays exact substring.

## Markdown Preview Pipeline
The note-editor preview is fully BLoC-driven. Keep this layering intact:

```text
OptimizedNoteEditorPage
  -> MarkdownPreviewBloc (lib/bloc/markdown_preview/)
     -> MarkdownRenderService (lib/services/markdown_render_service.dart)
        -> LineBasedMarkdownBuilder (lib/utils/line_based_markdown_builder.dart)
           -> MarkdownChunker (lib/utils/markdown_chunker.dart)      // block scan + chunk layout
           -> MarkdownListSyntax (lib/utils/markdown_list_syntax.dart) // shared list grammar
  -> MarkdownPreviewBlocView (lib/widgets/markdown_preview_bloc_view.dart)
     -> SourceMappedMarkdownView (lib/widgets/source_mapped_markdown_view.dart)
```

Non-negotiable invariants:

- Bloc state is `Equatable` and contains only primitives + a `renderHandle: int` token. Never put `InlineSpan` trees, builders, or other heavy objects in state.
- Spans are pulled from `bloc.renderService.builder` on demand; the widget rebuilds the heavy list only when `renderHandle`, `linesPerChunk`, or `fontSize` change (`buildWhen`).
- The bloc owns its `MarkdownRenderService` and `PreviewScrollController` and disposes them in `close()`. The page wires callbacks via `bloc.bindCallbacks(onLinkTap:, onCheckboxTap:)`.
- **Content sync**: use `bloc.bindContentProvider(() => _contentController.text)` once in `initState` and call `bloc.markContentDirty()` on every keystroke (free `int++`). Dispatch `PreviewContentRefreshRequested` (not `PreviewContentChanged`) when you want a lazy refresh; the bloc short-circuits when the dirty version hasn't moved since the last consume. Only use `PreviewContentChanged` for eager pushes (toggle, checkbox, locale change, content load).
- **Live refresh**: `_scheduleLivePreviewRefresh()` (called from `_onTextChanged`) debounces `PreviewContentRefreshRequested` at 500 ms for non-large notes (`lineCount <= AppConstants.previewPreloadLineThreshold = 3000`). It is gated on `!_isLoading` and `state.hasTheme` so the first build is never blocked. The debounce timer is cancelled in `dispose()`.
- **Search content sync**: `_pushPreviewContent` calls `_searchController.updateContent(content)` when `_searchController.isSearching`; `_scheduleLivePreviewRefresh` does the same after dispatch. Never call `updateContent` inside `build()`. `ReEditorSearchController.updateContent` deduplicates on `identical/==` so redundant calls are free.
- Theme dispatch (`PreviewThemeChanged`) happens from `MarkdownPreviewBlocView` lifecycle hooks (`didChangeDependencies` + a `DevOptions` listener) — never from `build()`. Equality is keyed on `(brightness, debugEnabled)` so closure-only changes do not trigger rebuilds.
- Scroll progress bypasses the bloc event queue: the view calls `bloc.scrollController.updateProgress(progress)` directly to avoid per-frame state churn.
- **Preview view key**: the page holds `final GlobalKey<SourceMappedMarkdownViewState> _previewViewKey = GlobalKey<...>()` as a field. It is bound to the scroll controller in `initState` via `_previewController = _previewBloc.scrollController..bindView(_previewViewKey)` and passed explicitly to `MarkdownPreviewBlocView(viewKey: _previewViewKey)`. Access state via `_previewViewKey.currentState` (e.g. `currentLineIndex`) for preview→editor scroll mapping.
- **Preview→editor scroll**: on toggle back to editor, compare `_previewViewKey.currentState?.currentLineIndex` against `renderService.chunkStartLineForLine(savedBaseIndex)` to detect real user scrolling. Chunks are block-aligned (variable line counts), so never assume `lineIndex ~/ linesPerChunk` — always resolve a chunk's start line through the builder/service. Only snap the editor and move the caret when the user actually moved the preview; otherwise fall back to `_restoreEditorPosition()` which honors the exact saved selection.
- **Toolbar helper**: use `_buildMarkdownBar({required bool enabled})` for both the loading-skeleton and loaded paths. Pass `enabled: false` when loading to preserve layout without wiring live callbacks.
- **Double-tap from preview**: `_handleDoubleTapLine` parks the cursor at end-of-line. `DoubleTapLineDetector` currently always passes `columnOffset = 0` (column resolution from styled spans needs `TextPainter` introspection — future work). Forward-compatible: when a future detector passes `columnOffset > 0`, the handler clamps it to the line length.
- Adaptive chunk sizing lives in `MarkdownChunker.adaptiveChunkSize` (capped at `maxAdaptiveChunkSize = 100`) so `scrollToLineIndex` precision stays usable on huge notes. The render service applies it before constructing the builder; the builder then receives the final per-chunk target.
- The empty-preview placeholder text is locale-cached on the page (`_emptyPreviewPlaceholder`) and re-dispatched when the locale changes while the note is empty.
- Preview hyperlinks: the page passes `_handleLinkTap` to `MarkdownPreviewBlocView.onTapLink`. The handler validates the scheme against `_allowedLinkSchemes` (`http`, `https`, `mailto`, `tel`), launches via `url_launcher` in `LaunchMode.externalApplication`, and shows a localized `CustomSnackbar.showError` (`linkSchemeNotAllowed` / `linkOpenFailed`) on rejection or failure. Do not bypass scheme validation.

## Markdown Block Model And Chunking
`lib/utils/markdown_chunker.dart` is the single source of truth for how note content is divided into render chunks. Both the preview renderer **and** the editor's debug chunk overlay consume it, so their chunk boundaries are guaranteed identical.

- `MarkdownChunker.computeLayout({lineCount, chunkSize, lineAt})` returns a `MarkdownChunkLayout` = `{ blocks: List<MarkdownBlock>, chunkStartLines: List<int> }`. It runs one O(n) forward scan.
- `MarkdownBlock { kind, startLine, endLine, atomic }` models **multi-line** blocks only (today: `MarkdownBlockKind.codeFence`, including an unterminated fence that runs to EOF). Single-line content (paragraphs, headings, list items, blockquotes, rules, single table rows) is **implicit** — never modeled — so the block list stays O(number of multi-line blocks), not O(lines).
- Chunk boundaries are **block-aligned**: `atomic` blocks are never split across a chunk; non-atomic blocks (code fences) may be split so very large code blocks keep virtualizing. When you add a single-widget block type (table, math), set `atomic: true` and chunking keeps it whole automatically — the preview and the editor overlay both inherit the alignment.
- The builder exposes block-aware helpers used everywhere instead of `lineIndex ~/ linesPerChunk`: `chunkStartLine(i)`, `chunkLineCount(i)`, `chunkIndexForLine(line)` (binary search), and `_blockForLine(line)` for code-fence membership (replaced the old per-chunk code-block state caches). `MarkdownRenderService.chunkStartLineForLine(line)` is the service-level convenience for the page.
- The recursive inline parser (`_parseInline`) is offset-preserving: every leaf text run is routed through `_applyHighlighting` with its exact source offset, so search highlights stay aligned through nested emphasis, links, escaping, and ghost/list content. When adding inline syntax, keep this contract — never break the source-offset threading.

## Markdown Lists
`lib/utils/markdown_list_syntax.dart` (`MarkdownListSyntax`) is the **single source of truth** for list grammar, shared by the editor and the renderer so they can never disagree about what is a list.

- `MarkdownListSyntax.parse(line) -> MarkdownListItem?` classifies a line as `MarkdownListKind.{bullet, ordered, task}` and returns the indent string, marker, ordered delimiter (`.` or `)`), checked state, the `[` bracket column (tasks), the content-start column, and the content text. All columns are line-relative; the renderer adds the line's source-start offset for absolute positions. Detection order is task → bullet → ordered.
- Supported (GFM): `-`, `*`, `+`, `•` bullets; `N.` / `N)` ordered; `- [ ]` / `- [x]` tasks (markers `-`, `*`, `+`). `indentLevel` counts columns (tab = 2) and divides by `indentUnit = 2`.
- The editor (`MarkdownListUtils`) delegates all detection to `MarkdownListSyntax`: `getListPrefix` (Enter-continuation — preserves indentation, continues tasks unchecked, increments ordered numbers keeping the delimiter), `isEmptyListItem` (terminate list on Enter), `isListLine` (Tab/Shift-Tab gating).
- The renderer's `buildLine` calls `MarkdownListSyntax.parse(line)` once and dispatches to `_buildCheckboxLine` / `_buildListItem` / `_buildOrderedListItem`. Nesting is a width-based `Padding` (`level * baseFontSize`), never literal spaces; bullets cycle `• ◦ ▪` by depth. Do **not** reintroduce a second list regex anywhere — extend `MarkdownListSyntax`.
- Editor companion: `ModernEditorWrapper` overrides re_editor's `CodeShortcutIndentIntent` / `CodeShortcutOutdentIntent` via `CodeEditor.shortcutOverrideActions` so **Tab / Shift-Tab** indent/outdent a whole list item by `indentUnit` spaces when the caret is on one; non-list lines fall through to re_editor's default `applyIndent()` / `applyOutdent()`.

## Money Ledger (counter processing engine)
A line-led markdown syntax for tracking a running sum (money or any quantity) inside a note. **Opt-in: gated by `SettingsKeys.moneyLedgerEnabled` (default off)** — the flag rides `getMoneyConfig()`, gates both render dispatch paths (preview builder + editor span builder), the wrapper tap zone, and the calendar ledger service (which clears its cache when disabled). Grammar, fixed-point arithmetic, and formatting live in `lib/utils/markdown_money_syntax.dart` (`MarkdownMoneySyntax`), the single source of truth consumed by the preview renderer, the editor span builder, the editor line index, and the preview's ledger pass.

- Syntax (line-led, optional leading whitespace): `$= 100` set/checkpoint, `$+ 12.50 label` add, `$- 8 label` subtract, `$* 1.19` multiply, `$/ 2` divide, `$$ label` running total, `$? label` net change since the last `$=` (or note start), `$! 500 label` spending-target *declaration* (inert; displays the target itself and anchors the budget baseline at the current balance), bare `$! label` target *status* (inert; displays the remaining budget vs the active target — see the Targets bullet), `$^ label` / `$^ N label` entry diff (inert; the net change over the last N **balance-changing entries** — an entry is any `$=`/`$+`/`$-`/`$*`/`$/`; display rows `$$`/`$?`/`$!`/`$^`/`$~` never count — with N a digit run of any length or the keyword `ALL` ending at a space/EOL, defaulting to 1 — any leading number is a count (an over-large one clamps; `3x`/a zero count stay label text); `ALL` means all entries since the current period), `$~ label` / `$~ N label` checkpoint span (inert; the net change over the last N **`$=` checkpoints**, deliberately reaching across period boundaries — N shares the exact any-length count grammar or `ALL`, defaulting to 1 so `$~` alone equals `$?`, and clamps to the **first `$=` checkpoint** (not the note start) when fewer than N precede it — so an over-large N (or `ALL`) reports the change since the oldest checkpoint and stays a change *between checkpoints* rather than the absolute balance; only a note with no `$=` at all falls back to the note start). All stored entry values flow through `MarkdownMoneySyntax.displayValue(m, balance, history, periodStart, anchors)` — the single source of truth across all folds, where `history` is the append-only entry-balance list (index 0 = note start, one value appended per entry via `isEntryKind`), `periodStart` is the history index of the current period's `$=`, and `anchors` is the parallel append-only checkpoint-balance list (index 0 = note start, one value appended per `$=`) that `$~ N` counts back through. **A `$=` resets the `$?`/`$^` window** (`$^ N` clamps its reference to `periodStart`, so it never reaches across a checkpoint and once N spans the whole period `$^` equals `$?`); `$~ N` is the deliberate opposite — it counts `$=` checkpoints, so it reaches across exactly N of them. `$=` doubles as a period boundary — put one under a month/year heading and close the period with `$?`.
- **Targets (`$!`)**: the marker splits on the presence of an amount, decided purely by shape in `parse` (`MoneyLineKind.target` vs `MoneyLineKind.remaining`). `$! 100 label` / `$! Groceries: 100` **declares** the target: the fold (`MoneyFold.targetCents`/`targetAnchor`) records the amount and the balance at that point as the budget's baseline, and the row displays the target itself (`displayValue` returns `amountFixed ~/ 100`) — a neutral statement, like `$=` the one *other* row whose operand is its value, so it renders its amount as a formatted value (currency shown), appends no annotation, and is **not** a display kind (`needsBalance` false without a slot → editor text-keyed memo). Bare `$!` (space or EOL after the marker required, so `$!important` stays plain text; label optional, colon tails are label text — `$! Remaining:` never errors) is the **status** row: a true display kind (chip/pill, positional path, tap-to-detail) whose value is `target + balance − targetAnchor` = remaining budget, green while ≥ 0 ("didn't spend more than the target", zero included), red once overspent (`moneyAccent`'s `remaining` case; an accent token overrides as always) and printed **with an explicit sign** (`+50.00` = left, `-30.00` = over, `±0.00` = exactly on budget) via the shared `MarkdownMoneySyntax.isSignedKind`. That predicate is the one home for "which values print signed" — the rule being **a value the surfaces colour by its sign shows that sign**, so `$?`/`$^`/`$~`/bare-`$!` are signed while `$$` (absolute balance, red only when negative) and every op row's value are not. The preview pill, editor chip, and both the sheet's header and rows all read it; they used to spell it out four separate ways, which is exactly how bare `$!` ended up colour-coded on all four and signed on none. **The baseline survives `$=` on purpose** — a ledger that records balances only with set-rows (`$= 500` … `$! 100` … `$= 450` … `$!` → 50.00 remaining) still measures its budget; a later `$!` declaration replaces the target and re-anchors. A status row with no declaration above it displays `MarkdownMoneySyntax.noTargetSentinel` (outside every reachable value, disjoint from `valuePinned`; check via `isNoTarget`) and every surface renders a "no target" chip in the warning accent instead of formatting it. Error declarations are fold-inert for target state too. **Label-first declarations suppress the target glyph**: `### $! yellow: Groceries: 500` renders "Groceries: 500.00 lei" — the `:` stays visible text on both surfaces (editor: the `$!` marker run conceals; no `_glyphSpan` at the colon) because a label-first target is a statement, not an equation; amount-first declarations keep the leading `◎`. Both `$!` kinds share the `◎` glyph (one family — the only deliberate glyph collision, test-pinned).
- **Syntax errors** (yellow warning rows, lines do not mutate balance): label-first op with missing trailing amount (`$= Label:` — the colon marks the shape), divide by zero (`$/ 0`), over-limit amount (`amountTooLarge`: >11 integer digits on `$=`/`$+`/`$-`, >4 on factors) and over-limit decimals (`tooManyDecimals`: >2 on amounts, >4 on factors) — over-limit shapes are deliberately errors, never silent plain text, so a too-big `$=` is visibly broken instead of quietly not counting (the old silent-fall-through is what made big `$=` rows "go white" and downstream `$~` rows read `+0.00`). Messages come from the single `MarkdownMoneySyntax.errorMessage()` used by all three surfaces; the palette colour is `MarkdownConstants.moneyWarning`. **Error rendering keeps the source text visible**: preview shows a bold `!` chrome glyph + the offset-mapped source + a trailing computed message; the editor substitutes the `$` 1:1 with `!` and tints the rest of the line (code units preserved — the old render replaced the line with the message text, which desynced caret/search offsets). **Error lines are fold-inert in every fold including the history/anchor appends** — the fold state machine lives in **one place, `MoneyFold`** (`step(match)` in the grammar lib: balance + entry history + checkpoint history + periodStart; `MoneyFold.resume` adopts an incremental pass's persisted lists by reference), and every fold steps through it: preview `_computeMoneyLedger`, editor `_scanMoney` (resume via truncated list lengths), `collectEntries`, and the calendar's `NoteMoneyLedgerService._fold`. Never inline fold rules at a call site — error-inertness was once re-implemented per fold and two copies missed it. `isCountedEntry` is the one predicate for "this line appends". Error rows still appear in the detail sheet with their message. Balances that clamp at ±`balanceLimitCents` (999,999,999,999.99) render **pinned**: `valuePinned()` is true and every surface (preview pill/echo, editor chip via `_moneyTotalSpan`, sheet header) shows the value in the warning colour — the number on screen is the cap, not arithmetic.
- **Composable prefixes** (both matched by shape only in `parse`, so the ledger never depends on any setting): a `#{1,6}` heading prefix with *optional* space (`## $$ Net worth` and `##$$ Net worth` both parse — unambiguous since a no-space hash run is not a valid heading; `MoneyLineMatch.headerStart/headerLevel`) renders the row at that heading's scale — preview scales `baseStyle` by the hX scale, editor conceals the hashes and scales the root span's fontSize (same line-height mechanism as `_buildHeader`); and a letter-led `name:` accent token after the op (`$+ blue: 250 rent`, `MoneyLineMatch.accentStart/accentEnd`, `:` must be followed by space/EOL so `$$ http://…` labels stay intact, letter-led so `$+ 250: x` can never read as an accent) overrides the row's semantic accent with a palette colour — resolved at render time against `MarkdownColorPalette`. On a count-taking display row (`$^`/`$~`) the token may sit **after** the count (`$~ 2 teal:`), the natural spelling, as well as before it (`$~ teal: 2`); `parse` scans both positions, and when it resolves after the count it is concealed chrome between the count and the label on both surfaces; a resolved token is concealed chrome, an **unresolved token renders literally with the semantic accent and the line still counts** (editing the palette can never change a balance). **The whole row takes the row accent — chrome glyph, value, *and* label** (`labelStyle` on both surfaces: colour only, base weight kept so the value still leads). That means the *semantic* sign colour too: a plain `$+ 12.50 rent` renders "rent" green, `$- 8 food` renders "food" red. An unresolved accent token is literal label text and takes the label colour with it. (v1 kept semantic colours off the label — Alex overruled it: a row coloured only on its number reads half-styled.) **A resolved token wins on every row kind, no carve-outs** — `$$`'s negative-red, `$?`'s direction colour, and bare `$!`'s green-under/red-over status colour all yield to it. (`$!` used to be the exception; it made `$! red:` ambiguous — token or over-budget warning? — and over-budget stays readable regardless since the remaining value renders with a leading `-`. The one thing a token never restyles is the "no target" warning chip, which marks a broken measurement like a pinned value.) The one thing a token does *not* recolour is op rows' dimmed trailing `= balance`: that grey marks "computed, not typed", and the distinction outranks row colour. Cheap probes (`leadsWithMoney` / `leadsWithMoneyInRange`) accept the heading prefix; a `#…$`-led line that fails the money parse falls through to normal heading rendering on both surfaces.
- **Label-first op rows** (`$= $+ $- $* $/` only): the typed amount may trail behind a `:` — `$= Net worth: 5000`, `## $- blue: Loss/Gain/Whatever: 5000`, `$* VAT: 1.19` — parsed by `_scanTrailingAmount` as a fallback when no digits sit at the amount position. **The colon is required and load-bearing**: without it `$- food 2024` would silently subtract 2024, so a colon-less label still refuses to parse (renders plain, unchanged). The whole tail after the last `:` must be the amount and nothing else (`$= Net worth: 5000 as of today` → plain text, no guessing which number); everything before it is label, colons included. Amount limits/`$/ 0` rejection apply identically — `_parseAmount` is now a shared helper used by both positions. This is the **only** shape where `labelStart < amountStart`, so **both renderers compare them to pick an emission order and must use `labelEnd`, never "label runs to line end"** (`money_detail_sheet` too). **The spelling picks the layout**: amount-first puts the op glyph in front (`+ 12.50 rent`), label-first renders it *where the `:` is* so the row reads as an equation (`Net worth = 5000`) — on those rows the `:` is chrome like the marker it replaces (trimmed from `labelEnd - 1` in the preview, the sheet, and the editor's label region), and the leading chrome span is suppressed. Editor: the op char is *concealed* at the marker rather than substituted (it must still be emitted as its own source char or every later offset shifts by one), and the `:` goes through `_glyphSpan` — a `CodeInlinePaintSpan` reusing `_EditorMoneyTotalSpan` unfilled — because a 1:1 text swap has no source char before the `:` to render as a space and would read `Net worth= 5000`. On reveal the `:` stays literal and the marker shows dimmed raw text. **Chrome must conceal its trailing spaces or the row renders indented**: the heading prefix is concealed as one `[headerStart, markerStart)` run (hashes *and* the space, matching `_buildHeader`'s `level + 1` — concealing only the hashes left every header-prefixed money row indented by one space), and on label-first rows the whole `[markerEnd, labelStart)` run is concealed too via `emitAccentToken(concealGaps:)` / the `accentStart < 0` branch. The one thing that stays visible there is an unresolved accent token, which brings its own spacing (nothing is ever silently eaten). The preview never hits this — it builds from parsed parts and never renders source gaps. Display rows are unaffected: `$$`/`$?`/bare `$!`/`$^`/`$~` take no amount; `$! N` declarations take the label-first shape like ops but suppress the glyph at the `:` (see the Targets bullet).
- **Value slot** (`MoneyLineMatch.valueSlot`, -1 when absent): a lone `$` in the label marks where the row's computed value renders instead of its default position, so label text can precede the number without the marker leaving the line start — `$$ Current sum: $`, `## $$ blue: Net worth: $`, `$+ 12.50 groceries, now $`. Shape-matched like the other prefixes (a `$` delimited by spaces or EOL, so `$5`/`US$`/`$$` in a label stay literal; first one wins) and scanned by `_scanValueSlot` **only from inside `parse`** — never from `leadsWithMoney`, so the prefix probe every document line pays is untouched by the feature. Composes with every op, heading level, and accent colour. It is purely a display concern: `apply`/`displayValue`/`history`/`periodStart` never see it, and a doc's balances are identical with and without slots. `$=` and `$! N` declarations are the rows with no default-position value (their typed amount already *is* their value); `$=` shows a formatted, currency-suffixed value only via an explicit slot, while a declaration renders its amount as one inline.
- The balance is **derived from note content** — nothing is persisted, no counter is mutated, re-rendering can never double-count, and the data rides note backups automatically (the "derived from content" precedent, like the planned TagIndex).
- All arithmetic is fixed-point int (cents for balances, 1/10000ths for amounts): no float drift. Multiply/divide round half away from zero to the cent via the split helpers `_mulScaled`/`_divScaled` — every intermediate stays under 2^53, so the math is exact on every platform incl. web; balances clamp to ±`balanceLimitCents` (999,999,999,999.99; amounts max 11 int digits = 99,999,999,999.99, so a single amount never silently clamps and `amountFixed` stays under 2^53). Amounts accept `.` or `,` decimals; a malformed amount rejects the whole line so it renders as plain text, while a *well-formed* amount past the limits is an error row (yellow).
- **Preview**: `LineBasedMarkdownBuilder._computeMoneyLedger()` folds the ledger once per `prepare` (O(n) lead-char probe over `_source`; only `$`-led lines outside multi-line blocks parse). `_buildMoneyLine` consumes the `$x` marker as chrome (like `[!TYPE]`), renders sign glyphs `+ − × ÷ = Σ Δ Δ= Δ~ ◎` in the shared `MarkdownConstants.moneyPositive/moneyNegative/moneyNeutral` palette, keeps the amount and label offset-mapped for search, and appends the computed running balance (dimmed on op rows, pill-tinted on `$$`/`$?`/bare-`$!`/`$^`/`$~` rows). Computed values are not source text and carry no offsets. **`$=` and `$! N` declarations are the exception: their amount renders *as* a value** — `formatCentsWithSymbol(value)` in place of the typed digits, so the currency shows — because those rows' operand *is* their value (the balance being set / the target being declared), which is also why they are the rows with no trailing annotation (that would just repeat the number). The substituted run keeps the amount's source offset, so search still lands on it (highlight ranges clamp to the rendered run). The editor deliberately does **not** follow: plain `$=`/`$! N` and op rows render from line text alone to stay on the text-keyed span memo, so the editor shows amounts exactly as typed — only display rows and explicit slots take the balance-aware positional path. The value span is built once by the local `buildValue({required bool atSlot})` closure so the slot and default positions can never drift apart — `atSlot` only drops the `=` lead-in that reads as an annotation at row end but as noise mid-sentence. With a slot the label renders as **two** independently inline-parsed runs at their true source offsets (before/after the slot), so search still lands on label text either side of the value; inline formatting spanning the slot is the accepted cost.
- **Editor**: op lines are purely textual (conceal `$`, substitute `-*/` 1:1 with `−×÷`, tint amount; text-keyed span cache — heading hashes and resolved accent tokens are also textual conceals, so they ride the same memo). `$$`/`$?`/bare-`$!`/`$^`/`$~` lines are positional: the value comes from `MarkdownEditorLineIndex.moneyValueAt` (an incremental money pass mirroring the task pass — the entry-balance history and the parallel checkpoint-balance history are both append-only result lists whose per-segment resume state is just their lengths plus the current period-start index, alongside the entry balance and the two target scalars `targetCents` (-1 = none) / `targetAnchor`; truncate-and-append, ~one segment rescan per keystroke) and styles through the positional memo with the value folded into the key (`'m:$value:$text'` — the no-target sentinel is just another value there). The value paints via `_EditorMoneyTotalSpan` (fork `CodeInlinePaintSpan`, substitutes 1:1 for the second marker char, height under the strut; labels `Σ`/`Δ`/`◎`/`Δ=`/`Δ~`, or the "no target" warning chip). Reveal lines show raw dimmed markers and skip the paint. **A value slot moves any row onto the positional path** (the gate is `valueSlot >= 0 || total/delta/diff/span`) since its render now depends on the balance — `moneyValueAt` already indexes every money line, so no index change was needed. At the slot the label's `$` is the 1:1 paint placeholder, exactly like the second `$` of a `$$` marker: `_moneyTotalSpan(atSlot: true)` drops the leading glyph and `filled: false` (op rows) drops the chip fill for the dimmed bare-number look matching the preview. Display rows with a slot substitute their second marker char with the glyph instead of the chip — that substitution **must stay one code unit wide or the caret drifts**, which is why `Δ=` narrows to `Δ` there. On reveal the slot stays literal text so the user edits real source.
- Fence lines are inert on both surfaces; lines longer than `MarkdownMoneySyntax.maxLineLength` (= the editor's 4096 raw-render guard) never parse, so the two ledgers can't disagree.
- Toolbar: ten default shortcuts — `default_money` (`$+ `, guard `money_shortcut_seeded`), the subtract/multiply/divide/set/total/change siblings seeded as one batch via `_seedDefaultShortcutBatchIfNeeded` (guard `money_ops_shortcuts_seeded`), then `default_money_target` (`$! `, guard `money_target_shortcut_seeded`), `default_money_diff` (`$^ `, guard `money_diff_shortcut_seeded`), and `default_money_span` (`$~ `, guard `money_span_shortcut_seeded`) each on their own later-shipped guard.
- **Display config (start balance + currency)**: global start balance (`SettingsKeys.moneyStartCents`) seeds every ledger fold and the `$?` anchor; currency (global `moneyCurrencySymbol`/`moneyCurrencySuffix`, per-note override under `moneyNoteCurrencyPrefix` keys) applies to computed values only — never source amounts, never parsing. **The currency may also be typed inline after the amount** (`$= 500 lei`, `$+ 50 lei coffee`): `MarkdownMoneySyntax.inlineCurrencyEnd` / `labelStartAfterCurrency` recognise the word **only when it equals the note's effective symbol** (ASCII-case-insensitive, whole-word), so nothing is ever guessed — any other word stays label text, and re-configuring the currency turns a no-longer-matching word back into a label. Still display-only: `parse` and `MoneyLineMatch` are untouched, so both spellings fold identically (pinned by a test). The preview and detail sheet drop the word from the label because the row's value already prints the currency; the **editor deliberately leaves it visible** as typed, like every other amount it renders source-faithfully. Works on **both** spellings: the word always sits right after the amount, so it is at the label start on an amount-first row and right after the trailing amount on a label-first one (`$= Net worth: 500 lei as of today`). Label-first rows allow **free trailing text** after the amount (`$!` targets take the shape too): `_scanTrailingAmount` walks candidate tokens right-to-left and the LAST whole token that parses as an amount directly behind a `:` wins — deterministic, never guessed — with a digit`:`digit tight-colon guard so times/ratios (`9:30`, `2024:500`) never read as amounts (`$= Note: 500 at 9:30` finds 500; the old line-end quirk where `$= Standup 9:30` set 30 is gone). Precedence pin: a lowercase one-word lead (`$= a: 100 …`) is the accent-token shape and wins first, so the first number is the amount there. The trailing region `[amountEnd, line.length)` renders as a second label region on both surfaces — value slot included (preview `emitRegion` / editor `emitLabelRegion`); the currency word is dropped by preview + sheet, visible in the editor. A `$` currency word right after the amount is never a slot: renderers go through **`MarkdownMoneySyntax.effectiveValueSlot`**, never `m.valueSlot` directly. Accepted cost of the free-tail rule: `$= Note: 5 cats and dogs` is a visible money row (amount 5) rather than silent plain text. **Money rows also compose with list markers** (`- $= 500`, `1. $+ 50`, nested indent, bullets `-`/`*`/`+`/`•`, ordered `N.`/`N)`; **the heading prefix composes after the marker too — all three chrome prefixes stack**: `- ## $= teal: 500`; task boxes never compose): `listMarkerStart/End` on the match, probes accept the prefix, a `- $…` parse failure falls through to plain list rendering, bulleted rows count in every fold, `isLineLedConstruct` protects them via its trailing probe+parse fallback, the preview wraps the row in list `WidgetSpan` chrome (`_wrapMoneyList`), and the editor emits indent + marker (`-`→`•` 1:1, ordered as typed) under a `CodeHangingTextSpan` root (`hangingChars: markerStart`, both reveal states). **The list-marker prefix renders in the row's style *before* its heading/emphasis mutations** (editor `listStyle`, preview `_wrapMoneyList(markerStyle:)`) — chrome outside the row's own styling, exactly like `_buildListItem`'s marker. Both surfaces used to hand it the styled row instead, so `- **$! Target: 150**` drew a bold bullet with a wider trailing space (and `- ## $$` a heading-sized one), pushing the marker and everything after it off the list's left edge — Alex reported the bullet sitting "more to the right than the rest". **Emphasis wrapper**: a money row may be wrapped in emphasis — `*$~ 2 Change: $ *`, `**$$ Total: $**`, `_` family too — 1–3 uniform marker chars **tight against the `$`** (so `* $=` stays a bullet) with a matching closer (same char, same length) ending the line (trailing spaces ok). Styles the whole row italic/bold (`emphasisItalic`/`emphasisBold` on the match); marker runs are chrome (concealed in the editor — opener rides the unified `chromeFrom` pre-marker run, closer appended concealed by `_emitEmphasisCloser`; never emitted in preview). `parse` reduces its internal end to the closer, so label/amount/slot/currency offsets all respect it; renderers bound free emissions with `MoneyRowLayout.contentEnd`, **never `line.length`**. Tight-but-unclosed / mismatched-length / >3 runs / text after the closer reject the whole line — visibly raw, never a half-styled guess. Fold-inert chrome: wrapped and bare spellings fold byte-identically (test-pinned). Composes with the other layers: `- ## **$= teal: 500 lei**` is a bulleted H2 bold teal money row. **Shared render layer**: per-row shape decisions derive once via `MoneyRowLayout.of(line, m, symbol)` (both renderers; the editor consumes flags+slot and keeps label text on raw offsets), glyphs via `MarkdownMoneySyntax.glyph(kind)`, semantic accents via `MarkdownConstants.moneyAccent(...)`, display/positional predicates `isDisplayKind`/`needsBalance` (editor's positional gate), sheet labels via `displayLabel(...)`; `parse()` constructs every match through one local `match(...)` closure (add fields there). Invariant pinned by test: **parse never accepts a line the probe rejects** — folds probe first, so a probe/parse gap silently drops rows from the ledger. Resolved via `SettingsService.getMoneyConfig(noteId:)` by the editor page on note open / settings return and packed into **one value-equal `MoneyDisplayConfig` object** (`lib/utils/money_display_config.dart` — enabled, startCents, currency, localized `MoneyErrorMessages`), built once in `_refreshMoneyConfig` and handed to every consumer: preview via `PreviewMoneyConfigChanged(config)` → `state.moneyConfig` → `MarkdownRenderService.prepareWithStyle(moneyConfig:)` rebuild key (both call sites — the bloc's `_emitPrepared` and `SourceMappedMarkdownView._buildCache` via `widget.moneyConfig` — now pass the same state object, so half a config is unrepresentable; the old four-loose-params footgun is gone); editor via `MarkdownEditorSpanBuilder.configureMoney(config)` (clears span memos on span-visible change, reseeds the line index); detail sheet via its `config:` param; `SimpleMarkdownPreview` takes `moneyConfig:` too (shortcut editor). Error messages participate in config equality, so a locale change rebuilds cached renders automatically (the page also refreshes them in `didChangeDependencies`, like the empty-preview placeholder). Never route money config through `PreviewThemeChanged` (its dedupe gates would swallow it). Backup: the three global keys ride the settings whitelist; per-note overrides export as `noteMoneyCurrencies` (backup version 6, null-tolerant import).
- **Tap-to-detail**: `$$`/`$?`/bare-`$!`/`$^`/`$~` values are tappable on both surfaces (preview pill recognizer keyed `'money:$lineIndex'`; editor via `ModernEditorWrapper._resolveTapAction` zone `[markerStart, amountStart)` after the shared pass-through guards, gated on the shared `isDisplayKind` — `$^`/`$~` count digits stay editable — enabled through `onMoneyTap` in the interceptor condition). **The `$^ N` / `$~ N` window count is chrome, not content**: neither surface paints it (preview simply declines to emit the run; the editor conceals `[markerEnd, labelStart - 1)` as one — spaces, accent token and count in either order — keeping the single space before the label so the chip and label don't glue together, and revealing it all when the caret lands on the line). Same rule as the accent token, including the opt-out: an *unresolved* accent token keeps the whole run visible as literal source. The editor conceals, never drops, so offsets stay 1:1; a display row is parse-guaranteed to have a space after its marker and before its label, which is what makes that run safe to collapse. Both route to the page's `_handleMoneyTap` → `MarkdownMoneySyntax.collectEntries` (fence-aware via `lineInFence`, O(document) on tap only; returns `entryLines` + `anchorLines` + `targetLines` in order) → `MoneyDetailSheet`. `$?` sheets list entries since the last `$=`; `$^ N` sheets (`MarkdownMoneySyntax.diffWindowEntries`) list the window it measures — the last N balance-changing entries clamped to the current period, from their baseline entry through the tapped row; `$~ N` sheets (`MarkdownMoneySyntax.spanWindowEntries`) list from the Nth-most-recent `$=` (floored at the first checkpoint, note start only when no `$=` exists — matching `displayValue`) through the tapped row, spanning whole periods; bare-`$!` sheets (`MarkdownMoneySyntax.targetWindowEntries`) list the budget window — the active target's declaration (`targetLines.last`, declaration row included) through the tapped row, or just the tapped row when no target exists; the count-taking resolvers derive the count from the `ALL` sentinel (`windowCount < 0`) exactly like `displayValue`, never index with it raw. **All three resolvers live in the grammar lib beside `displayValue`** (they resolve the same reference and must move together — they diverged twice while they lived in the page), taking the `MoneyLedgerCollection` record `collectEntries` returns.
- **Calendar surfacing**: `NoteMoneyLedgerService` (derived in-memory singleton, DatabaseLifecycle-registered, invalidated per-note via `NoteRepository.noteChanges`) computes `{balance, net, title}` per event-linked note; `net` sums op effects only (sets are baseline moves). Attribution: a note's net lands on the UTC date of its event's `startDate` only (recurring events never double-count). Surfaces: `MoneyDayBarProvider` / `MoneyDaySummaryProvider` (priority 90, registered in the resolvers' `defaults`) and a `Δ` month total in the calendar header; refreshed in `CalendarBloc` load/create/update handlers.

## Markdown Colors (colored text + colored highlight)
Two colour-aware inline constructs sharing one palette. Grammar, palette decoding, and contrast resolution live in `lib/utils/markdown_color_syntax.dart` (`MarkdownColorSyntax` + `MarkdownColorPalette`), the single source of truth consumed by the preview renderer and the live editor span builder.

- Syntax: `{name:text}` colours the text; `==name:text==` tints a highlight. Plain `==text==` is unchanged and keeps the legacy amber (`MarkdownConstants.markBackgroundLight/Dark`) — the `yellow` preset's highlight *is* that amber, so `==yellow:x==` and `==x==` render identically.
- Names are lowercase `[a-z0-9_-]`, 1..`maxNameLength` (24) chars. The restricted alphabet keeps the scanner branchless and rejects by shape before allocating.
- **An unresolved name is never consumed.** `{note:see below}` stays literal text and `==note: see below==` renders as an ordinary default highlight with its prefix intact, so defining a colour can only add rendering — it can never retroactively eat existing note text.
- Presets: `red orange yellow green teal blue purple pink gray`, each a light/dark pair mirroring the callout/money palettes. Custom colours (settings) shadow presets of the same name.
- **Custom colours are contrast-resolved once, at palette construction**: a picked colour is used verbatim on whichever theme it already reads on and lightness-shifted only far enough to clear a 3.0 contrast ratio against a fixed reference surface on the theme where it would not. Render time is one map probe + a field read — never contrast maths per span. Reference surfaces are fixed (not theme-derived) so a palette can be built in the service layer without a `BuildContext` and stays a valid cache key across both brightnesses.
- Persistence: `SettingsKeys.markdownCustomColors` stores `name=aarrggbb;name=aarrggbb`. `normalizeName` strips everything outside the grammar, so `;` and `=` can never appear in a name and the encoding is injection-safe. `SettingsService.getColorPalette()` memoizes by source; the key rides the backup settings whitelist.
- **`MarkdownColorPalette` is value-equal on its persisted `source` string**, which is what makes it usable directly as a render-cache key (one string compare, `identical` short-circuit) instead of threading a generation counter.
- Threading mirrors the money config exactly: preview via `PreviewColorPaletteChanged` → state → `MarkdownRenderService` rebuild key (**both** `prepareWithStyle` call sites — the bloc's `_emitPrepared` and `SourceMappedMarkdownView._buildCache` — must pass the same palette); editor via `MarkdownEditorSpanBuilder.configureColors` (clears both span memos). Resolved by the page in `_refreshColorPalette` on note open and on settings return, with a `forceRepaint()` nudge only when the palette actually changed — never a remount.
- **Editor rendering is pure conceal**: `{name:` and `}` (and the `name:` prefix inside `==…==`) are transparent + ~0 fontSize, never substituted or removed, so the line keeps every source code unit and caret/selection offsets stay aligned. Reveal (caret) lines show the markers dimmed.
- Composition: colour runs are parsed recursively on both surfaces, so they nest with emphasis, links, tags, lists, headings, callouts, table cells, and money labels in either direction. They are inert inside inline code and code fences, `\{` escapes them, and **ghosts win** — a colour run inside a `{{ … }}` run is never styled (the editor's ghost-skip branch must fall through for non-ghost `{`, or coloured text silently stops rendering on any line containing a ghost).
- Settings: `lib/pages/markdown_colors_page.dart` (presets listed read-only, custom colours add/recolour/rename/delete, live syntax preview), reached from the markdown settings page via `AppNavigator.toMarkdownColors`.
- Toolbar: two default shortcuts — `default_color_text` (`{red:` / `}`) and `default_color_highlight` (`==yellow:` / `==`) — seeded as one batch via `_seedDefaultShortcutBatchIfNeeded` (guard `color_shortcuts_seeded`). Both bypass the generic applier for `_insertWithGhostSlot`: a selection is wrapped like Bold, an empty selection gets an empty ghost in the slot (`{red:{{  }}}`) with **the whole ghost run selected** so the first keystroke replaces it. The ghost must be *selected*, never merely have the caret inside it — typing into the placeholder leaves the run a ghost (`{red:{{ hello }}}`) and the ghost's dim styling overrides the colour, so the text renders grey and the feature looks broken. The wrapper text is read from the shortcut, so editing it to `{green:` — or duplicating it per colour — keeps the behavior. **The colour name itself cannot be a ghost**: `{{{red}}` makes the ghost scanner consume the outer `{` (inner becomes `{red`), and a leading-space form (`{ {{c}}:…}`) would need the name grammar to accept whitespace, which would start matching pasted JSON. Colour names stay literal by design.

## Ghost Text (fill-in placeholders)
Ghost text is an inline, single-line `{{ … }}` placeholder rendered dimmed, used for workout templates ("fill in your weight"). Syntax + scanning live in `lib/utils/ghost_text.dart` (`GhostText`), the single source of truth consumed by the preview renderer, the editor span builder, the editor tap-handling, and the toolbar shortcut.

- `GhostText.findGhosts(line)` / `matchAt` / `ghostAtOffset` return `GhostMatch { start, end, innerStart, innerEnd }` (line-relative). Markers are `{{` / `}}` (distinct from single-brace counter tokens `{c1}` / `{c2}`).
- **Authoring**: it is a normal default shortcut (`default_ghost` in `DefaultMarkdownShortcuts`, wraps selection as `{{ … }}`), so it appears in the markdown settings Shortcuts list — reorderable / hideable / editable like Bold. `MarkdownBarService._seedGhostShortcutIfNeeded()` is a one-time migration (guarded by the `ghost_shortcut_seeded` setting) that appends it to pre-existing profiles. The page special-cases it in `_handleShortcut` (caret lands between the markers on an empty selection).
- **Preview** (`LineBasedMarkdownBuilder._buildGhostSpan`, reached from `_parseInline`): markers hidden, inner text dimmed via `LineMarkdownStyle.ghostColor`, search-highlight offsets preserved on the inner text. Tapping a ghost fires `onGhostTap(absStart, absEnd)` → plumbed service → bloc (`bindCallbacks`) → `MarkdownPreviewBlocView.onGhostTap` → page `_handleGhostTap`, which switches to the editor and **selects** the run (no mutation).
- **Editor**: `_buildGhostEditorSpan` (a re_editor `CodeLineSpanBuilder` on the content controller) dims the run and conceals the `{{` / `}}` markers (transparent + ~0 width — characters stay in the model so caret/selection offsets never desync). Tapping a ghost selects the whole run (`ModernEditorWrapper._maybeActivateTappedGhost`, armed by a pointer-up + caret-landing check so arrow-key navigation never triggers it). Typing replaces the selection; tapping away keeps the placeholder (nothing is mutated, so "restore on leave" is automatic).

## Vocabulary Autocomplete (v32)
User-defined term lists that the editor offers while typing, so the same exercise stops being written three different ways. **Nothing it inserts is new syntax** — an accepted suggestion is plain text, which is why existing notes, every markdown construct, exports and the preview pipeline are all untouched by this feature. Design record: `docs/vocabulary-autocomplete-feature.md`.

- **Data**: `vocabularies` (name, `is_enabled`, `sort_order`) + `vocabulary_items` (`vocabulary_id`, `term`, `sort_order`), both carrying the five CRDT columns **from birth** (the v29 template shape — no `DEFAULT ''`, nothing to backfill). Terms are rows, not a delimited blob, because any delimiter is a term someone eventually types ("Squat, paused") and because per-row identity is what survives a re-save. The column is `term`, not `text` — `text()` is Drift's column builder and a getter of that name would shadow it. **No index**: both tables load wholesale into the facade at first use, the v29 reasoning.
- **`;;` lines are section headers**, stored as ordinary `vocabulary_items` rows so they carry position and identity exactly like terms — the diff-based save reorders and tombstones them with no special case, and a list round-trips through the editor unchanged. Only the suggestion path filters them (`Vocabulary.suggestibleItems`, consumed by `Vocabularies.updateCache`); the grammar lives on `VocabularyItem` (`commentMarker`, `isCommentText`, `commentLabel`) because that is the one file both the facade and the service already import, so neither depends on the other. Two characters, not one, so a term keeping a single semicolon is never swallowed. Headers de-duplicate like any other line, and **"how many terms" always means `Vocabulary.termCount`**, which excludes them.
- **The list editor is a page (`lib/pages/vocabulary_editor_page.dart`), not a bottom sheet.** A sheet is capped at a fraction of the screen *and* gets no keyboard padding from the framework, so a long list showed a handful of lines and the only way to see its shape was to dismiss the keyboard. A `Scaffold` resizes for the keyboard itself — hence **no `viewInsets` arithmetic anywhere in that page**, unlike every sheet in the app. The name field and enable switch fold away while the terms field has focus (the header chevron re-opens them without dismissing the keyboard), so the list gets the whole body.
- **`VocabularyDao.saveItems` is a diff, never a wipe-and-reinsert.** The editor edits the whole list as one block, so every save re-submits every term; wiping would fork each row's id and bump each version, turning one edited word into a full-list conflict once devices merge. Unchanged terms keep their row and version, removals **tombstone**, and a re-added term resurrects the row it had before. Re-saving an untouched list issues no writes at all.
- **`VocabularyService`** is the `EventTemplateService` shape (whole table loaded once, republished after every mutation, `forTesting`, `DatabaseLifecycle` reset clearing singleton **and** facade). It owns term normalization: `parseTerms` trims, drops blanks and de-duplicates **folded**, so "Bench press" typed twice in different case collapses to the first spelling. Store verbatim, match folded — the tag roadmap's canonicalization rule.
- **`Vocabularies` (lib/constants)** is the synchronous facade the editor reads per keystroke: `candidates` is the flattened, pre-folded candidate list of *enabled* lists only (folding happens once per publish, never per keystroke), and `byName` resolves a ghost placeholder to a list with singular/plural tolerance in both directions. `idsForScopeTokens` is the trigger-side resolver and is deliberately looser — folded **prefix** match (`@exer:` → "Exercises", `@push:` → "Push Day") *or* the same plural tolerance — returning a **set**, because one token naming several lists is a feature and not an ambiguity to reject.
- **Two entry points, one session** (`VocabularySuggestionController`, lib/controllers): a **trigger character** (`SettingsKeys.vocabularyTriggerChar`, default `@`) typed after whitespace, and an **engaged ghost** — the wrapper already selects a tapped `{{ … }}` run whole, so the controller reads that straight off the selection and needs **no coupling to `ModernEditorWrapper`'s tap state at all**. **Either entry point can scope itself to particular lists.** A named placeholder (`{{exercise}}`) scopes to that list; on the trigger side, everything before the run's **first colon** is a comma-separated scope segment — `@exercise:ben` filters inside Exercises, `@exercises,meals:oat` inside the union of the two, `@ben` is unchanged and searches everything. Splitting the *run* (not the line) keeps prose colons (`sets: @ben`) out of it. **Resolution is allowed to fail and never blocks typing**: a scope naming no list falls back to an unscoped query over the raw run *as written*, colon included, and an omitted one (`@:ben`) is an unscoped query for what follows. Accepting consumes the whole run, scope included. The one unreachable shape is `:` configured as the *trigger*: the separating colon is then a mid-word trigger occurrence and the guard protecting `a@b.com` fires first — do not widen that guard to recover it. Once the user types over the engaged run the braces are gone, so the ghost's start offset is kept as an **anchor** and the session keeps filtering from there; a second space, a caret move before it, or a non-collapsed selection abandons it.
- **`VocabularyTrigger` (lib/utils)** owns the "is the caret in a query" rule — a *typing* grammar, never persisted, rendered or exported, which is why neither render surface consumes it. The trigger needs whitespace before it and a non-space after, so `3x8 @ 60kg`, `5x5@100kg` and `a@b.com` all stay ordinary text; it returns null inside a ghost run (ghosts win, as everywhere else). Callers add the editor-state guards it cannot see: collapsed selection, not composing, not a fence line, under `maxStyledLineLength`.
- **`VocabularyMatcher` (lib/utils)** ranks prefix > word-start > substring > subsequence, folding through `normalizeForSearch` (never a second fold table), capped at 8, with the user's own list order as the tie-break inside every tier. Bucketed rather than sorted, so input order survives and a full prefix tier short-circuits the scan. Its `vocabularyIds` filter is a set: `null` unscoped, an **empty set matches nothing** — a caller whose scope resolved to nothing decides upstream (where the raw run is still available) rather than silently searching everything.
- **The bar replaces the toolbar's content at identical height** (`VocabularySuggestionBar`, branched inside `MarkdownBar.build` behind a `ValueListenableBuilder` so only the bar rebuilds) — 40px pills inside 8px padding, matching the shortcut row exactly. A session opening must never shift the editor; capture speed is the whole point, and a jumping toolbar would cost more than the autocomplete saves. It stays inside the existing `CodeEditorTapRegion`, or tapping a pill would drop the keyboard. A scoped session labels itself with the resolved list names ahead of the pills, inside that same height budget — user data, so no l10n key.
- **Accepting** replaces `[start, end)` through the page's `_applyVocabularyInsertion`, which carries the full programmatic-insert discipline (`_isProcessingTextChange` guard, one `runRevocableOp` so a completion is a single undo step, `_previousTextLength` resync) — the `_handleShortcut` contract. A trailing space is added only when the next character is not already one, so end-of-line accepts keep typing flowing while `{{exercise}} 3x8` keeps its spacing.
- **re_editor's own `CodeAutocomplete` is deliberately unused** even though the fork ships it intact: it hijacks Enter and the arrow keys while open (which breaks "never block free typing"), anchors a popup at the caret rather than at the thumb, matches prefix-only, and does not wrap its insertion in `runRevocableOp`. No fork change was needed for this feature.
- **Not shipped, on purpose**: no render-time highlighting of known terms (it would touch the span builder's perf-critical memos and both render surfaces), no per-term insertion templates, no usage learning, no per-note/folder binding. `candidateSource` on the controller is the seam the tag roadmap's Tier 2.4 `#tag` autocomplete and the `/` slash-menu idea plug into — same session, bar and insertion path, different provider.

## Data And Persistence Rules
- The database uses Drift with a singleton active database and background `LazyDatabase` connection.
- Folder, note, content chunk, calendar-event, calendar-event-occurrence, calendar-event-absence, calendar-event-template (v29), calendar-event-skip (v30) and vocabulary/vocabulary-item (v32) tables include CRDT-style metadata for future sync: `hlcTimestamp`, `deviceId`, `version`, `isDeleted`, and optional `deletedAt` where supported. On `calendar_events` (v27) and `calendar_event_occurrences` (v28) `hlc_timestamp`/`device_id` carry `DEFAULT ''` (the v29/v30/v32 tables were born with the block and carry none) — an `ALTER TABLE` on a populated table demands a default; the migrations backfilled real identity and every write path stamps, so `''` after that means something skipped the DAO.
- Notes store metadata separately from content. Content is chunked and may be compressed; avoid unnecessary full-content copies in hot editor paths.
- Reorder operations should be transactional and preserve user-defined positions.
- Search uses both SQLite/FTS and an app-level index; keep indexes in sync when notes are created, updated, deleted, or moved. **One normalization for all search surfaces**: `normalizeForSearch` / `searchTokens` / `tokenizeForSearch` in `lib/services/folder_search_service.dart` (diacritics map in `SearchConstants`, incl. Romanian comma-below ș/ț) are shared by the isolate bulk indexer, the incremental index, the query side, and the calendar agenda search — never reintroduce a local fold or tokenizer (the isolate once had its own map, it drifted, and bulk-indexed Romanian words became unfindable). `removeDiacritics` iterates **code units**, not one-character substrings, and consults `_diacriticsByCodeUnit` — which is **derived from `SearchConstants.diacriticsMap` by comprehension**, so it is a re-keying of the canonical table and not the second table the warning above forbids; every key is a single UTF-16 code unit, units `<= 0xBF` skip the lookup, and a string needing no fold returns itself unallocated. `searchTokens` keeps duplicates on purpose: the index counts them as real term frequency.
- Counters use `noteId == ''` for global values in `counter_values`; per-note values use the real note id.
- Custom markdown shortcuts can bind up to two counters via `CustomMarkdownShortcut.counters` (`List<CounterBinding>`). Each binding has a `counterId` and a `CounterOp` (`increment` / `decrement`). The `{c1}` / `{c2}` tokens in `beforeText` / `afterText` / repeat wrapper text expand to the matching binding's post-mutation value at insertion time. Each token occurrence triggers exactly one mutation per repeat iteration. Token expansion runs through `ShortcutApplier` via the `CounterMutator` callback, which routes to `CounterBloc` (`IncrementCounter` / `DecrementCounter`) and respects the global vs per-note scope contract. The legacy `counterId` field is preserved for backwards compatibility — when `counters` is empty but `counterId` is set, `effectiveCounters` synthesises a single increment binding so applier logic stays uniform.
- `CustomMarkdownShortcut.category` is an optional free-text grouping label (`null`/empty = uncategorised). It is settings-only organisational metadata: it never affects toolbar order or rendering, has no separate persisted registry (the category set is derived from the shortcuts themselves), and is additive in the profile JSON, so older profiles and backups load unchanged.
- Settings are stored through `UserSettingsDao`, `SettingsService`, and `SettingsKeys`. Do not scatter raw string keys.
- **Settings pages are searchable through one matcher**: `lib/utils/settings_search.dart` (`SettingsQuery`, `matchSettingsEntry`, `matchesSettingsQuery`) rendered by `lib/widgets/settings_section_list.dart` (`SettingsEntry` / `SettingsSectionData` / `SettingsSectionList`). Never filter with a local `toLowerCase().contains()` — that is a second fold and it silently breaks `ro`/`de` (`evidentieri` must find `evidențieri`, `schriftgrosse` must find `Schriftgröße`). `FoldedText` exists because the shared fold is **not** length preserving (`ß`→`ss`, `æ`→`ae`), so highlight spans must be mapped back through its index table rather than applied to the source directly. Matching is deliberately exact-substring with multi-token AND and no fuzzy/ranking: rows keep their declaration order so sections and learned positions survive filtering. A page declares rows as `SettingsEntry`s whose `builder` receives the pre-highlighted title/description, so each row keeps its own widget type; hidden `keywords` (localized, comma-separated ARB strings) are matched but never rendered.

## Sync And Accounts (Phase 01 — identity and pairing)
- Cloud sync is being added in phases on top of the CRDT columns already present on folders/notes/chunks. **Phases 00 (identity) and 01 (pairing) are shipped.** A user can sign in with Google and link one other account into a pair; no note, folder or event data crosses the wire yet, there is no schema change, and no `sync_metadata` / `HybridLogicalClock.receive()` usage.
- **Local SQLite stays the source of truth.** Firestore is a transport, never the primary store. Any later phase that inverts this is wrong.
- **One platform gate**: `SyncAvailability.isSupported` (`lib/services/sync_availability.dart`) is `!kIsWeb && (Platform.isAndroid || Platform.isIOS)`. `kIsWeb` is checked first because `dart:io`'s `Platform` throws on web. Every sync entry point routes through it — never test the platform directly. Windows/Linux/macOS stay local-only because `google_sign_in` ships no implementation there, regardless of what the Firebase plugins now claim to support.
- `main.dart` calls `Firebase.initializeApp` only when the gate passes, wrapped in try/catch: a checkout without `google-services.json` must still launch, just without sync.
- **`AuthService` is an interface** (`lib/services/auth_service.dart`) with two bindings chosen in `injection.dart`: `FirebaseAuthService` when the gate passes **and** `Firebase.apps` is non-empty, `NoOpAuthService` otherwise (unsupported platform *or* failed Firebase init). Blocs/UI consult `AuthService.isAvailable` — the bound service, never the platform gate — so a degraded binding reads as "unavailable" instead of a sign-in button that can only fail. This keeps `firebase_auth` types out of the bloc/UI layers and off the desktop path. `AppUser` (`lib/models/app_user.dart`) is the layer boundary — never surface Firebase's `User`. `SyncBloc` is covered by `test/bloc/sync_bloc_test.dart` against a fake `AuthService`.
- **`AuthService` is deliberately NOT on the `DatabaseLifecycle` reset contract.** That contract exists for singletons caching a `late AppDatabase`; the Firebase identity is *global*, so tearing it down on a database switch would drop the auth stream for nothing. Pairing state *is* per-database — it lands in `user_settings` via `SettingsService`/`SettingsKeys`, and `PairingService` is on the reset contract so its cache and its snapshot listeners follow the active database.
- **Pairing (Phase 01)**: `PairingGateway` (`lib/services/pairing_gateway.dart`) hides `cloud_firestore` exactly as `AuthService` hides `firebase_auth` — only `PairRecord`/`InviteRecord`/`PairProfile` cross the boundary, and `FirestorePairingGateway` maps every `FirebaseException` onto a `PairingError`. `PairingService` owns the workflow; `PairingBloc` (`lib/bloc/pairing/`) is separate from `SyncBloc` because pairing is orthogonal to auth. `firestore.rules` is committed at the package root.
- **The locally stored `pairId` is a cache, not the truth.** The server answers "which active pair contains my uid" (`findActivePairs`), reconciled on load and on every auth change. Without that inversion, a second device, a second local database, or two people redeeming each other's codes fork into two pairs that never converge. When a uid *is* in two active pairs, **the earliest `createdAt` wins and the rest are tombstoned** — both devices compute that independently, so it converges with no conflict UI. Rules cannot enforce one-active-pair-per-uid (it needs a query); this is a client invariant that only holds because reconciliation runs.
- **Unpairing tombstones the pair, never deletes it** (`status: 'ended'`, `endedBy`, `endedAt`; `members` never shrinks). Both sides keep read access, so the passive partner can still learn who ended it, and the doc survives to anchor the Phase 02+ subcollections — Firestore has no recursive delete without Cloud Functions, which Spark does not include. Re-pairing always mints a fresh `pairId`.
- **Pairing is online-only on purpose.** Firestore's offline queue would accept every write and resolve nothing, so writes go through `runTransaction`, authoritative reads use `Source.server`, and every gateway call is bounded by a timeout that surfaces as `PairingError.offline` rather than a spinner that never ends. A failed reconcile never clears the cache — opening the Sharing page offline must not read as "not paired".
- **The pairing settings keys are deliberately absent from `BackupService._exportSettings`**: restoring a backup onto a third device must not clone a pair membership. `pairing_pending_code` is persisted so an app restart between generating and redeeming cannot strand the creator.
- Invite codes are 8 characters over `23456789ABCDEFGHJKMNPQRSTVWXYZ` — no `0/O/1/I/L/U`, because the code gets read aloud. Invites are create-only with a 10-minute lifetime bounded in the rules against `request.time` (a skewed device clock must not mint a year-long invite), and `list` on the collection is denied so codes cannot be enumerated.
- **A pair carries the `inviteCode` it was born from, and the rules `get()` that invite to authorise the create.** Membership alone is not proof of consent: uid is not secret (the Sharing page prints it), so without this clause anyone could force a pair on anyone, and a planted pair with an earlier `createdAt` would win reconciliation and evict the victim's real one. The invite exists before the pair, so a rules `get()` can see it — the same-batch limitation only blocks the reverse direction. `permissions` is seeded closed at create and each member may only ever rewrite its own entry.
- **Firestore rules treat a missing document as `resource == null`**, so `resource.data.x` errors and denies. The `invites` `get` rule allows `resource == null` explicitly and `redeem` re-raises `permissionDenied` as `codeInvalid`; without both, a one-character typo — the most common failure in the flow — tells the user "permission denied".
- `firestore.rules` **and** `firestore.indexes.json` are committed and deploy together. The composite index (`members` array-contains + `status`) is not optional: without it every reconcile fails `failed-precondition`, silently in release builds.
- Errors carry the `PairingAction` that produced them. The code field only renders redemption failures — a failed "create a code" must not put a red border on a field the user never touched.
- Google Sign-In 7.x is a breaking rewrite from 6.x: `initialize()` must complete once before any other call, `authenticate()` **throws** `GoogleSignInException(code: canceled)` on user dismissal rather than returning null (mapped to `null`, not an error), and `authentication` carries only `idToken`. No `serverClientId` is passed in Dart — Android resolves it from `google-services.json`'s `client_type: 3` entry via the Gradle plugin, iOS from `Info.plist`.
- Firebase config files (`google-services.json`, `GoogleService-Info.plist`, `lib/firebase_options.dart`, `firebase.json`) are **gitignored**; regenerate with `flutterfire configure --platforms=android,ios`. The generated options intentionally cover android+ios only, so a stray desktop call throws `UnsupportedError` loudly instead of half-working.

## Import/Export Pipeline Rules
- Every layer has paired `createX` / `importX` methods on `FolderDao`/`NoteDao`, the matching repositories, and the storage services. `createX` always stamps `createdAt`/`updatedAt` to "now"; `importX` accepts caller-supplied timestamps so a round-tripped archive preserves originals. Never widen `createX` with optional timestamp params — add an `importX` overload instead.
- All UI access to import/export goes through `ImportExportBloc`. Pages dispatch events (`ExportNoteRequested`, `ExportFolderRequested`, `ExportItemsRequested`, `ImportFileRequested`, `ImportArchiveRequested`) and react to `ImportExportInProgress` / `ImportExportExportSuccess` / `ImportExportImportSuccess` / `ImportExportFailure`.
- Archive format: per-folder `_folder.json` (carries name, `createdAt`, sort orders), per-note JSON/MD/TXT bodies, top-level `manifest.json` with `version` (`ImportExportService.archiveVersion`). When bumping the manifest schema, also bump `archiveVersion` and accept the previous version in `_assertSupportedManifest`. Reject newer versions with `UnsupportedArchiveVersionException` before any DB writes.
- Temp files: every export lands under `getTemporaryDirectory()`. `shareExport` deletes the file after the share sheet returns; `sweepStaleExports` runs at app startup from `main.dart` and clears artefacts older than 24h. New export entry points must funnel through these helpers — do not invoke `SharePlus` directly from blocs/pages.
- Calendar `.ics` export: `IcsSerializer` (floating local time, `DTSTART` moved to the first real occurrence, workdays = `BYDAY` + holiday `EXDATE`s, holidays-only/specific dates = `RDATE`s, 730-day expansion bound) → `ImportExportService.exportCalendar` → `ExportCalendarRequested` on `ImportExportBloc`. `ExportFormat` deliberately does **not** grow an `ics` variant — it would leak into every note-format picker; `.ics` rides `ExportResult.eventsExported` and the sweep list instead.

## UI And UX Direction
- This is a productivity/tracking app, not a marketing site. Favor compact, stable, repeat-use interfaces.
- Use Material 3 and existing constants for spacing, text, colors, icons, and dimensions.
- Keep controls touch-friendly: icon buttons, tooltips, menus, toggles, sliders, reorder handles, and clear destructive confirmations.
- Avoid layout shifts in editor, toolbar, counters, and folder/note lists. Stable dimensions matter more than decorative styling.
- Keyboard avoidance in the note editor is manual and gated, not `Scaffold`'s: the editor Scaffold sets `resizeToAvoidBottomInset: false` and pads its body by `_keyboardInset(context)`, which only trusts `viewInsets.bottom` while the page owns an input connection (`_contentHasFocus`, mirrored from `_contentFocusNode`, or an open search bar). Android can hand back a stale keyboard inset after a resume — ungated, that inset floats the markdown toolbar above an empty strip until the app is restarted. The same gated value drives `previewWhenKeyboardHidden` and the toolbar's bottom safe-area spacer (`viewPadding.bottom` when no keyboard). `main.dart` completes the pair by unfocusing on `AppLifecycleState.paused` so the IME animation finishes while the window is still live.
- For any capture-oriented feature, prefer quick capture patterns: reusable templates, pinned counters, recent/frequent actions, clear save status, and minimal taps.
- Respect light/dark/system themes and supported locales.

## Generated And Local Package Notes
- `packages/re_editor/` is a local editor fork, perf-tuned for this app. Key optimizations to preserve:
  - `CodeLines.asString` uses a 2-slot round-robin cache (LF+trimNewlines vs LF-only calls alternate without thrashing).
  - `_CodeLineSegmentQuckLineCount` sub-counts with a `_hashCache` field; `==` short-circuits on length/dirty/lineCount/charCount before deep comparison.
  - `findDisplayParagraphByLineIndex` and `_findDisplayRenderParagraph` in `_code_field.dart` use binary search on the sorted paragraph array.
  - `_CodeParagraphCache` is a bounded LRU (max 512 entries) that evicts head on overflow.
  - `_CodeHighlight` debounces highlight requests at 50 ms to avoid per-keystroke re-highlight.
  - `_kInitialCodeLines` uses `List.unmodifiable` on both levels for write-protection (no `const` because sub-objects aren't `const`).
  - When adding new mutation paths to `CodeLines`, call `cloneShallowDirty()` (not the public constructor) to preserve the `_segmentEnds` / `_asStringCache` reset contract.
  - `CodeInlinePaintSpan` (`code_paragraph.dart`): a placeholder span that reserves a box in the line layout and custom-paints onto the canvas after `drawParagraph` (used by the editor's task checkboxes). It occupies exactly one U+FFFC code unit, so span builders must substitute it 1:1 for a single source character; keep its height under the strut height (placeholders ignore `forceStrutHeight`) or the line grows. `_ParagraphImpl` pairs paint spans with `getBoxesForPlaceholders()` boxes lazily on first draw.
  - `CodeDecoratedTextSpan` + `CodeTextDecoration` (`code_paragraph.dart`): a text run that paints a rounded chip BEHIND itself (before `drawParagraph`) — used for the editor's `#tag` pills and inline-code chips. Unlike `CodeInlinePaintSpan` it reserves no layout space; the text stays ordinary editable text.
  - `trucate` / `_dropPrefix` keep untouched subtrees by identity (no rebuild) — required so decorated/placeholder subclass spans survive the hanging-indent marker/content split; don't regress this to unconditional copies.
  - `_CodeFieldRender.describeSemanticsConfiguration` announces the editor as a multiline text field (value from the `asString` cache) — without it the raw-canvas editor is invisible to screen readers. `codes`/`hasFocus`/`readOnly` setters call `markNeedsSemanticsUpdate()`.
  - `CodeFindController.goToMatch(int index)` is an app-added method: it clamps the index, pushes exactly one new `CodeFindValue`, and centers the match. It exists so the note search bar's match list can jump to an arbitrary hit without stepping `nextMatch()` (each step pushes a value, and every push costs a selection write plus a scroll).
- Treat `packages/re_editor/` as part of the workspace for bug/perf fixes, but avoid API-breaking changes.
- Generated localization Dart files are outputs from ARB files.
- `lib/database/database.g.dart` is generated by Drift.
- Android/iOS/macOS/Linux/Windows/web folders are platform shells; prefer app-level fixes in `lib/` unless the issue is platform-specific.

## Good Defaults For New Tracking Features
- If a feature captures user data, decide whether it belongs in note markdown, a counter, settings, or database schema before adding new storage.
- Prefer note-level features when the data is naturally part of a session or entry, and counter features when the value needs repeated numeric updates or cross-note aggregation. Derived-from-content features (the money ledger is the reference case) beat a parallel store that can drift.
- Preserve backup/export support for any persisted user data.
- Make sorting, pinning, and reordering explicit when users are likely to curate the information manually.
- Keep input flows fast: sensible defaults, remembered choices, localized validation, and no unnecessary dialogs.
