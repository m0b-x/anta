## QA Harness (device automation)
- QA builds carry `--dart-define=ANTA_QA=true --dart-define=ANTA_QA_DB=qa` (plus optional `ANTA_QA_SKIP_ONBOARDING=false`, and `ANTA_QA_PERMISSION_PROMPT=true` to let the launch permission dialog appear — off by default, since a dialog nobody scripted would sit on the first screen of every flow). In QA mode the app opens the `qa` database inside the same `gym_notes/` directory and namespaces its SharedPreferences prefix, so an automated run never touches the owner's default database.
- A QA build is also cut off from Firebase: identity is global to the install, not per database, so `SyncAvailability.resolve` answers false when `QaMode.enabled` (Firebase is never initialized; `NoOpAuthService` and `NoOpPairingGateway` are registered). `--dart-define=ANTA_QA_CLOUD=true` (`QaMode.allowCloud`) is the deliberate opt-in for testing sync; the QA agent reports the gate as `cloud` and `qa doctor` warns when it is on.
- Two marker files in the app documents dir steer the next QA launch and are consumed by it: an empty `qa_reset` clears the QA prefs and deletes `gym_notes/qa.db*`, and a `qa_seed.json` (full-backup JSON) is imported. On Android they travel through `/data/local/tmp` + `adb shell run-as` (debug builds only); on the iOS simulator and macOS they are plain file writes into the documents directory on the host (`xcrun simctl get_app_container … data` + `/Documents`, `~/Library/Containers/com.alexzamfir.anta/Data/Documents`). `QaBootstrap` prints each `[qa]` line **and** keeps it in `QaBootstrap.log` (text) and `QaBootstrap.entries` (typed `{kind, ok, message}`), both handed back by the agent over the VM service so the driver branches on `ok`, never on wording.
- `tool/qa/qa.dart` is the driver (`devices`, `boot`, `run --fresh --seed`, `relaunch`, `shot`, `dump`, `tap`/`type`/`swipe`/`key` by label, `log`, `errors`, `doctor`, `agent`) for three targets — Android emulator (adb + uiautomator, `--via agent` optional), iOS simulator and the macOS desktop build (both through the in-app agent). Nothing under `tool/qa/src/` imports Flutter; `test/qa/` covers it against fakes, real captured `uiautomator` dumps and a fake VM service.
- `test_driver/main_driver.dart` enables the Flutter Driver extension (text-entry emulation off) and installs `test_driver/qa_agent.dart`: a semantics dump with physical-pixel rects and role flags, pointer/key/text synthesis (`TestTextInput`, so any Unicode and no soft keyboard), a `canPop`-guarded `popRoute`, an inspector screenshot, and an error ring buffer — reached through `request_data` over the VM service (`ext.flutter.driver`). `qa run` gives DTD + VM URIs; `qa relaunch` starts the installed build with a fixed `vm-service-port` and no auth codes (`simctl launch` argv, `FLUTTER_ENGINE_SWITCH_n` env, or `am start` extras) so the agent is reachable in ~2 s without a build. URIs are recorded per device (`build/qa/vm_<id>.txt`).
- Reference: [docs/qa-harness.md](docs/qa-harness.md) and the `qa-emulator` skill. The QA database is a *runtime* selection, not a new persistence pattern — `DatabaseLifecycle` and every rule above still apply to it unchanged.

- **The calendar layer (2026-09-26).** `tool/qa/fixtures/calendar.json` is a relative-dated seed (`"startDateMs": "{{today-28}}"`, resolved by the tool before the push, never edited on disk) covering every calendar state a pass needs; `tool/qa/flows/calendar/*.txt` are the saved flows — twenty-three since Tier 3 of the language adoption (2026-10-03), `00_open` … `22_palette` — and `qa flows calendar` runs them, all green from a fresh install (`21_removed_holidays` consumes the seed's suppressed holiday, so a lone re-run of it needs `qa relaunch --fresh --seed`); `qa set theme=dark locale=de text-scale=2.0` switches the running QA build without a relaunch (text scale through `QaOverrides` + `QaTextScale` in `MaterialApp.builder`, QA builds only; locale and theme through `AppSettingsBloc`); `--setting key=value` patches the seed's settings. Editor rows, chrome and body carry `SemanticsIds` (`event-*`, `event-form`, `event-row-<eventId>` on day-panel rows) because titles are ambiguous against the marker labels; the filter surfaces carry their own (`filter-…`, `filter-list-…`, `category-pick-…`, `filter-preset-…`), and so does every sheet the language-adoption tiers rebuilt (the `calendar-ui` skill's catalogue). On the agent path `scroll-to` settles until no frame is scheduled before it dumps (`_flingSettleMs`, 2026-10-03): a fling under iOS physics outlived the swipe's 500 ms settle and left the found row at the viewport's edge. Every menu is a popup route since 2026-09-27 (`FormMenuRow`, the header menus), so its items are `menuItemRadio` nodes with ids on both platforms — the `MenuAnchor` gap of 2026-09-26 is closed. Rule: a flow is updated in the slice that changes its screen; the `ui-revamp` gate runs the flows in the last slice.
- **The alerts layer (2026-10-04; the pair 2026-10-05).** `tool/qa/fixtures/alerts.json` puts three events minutes ahead of the run with the pair `{{minute+N}}` / `{{minuteday+N}}` — two Alarm-tier alerts, one on an event that is removed after it rings, and a Reminder-tier one the flows leave armed for a look at the shade — and `tool/qa/fixtures/alerts_pair.json` two Alarm-tier events on one minute, the seed that stacks two alarm pages. `qa flows alerts` runs three flows (the settings page's test ring, an event's ring, Keep on the removable one and the calendar row afterwards) and `qa flows alerts_pair` one (the two pages stopped one after the other); `test/qa/alerts_fixture_test.dart` and `test/qa/alerts_pair_fixture_test.dart` pin the fixtures. **The seed goes in with `qa relaunch --fresh --seed`, never with `qa run`**, which resolves the minutes and then builds — the build comes out of the lead, and an alarm that lands in the past arms nothing. Recipe, ids and the device facts the rework learned: the `qa-emulator` skill, "The alerts pass".
