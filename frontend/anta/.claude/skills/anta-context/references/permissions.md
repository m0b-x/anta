## Permissions (2026-09-20)
- **One system for what the operating system allows.** `AppPermission` (`lib/models/app_permission.dart`) is the catalogue: `notifications` and `exactAlarms` are **essential** (a feature cannot work without them), `fullScreenIntent` and `batteryOptimization` are **recommended** (a feature degrades). `PermissionSnapshot.needsAttention` means "an essential permission is denied" and is the single definition behind the launch dialog, the drawer row's warning subtitle, the calendar settings row and the save-time snackbar; a recommended gap never nags.
- Layers: `PermissionsPage` / `PermissionPromptDialog` / the Alerts hub banners → page-scoped `PermissionsBloc` → `PermissionService` (GetIt singleton) → `PermissionGateway` (`AndroidPermissionGateway`; `NoOpPermissionGateway` on iOS, desktop, web and every test, where the page says "Nothing to allow"). `AlertGateway` no longer answers permission questions at all. The service holds no database reference (it reads its two settings through `SettingsService.getInstance()` per call), so it stays off the `DatabaseLifecycle` contract like `AuthService`.
- **The snapshot is live, not stored.** `PermissionService.snapshot` (a `ValueListenable`) is re-read on every `AppLifecycleState.resumed` (the only way a permission changes outside the app's own prompt), after every request, at DI time (unawaited) and when the Permissions page opens. Reads are last-writer-wins by generation, so a slow read can never overwrite a newer one. Read-only surfaces (drawer subtitle, calendar settings row, alert editor hint) bind to the listenable behind a `GetIt.I.isRegistered` guard — the `AlertScheduler.registryRevision` precedent — so widget tests that never register the service are unaffected. Surfaces that **act** own a page-scoped bloc; never register `PermissionsBloc` app-wide (its one-shot `notice` would fire on every mounted listener). Its handlers run concurrently (bloc's default transformer) and the page dispatches `PermissionsStarted` and `PermissionsRefreshRequested` together, so every emit re-applies the bloc's own `_launchPromptEnabled` rather than trusting whichever handler built the first `PermissionsReady`.
- **Android answers in one round trip** on the app-owned `com.alexzamfir.anta/permissions` channel (`MainActivity`): a key **absent** means "not a thing on this Android version" (exact alarms outside API 31–32, because `USE_EXACT_ALARM` makes it unconditional from 33; full-screen intent below 34) and the row is simply not listed; **`null`** means the query threw (`PermissionStatus.unknown`, rendered "Couldn't check", never "All set" and never a launch-dialog trigger); and `notifications` is false when the app-level switch is off **or** any of the three alert channels that can cost an alert (`alerts_reminder`, `alerts_alarm_v2`, the `alarm` package's `alarm_plugin_channel` — the low `alerts_quiet` of 2026-10 is left out on purpose) is blocked — a blocked channel drops alerts as silently as a revoked permission and is fixed on the same system page. A lowered channel importance is a user preference, not a denial.
- **A request must always do something.** `PermissionService.request` runs the system prompt when there is one and falls through to the permission's own settings page when the platform answers `blocked`. Android cannot say "permanently denied" as a query, and the app lifecycle cannot either (a permanently denied request still starts and finishes a transparent system activity, so `inactive → resumed` fires with no dialog on screen); the gateway derives it from `shouldShowRequestPermissionRationale` **before and after** the prompt — either true means a dialog was answered, neither means nothing was shown. The one misread, a never-asked dialog dismissed without an answer, lands on the settings page, which is benign. A `blocked` answer is remembered per permission for the session so the row offers "Open settings" outright, and forgotten the moment that permission reads granted again, because a grant made in system settings resets Android's refusal count. Settings pages open with plain `startActivity` from the activity (no `NEW_TASK`, so Back returns to ANTA), each falling back to the app details page; the plugin's `requestExactAlarmsPermission` / `requestFullScreenIntentPermission` are deliberately unused because they hold a plugin-wide "request in progress" flag until an activity result arrives, and every prompt is serialized in the service for the same reason. Battery exemption stays a link, never a request (Play policy).
- **Launch dialog** (`PermissionLaunchPrompt`, called from `main.dart`): after onboarding completes, or once `restoreLastLocation()` has finished for a returning user (so the dialog is never buried under replayed routes), never on a launch an alert took over, and never in a QA build unless `--dart-define=ANTA_QA_PERMISSION_PROMPT=true`. "An alert took over" is recorded as a **fact**, not read off the queue: `_drainPendingNavigation` runs synchronously right after the restore is queued, so by the time the restore has finished `PendingNavigationQueue` is always empty — `_MyAppState` latches `_alertNavigationSeen` when a drain hands anything out, awaits the (bounded) launch-intent read before deciding, and `PermissionLaunchPrompt.maybeShow` asks `isInterrupted` both before and after its own async read. A ring that starts later simply pushes the alarm page above the dialog. It is due when the "Check at launch" option is on, something essential is missing, and the stored acknowledgement does not **cover** the current gap. The acknowledgement is `"<deviceId>|<missing essential names>"` under `permission_prompt_acknowledged`; covering is a subset test on the same device. That one rule is what makes "first launch", "first launch of an update that needs something new" and "a permission revoked since" each raise it exactly once with no revision constant to remember to bump, and what stops a `.db` restored from another phone from carrying that phone's answer. Only **Not now** and **Continue** acknowledge; system back does not, and the barrier is off. Continue runs the system prompts only — the dialog explains first, so the operating system's one or two asks are never spent without a visible cause — then opens the Permissions page if anything is still missing. `AppPermission` names are persisted inside that value: rename one and its gap is raised once more.
- The acknowledgement and `permission_launch_prompt` live in per-database `user_settings` (project rule: no raw SharedPreferences) and are outside the JSON backup allow-list; the accepted trade-off is that a second database asks once more.
- The first-alert contextual prompt (`CalendarPage._checkAlertPermissions`, latch `alert_notifications_asked`) stays, through `PermissionService.promptFor`, which never opens a settings page. Every alert saved while something essential is missing raises a snackbar with a Review action — unlatched, because that alert will not ring — and `Test alarm` refuses to arm in the same state and says why.
- `NavDestinationKind.permissions` is restorable (Android may kill the process during the round trip to system settings) but **not** in `reopensDrawerOnPop`: the page is reached from the drawer, the launch dialog, a snackbar and calendar settings, so `PermissionsPage.popsToDrawer` is a constructor flag only the drawer row sets.
- **Adding a permission**: a new `AppPermission` value with its importance → the exhaustive switches in `PermissionPresentation` (icon, title, description ARB trio) and the hub's `_bannerFor` → the gateway binding (`status` key plus its settings page in `MainActivity`). **Adding a platform** (the Darwin gateway of event-alerts Session 9): a `PermissionGateway` binding registered in `injection.dart` beside the alert gateway — `UNAuthorizationStatus.notDetermined` maps to `canPrompt`, a `denied` authorization to a `blocked` prompt — and nothing above the gateway changes. Do not list a permission on a platform before a shipped feature there needs it: iOS is empty today because nothing rings on iOS yet.
