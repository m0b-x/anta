## Navigation And Launch Restore (reworked 2026-09-01)
- The app reopens the **whole chain** of pages the user was in when it last went away — folders, notes, the calendar and its sub-pages, and the drawer's settings pages. It replaced a folder-plus-note special case that stored three keys (`last_folder_id` / `last_folder_title` / `last_note_id`) and could only ever restore one folder, so a user three folders deep came back with Back jumping straight to root.
- **The persisted shape is a stack.** `SettingsKeys.lastLocationStack` holds one versioned envelope — `{"v":1,"stack":[{"k":…,"p":{…}}]}` — encoded by `NavDestination.encodeStack` (`lib/models/nav_destination.dart`), bottom-to-top. `NavDestinationKind` **is** the restore allowlist: a page earns a member only if its identity is fully expressible as strings, it is somewhere a user parks rather than passes through, and restoring it cold is harmless. That excludes `ShortcutEditorPage` (an `onSave` closure), `CounterPerNotePage` (a live `Counter`), `MarkdownSettingsPage` (bloc-supplied `allShortcuts` — incidental, one constructor change from admission), `SearchPage` (a query surface, not a place) and `DeveloperOptionsPage`. Enum **names are persisted**: renaming a member truncates every existing install's stack at that entry — and so does *reordering* the members, so new kinds are appended (`allNotes`, `recentNotes` are the two Slice 6 added).
- **Decoding is total and always yields a coherent prefix.** An unknown kind (a newer build's), a missing required param, an unrecognised envelope version or outright garbage each degrade to a truncated or empty stack, never a throw — a corrupt settings row must not keep the app from launching. Bump `stackVersion` only if the *list* semantics change; a new kind alone does not need it.
- **Recording is a `NavigatorObserver`, not scattered calls.** `AppNavigator` stamps each restorable route with a `NavDestination` in `RouteSettings.arguments`; `NavigationHistoryObserver` (`lib/services/navigation_history_service.dart`) sees push/pop/replace/remove symmetrically and feeds `NavigationHistoryService`. It never inspects page types — the whole decision is "is this route stamped?", so modal sheets and dialogs (`PopupRoute`s) are invisible by construction. The old scheme saw only pushes, which is why it needed a `RouteAware.didPopNext` hook on the folder page and still half-worked; that hook is gone.
- **The stack is the longest prefix of stamped routes above the root page**, not every stamped route on the navigator. Taking a prefix is what handles unrestorable pages: they go unstamped, recording suspends while one is on top, and restore lands the user on the deepest ancestor it can honestly rebuild instead of a chain with a hole in it. **A brand-new note's route is one of them**: it has no id until the first save, so `toNoteEditor` stamps nothing and the stack stops at the folder — killed mid-draft, the app reopens the folder, and the draft itself is the auto-save's business, not this stack's.
- **The invariant that replaced the clear-on-return rule**: the persisted stack is exactly the recordable routes currently above `home`. The root folder page (`folderId == null`) *is* `home`, is always present and is never an entry — so popping the last recordable route simply empties the stack. Sitting at root persists the empty envelope (never a deleted row: that is what keeps a healthy install distinguishable from a never-migrated one, and stops the legacy migration re-running).
- **The launch race is the sharp edge.** Mounting the root page publishes an empty stack; if that write reached SQLite before restore read the stored value, the app would erase the location it was about to reopen. So writes stay sealed until `NavigationHistoryService.beginRecording()`, which `AppNavigator.restoreLastLocation` calls in a `finally` (every early return included) and `main.dart` calls on the onboarding path. Its first write is debounced, not immediate, so the replay's pushes are certain to have been observed — which is also how a chain truncated by a deleted folder heals itself without restore writing anything back.
- **Writes are debounced (~400 ms), coalesced and chained**, and flushed from `main.dart`'s `didChangeAppLifecycleState` on `paused`. That flush is load-bearing, not polish: Android kills paused processes and that moment is the entire point of the feature. A queued write carries a **generation** that `_handleDatabaseSwitch` bumps: the continuation resolves `SettingsService` itself, and a switch landing in that window would otherwise write the closing database's ids into the new one — so a write whose generation moved is dropped before the service is asked for. `AppRouteObserver.pageRoutes` sheds routes whose navigator is gone as it is read; a navigator torn down without popping never reports its routes as removed, and they would otherwise accumulate for the life of the process.
- **Replay has two strictly separated phases** (`AppNavigator._replayLastLocation`). Phase 1 resolves the *whole* chain — folders via `FolderStorageService`, notes via `NoteRepository` — truncating at the first target that no longer exists, and re-points a note entry at the folder it lives in **now** so a moved note is followed rather than abandoned — the entries *beneath* it are left as recorded, so Back from a restored moved note goes to the folder the user actually came through, not to the note's new parent. A folder is resolved with `includeDeleted: false` (the default on `FolderStorageService.getFolderById` is true, because undo, move history and sync all hold ids of rows the soft delete kept): a deleted folder is not a place, so the chain truncates at its parent. Phase 2 pushes, instantly (`rootPushInstant`) and **never awaiting a push**: a Navigator push future completes when the route is *popped*, so awaiting the first once deferred every later one until the user pressed Back. Keeping all resolution in phase 1 is what removes the temptation to interleave an `await` between two pushes. Phase 1 is long enough for the user to navigate during it, so the navigator's live page routes are fingerprinted before the first read and again before the first push: a stack that moved **cancels the replay**, leaving the user on the page they asked for rather than under the remembered chain (recording is still unsealed, so what they navigated to is what gets remembered).
- **The drawer case.** There is no settings *page* — settings is `AppDrawer`, and its rows reopen the drawer on `SettingsResult.openDrawer` because the row awaited the push. The awaiter is the row's own context, which is *inside the drawer*, and `DrawerController` unmounts that the moment the drawer closes — so the reopen never used to happen at all. Both the rows and the avatar badge therefore resolve the host through `DrawerHostRegistry.openTopDrawer()`, which is addressed to a page rather than to a context. A restored settings page has no awaiter either, so replay attaches that continuation itself to the **bottom-most** drawer-owned entry (`NavDestinationKind.reopensDrawerOnPop`; Calendar is deliberately false — it sits above the divider as a feature) and resolves the host through `DrawerHostRegistry`, which the folder page and note editor register a `GlobalKey<ScaffoldState>` with. The registry is the designated successor to the result-based pattern if the two ever need unifying — do not add a third. Its walk stops without opening anything in two distinct cases, both no-ops rather than fall-throughs: a host whose `Scaffold` has no drawer right now (selection or search mode) — falling past it would raise a drawer on a page that is not on screen — and one whose drawer is already open. The six drawer-owned settings pages honour `SettingsService.getFolderSwipeEnabled()` on their `drawerEnableOpenDragGesture`, read once at init exactly as the browser reads it.
- **Scope, deliberately.** Restoring `CalendarPage` restores the page, not its *state*: the visible month, filters and open sheets are widget state, not routes, and reviving a month from three days ago would be wrong anyway. `SettingsKeys.restoreLocationMode` (`off` / `notes` / `everything`, default `everything`, on the controls settings page) filters at **replay only** — recording never stops, so turning restore back on takes effect immediately rather than after the next navigation.
- The read-through legacy migration in `SettingsService.getLastLocationStack` synthesises a stack from the three retired keys and deletes them. It is ten lines, idempotent, and protects every existing install — keep it.
- **App bar convention (Slice 1, 2026-09-06; leading control revised 2026-09-07): back and menu are paired.** The root browser (`folderId == null`) shows the drawer button alone, having nowhere to go back to; every page below it — nested folders, All notes / Recent, and the note editor — draws `LeadingNavPair` (`lib/widgets/leading_nav_pair.dart`), the back arrow and the drawer button split by a hairline, at `leadingWidth: LeadingNavPair.width` (87 = 2 + two 42 dp halves + a 1 px `outlineVariant` hairline; the parity pass of 2026-09-07 took it down from 100, which reserved 15 dp the pair never drew). It is the pre-round-2 control promoted out of `unified_app_bars.dart`, where `SettingsAppBar` had gone on drawing it all along, and it went back because users reported the edge swipe as a strain — it shares the left edge with the Android back gesture and loses often enough to matter. Slice 1's "one icon per corner" is therefore **dropped**; what survives is that the search and selection bars still lead with a lone `←`, since there it leaves search or selection rather than the page. Long-press for the ancestor breadcrumb (and its `MergeSemantics` + `CustomSemanticsAction`) lives on the **arrow half only** — the two halves must stay two semantics nodes. Cost: ~44px off the collapsed title, which in the editor is also the rename tap target — measured 2026-09-07 at 132 dp on a 360 dp screen at the old 22 px bold title, which is why every collapsed title is now 17 px / w500 (`AppBarMetrics`) and the pair is 87. `SettingsAppBar` draws the menu half only when `Scaffold.of(ctx).hasDrawer` (four per-note pages sit on drawer-less Scaffolds) and pops with `SettingsResult.openDrawer` only when the page opts in with `popsToDrawer: true`. The drawer keeps its reach three ways, and losing one is a bug: the button, the edge-drag gesture (`Scaffold` builds it from `drawer` / `drawerEnableOpenDragGesture` alone and never reads `AppBar.leading`), and a **Settings row at the bottom of every overflow menu** — the last being the only one that works while the search field owns the bar. The trailing corner is one `⋮` per page: `FolderOverflowMenu` (sort / select / move history ── rename, move, share, import ── delete ── settings; the root menu drops the rows that need a folder, and the move-history badge rides the `⋮` itself so it is still visible unopened) and `NoteOverflowMenu` (the note's folder with "Open folder" ── edit title, move, share ── delete ── settings). `PopupMenuButton.onSelected` runs **after** the menu route is gone, so Settings must open the drawer through the page's own `_scaffoldKey`, never through the item's context.
- **The browser's bar is a sliver, the editor's is a box (Slice 2, 2026-09-06).** `FolderSliverAppBar` is a `SliverAppBar.large` (`expandedHeightFor(isRootPage)`: 116 nested = 48 toolbar + 22 eyebrow line + 32 title line + 14, 102 at root = 48 + 8 + 32 + 14; `toolbarHeight` 48 **and** an explicit `collapsedHeight: topPadding + 48`, because `.large` ignores `toolbarHeight` for its extent and only adds the padding itself when `collapsedHeight` is null; `pinned`) and is the **first sliver of the page's existing `CustomScrollView`** — outside selection mode the `Scaffold` has no `appBar` at all. Selection mode is the exception: it drops the sliver and puts `SelectionAppBar` back in `appBar:`, because a count that scrolls away is worse than a large title that never appears — and **that swap must be paid for in scroll offset**, since the expanded extent moves out of the viewport and a `SelectionAppBar.height` (48) box bar takes its place outside it — the shift is `expandedHeightFor(root) − SelectionAppBar.height`, **68 nested / 54 root**, and it holds at every scroll offset (the collapsed bar's own height never enters: how tall the pinned bar *paints* does not move content). The `_selection.changes` listener jumps the controller by the difference in the **same synchronous tick** as the `setState` (a post-frame callback paints one frame at the wrong offset, which is the jump it exists to remove) and restores the exact inverse on the way out — `swapped > offsetOnEnter ? swapped + shift : offsetBefore`, so entering above the clamp floor and then scrolling gives the floor loss back (the naive `+ shift` was off by `shift − offsetBefore`); clamp at 0 only, never against `maxScrollExtent`, which is not laid out yet. At the root the smart rows and the `FOLDERS` label **stay mounted** through selection (inert: `IgnorePointer` + `ExcludeSemantics` + reduced opacity), because removing them would take ~164 dp of extent the swap does not pay for. Three rules follow from the framework and none of them is optional. **(1) `.large` builds `title` twice** — once in the toolbar row and once inside the `_ScrollUnderFlexibleSpace` it supplies by default (`app_bar.dart`) — so `title` stays a **single-line `Text`** for the collapsed state (never two lines, a `GlobalKey` or a `FocusNode`, which would duplicate or throw), and the expanded eyebrow-plus-headline is drawn by a **custom `flexibleSpace`** that reads `FlexibleSpaceBarSettings` (supplying one is also what stops the double build). It reserves `settings.minExtent` at the top and bottom-aligns the rest inside a `ClipRect` + `OverflowBox`, because a shrinking flex child would overflow instead of sliding under the toolbar. **(2) The default expanded title box is 60 px** (152 − 64 − 28), which an eyebrow above a headline does not fit — hence the explicit heights, with the eyebrow's 22 dp line starting exactly at the toolbar's bottom (no band). **(3) `isScrolledUnder` is `shrinkOffset > maxExtent - minExtent`**, strictly greater, and a list shorter than the screen simply never reaches it: the bar stays expanded and that is correct, not a bug to paper over with `SliverFillRemaining`. `keyboardDismissBehavior: manual` is set on the scroll view for the search field Slice 5 puts in the bar. `RefreshIndicator` keeps working (the pinned sliver does not eat overscroll) but needs `edgeOffset` or its spinner drops behind the expanded bar.
- **The gradient is gone from the main bars (Slice 2 decision).** `UnifiedAppBar.main` — `NoteAppBar` and `SelectionAppBar` — and `SearchAppBar` are flat, 48 dp tall, on `SurfaceRoles.pageGround` (one tone under the editor body, exactly as the browser bar sits under its groups), with transparent surface tint and no scrolled-under elevation; a gradient cannot follow the collapse, and the browser bar has to be the editor bar expanded. `UnifiedAppBar.settings` keeps its gradient until the settings pages are redesigned, so `AppBarStyle` still has two members.
- **The ancestor menu.** Nested browsers fetch `FolderStorageService.getAncestors` once alongside their own folder and keep it in `_ancestors` (null until it answers, so the eyebrow appears once instead of saying "Folders" and correcting itself; re-fetched after a move from the overflow menu). The last ancestor's name — or `l10n.folders` — is the eyebrow above the large title. A **long press on the back button** (`BackButton` drops `onLongPress`, so the leading is a hand-built `IconButton(icon: BackButtonIcon())`) and a **tap on the eyebrow** both open `showFolderAncestorMenu`, a `showMenu(positionBuilder:)` anchored under whichever control was touched, listing the ancestors **nearest first** and ending with the root under a home icon. The eyebrow is not decoration: a long-press-only action is invisible to a screen reader, so it is the visible twin of the same menu, and the back button carries the menu as a `CustomSemanticsAction` — wrapped in `MergeSemantics`, or the annotation settles on whatever node encloses the button and the action is offered for the whole bar.
- **`AppNavigator.popToFolder(context, folderId:, title:)`** is how the editor returns to its folder. `Navigator.popUntil` animates every route it passes (flutter#59990), so a note reached through a chain of wiki links would flicker through each one: the intermediates are removed with `removeRoute` (top-down, never the current route) and a single `pop()` plays the one transition. It finds the target by the `NavDestination` stamp in `RouteSettings.arguments`, walking the page-route list that `AppRouteObserver` (the app's `RouteObserver`, in `app_navigator.dart`) keeps — a `NavigatorState` exposes no history of its own. A folder that is not on the stack at all (launch restore, a wiki chain into another folder) falls back to `pushReplacement`, stamped so recording stays coherent. Deleting a note from the editor pops the same way, which skips the `PopScope` exit save on purpose — `NoteSaveCoordinator.disableSaves()` is called *before* the delete is dispatched, or a debounced auto-save would write into a tombstone and an early create would put a brand-new note back. **`popToAncestor(context, {folderId, title})`** is the ancestor menu's row action and sits on top of it: a non-null id is `popToFolder`, and a null id means the root browser, which is `home` and carries no stamp — it is addressed by `Route.isFirst` and collapsed onto the same way, deliberately **not** by `popUntilFirst`, which pops one route at a time and would play a transition per level.
- **The browser's list is grouped, its counts are one query, and the FAB is gone (Slice 3, 2026-09-06).** Display order is **every folder, then every note** (`groupFoldersThenNotes` in `lib/models/content_item.dart`), each group in its own sort order, with an uppercase section label above each — but **only when both groups are present**, since a folder full of notes does not need to be told they are notes. `mergeByPosition` is no longer what the page renders; the two `position` columns still share one index space and `MixedReorderService` still writes both in one pass, so a drag inside either group persists exactly as before — the cross-kind orderings that space could express are simply no longer drawn, and `regroupFoldersThenNotes` re-sorts a multi-selection drag back so the optimistic render matches what the next load will produce. Rows are `FolderRow` / `NoteRow` (`lib/widgets/`) over the shared `ContentRowShell` (`content_rows.dart`), which rounds only the ends of a group (middle rows are a plain ink host, not a `PhysicalShape` clip) and puts an inset divider under every row but the last (`dividerIndent` comes from the row: 52 under folders, 16 under notes), so a run reads as one card. Row anatomy is the mock's (`RowMetrics`, parity pass 2026-09-07, owner decisions D14–D16): a folder row is 48 dp — `folder_outlined` 22 in `primary`, name 15/400, a **trailing descendant count in `outline` tabular digits (width reserved so a late count changes nothing) and an 18 dp chevron**, no subtitle; a note row is 62 dp — **no leading glyph**, title 15/500, a single `Text.rich` second line of the edit date in w500 `onSurface`, " · ", and the preview in `onSurfaceVariant`. **No row draws a `⋮`**: a long-press opens the row's action sheet (rename / edit title, move, share, delete) led by **Select**, which enters selection with that item. `NoteRow`'s date says Today / Yesterday / a weekday inside six days / `MMMd` / `yMMMd` (`formatRowDate`, ARB `today` + `yesterday`), and the preview is the **marker-stripped** text of the whole note (`MarkdownPlainText.strip`, see the markdown section) when `SettingsService.getShowNotePreview` is on — the setting's first reader; the page re-reads it in `didPopNext`, because the switch lives in a settings page pushed over this one. **There is exactly one `SliverReorderableList` over the whole sequence, headers included** — two would let a drag leave one and never arrive in the other. Headers carry no `ReorderableDragStartListener`, so they cannot be lifted, and `_onReorderEntry` clamps a drop to the bounds of the dragged row's **own** group measured in the post-removal list `onReorderItem` reports against (`onReorder` is deprecated since 3.41; use `onReorderItem`). No `dragBoundaryProvider` was needed: reordering only happens in selection mode, where the pinned sliver bar is not on screen at all, so flutter#164064's autoscroll dead zone under it cannot arise. Counts: `FolderDao.noteCountsWithDescendants(ids)` answers a whole page of folder rows in **one** `WITH RECURSIVE` statement (`tree(root, id)` seeded from the ids, carrying the seed along so every folder reached is attributed back to it, `LEFT JOIN`ed to live notes and grouped by root) — it replaced two queries *per card*; the page reads it for the visible ids and re-reads on the folder/note change streams behind a 120 ms debounce, and clears it **without** `setState` when there are no folders, because that path runs from the list's own builder. The floating action button, its create sheet and the `_isSortSheetOpen` FAB-lift are all deleted: `bottomNavigationBar` outside selection mode puts **both** create buttons at the left — New folder then New note (nested) or Import (root) — behind a 4 dp `bottomBarInset`, with the count still centred on the **bar's** own centre line rather than in the gap left over: it is a `Stack` of a start-aligned `Row` and a `Positioned.fill` `IgnorePointer` whose symmetric `bottomBarInset + 2 × bottomBarButtonSize` padding keeps the label off the buttons (it ellipsizes at one line instead of ever running under them). 60 dp on `rowGroup` under a 1 px `rowDivider` line, 28 dp outline glyphs in `primary` inside 54 dp targets, a 13 px count, padded by `max(viewInsets.bottom, viewPadding.bottom)`; the left cluster and the step up in size are a **deliberate deviation from the mock's rev 2.4** (owner decision 2026-09-07, roadmap D20; the mock's rev 2.5 draws it too): the two create actions are the bar's whole job, and one-handed reach beats symmetry. `SelectionActionBar` is the same 60 dp strip so the swap into selection moves nothing. The count is read off the paginated states' `totalCount` in its own `BlocBuilder`s (the bar is built before the list's and would otherwise trail it by a frame) and rendered as `folderCountLabel` / `noteCountLabel` joined by `folderAndNoteCount` — two plural keys and a joiner rather than one nested-plural message, so each half stays a translatable sentence with Romanian's `few` form intact.

- **One colour label per note and per folder (Phase 1, 2026-09-12).** `ItemLabel` (`lib/models/item_label.dart`) is a fixed eight-member enum — `none` plus red, orange, yellow, green, teal, blue, pink — whose **declaration order is the storage encoding**: `label INTEGER NOT NULL DEFAULT 0` on **both** `notes` and `folders` (schema **v39**, `_migrateV38ToV39`, two guarded `ALTER TABLE … ADD COLUMN`s, no index and no backfill because 0 is what every pre-v39 row meant). Never reorder the enum; append only. The hex values live once in `AppColors.labelColor(label, brightness)` / `AppColors.labelRing(brightness)` (a light and a dark value per hue, plus a 1 px inset ring at 10 % of the opposite tone so yellow reads on `rowGroup`); `AppColors.folderIcon` stays `primary` — **a label never tints the folder glyph**. `LabelDot` (`lib/widgets/label_dot.dart`, `RowMetrics.labelDotSize` = 10) draws at the **trailing** edge: on a note row after the title column and *before* the reorder drag handle, on a folder row before `RowCountChevron` or before the handle, and on `SearchResultRow` so a result and the browser row it stands for agree. `ItemLabel.none` renders `SizedBox.shrink()` and reserves nothing, so an unlabelled row lays out exactly as it did before labels existed. Assignment is `LabelSwatchStrip` (`lib/widgets/label_swatch_strip.dart`) — a clear swatch with a diagonal slash then the seven hues, 22 dp dots in 32 dp circles inside 48 dp-tall cells that divide the strip's width equally (eight fixed 48 dp targets would overflow a 360 dp phone), the current value ringed in `primary` — shown as `showRowActionSheet`'s new optional `headerBuilder` (it takes the **sheet's** context, because picking a swatch pops the sheet) and, everywhere else, through the one `showLabelPickerSheet(context, value:)` in the same file (handle, "Label" title, the strip; padded `max(viewInsets, viewPadding)`; resolves to the pick or `null` on dismiss, and a caller writes only on a non-null, changed answer): the browser's `SelectionActionBar` first action `onLabel` → `_labelSelected` opens it ringed on the selection's common colour, and the editor's `⋮` menu (Slice C, 2026-09-13) carries a **Label** row between Move and Share — `NoteOverflowMenu.onLabel`, nullable and omitted while the note has no id, which is why the editor's `OptimizedNoteCreated` listener branch ends in a `setState` — whose `_labelNote` reads the current colour fresh through `NoteStorageService.getNoteMetadata` (never `widget.metadata`, the value at push time; a tombstone reads as `null` there and lands on the `noteNotFound` snackbar, as Move and Share do), without flushing saves first, and dispatches `SetOptimizedNoteLabel` once on a changed pick. Writes go Widget → bloc → service → repository → DAO like every other row action: `SetOptimizedNoteLabel` / `SetOptimizedNotesLabel` and `SetOptimizedFolderLabel` / `SetOptimizedFoldersLabel` (separate from the `Update…` events, which carry the duplicate-name check and the search re-index a colour cannot affect) → `setNoteLabel` / `setLabelForNotes`, `setFolderLabel` / `setLabelForFolders` → `updateNoteLabel` / `updateFolderLabel` (fresh HLC, `version + 1`, tombstones refused) and `updateLabelForNotes` / `updateLabelForFolders` (**one** `UPDATE … WHERE id IN (…) AND is_deleted = 0`, `version = version + 1` in SQL — pinned by `item_label_dao_test.dart`), then a `RefreshNotes`/`RefreshFolders` so the row repaints immediately. `mergeNote` and `mergeFolder` carry `label` in **both** branches. Backup and archives take it as an **additive** key — `JsonKeys.label` holding the enum *name* — so neither the backup `version` nor `ImportExportService.archiveVersion` moves and a missing or unknown name reads as `none`. **Labelling is not an edit**: a label write moves the HLC and version but leaves `updated_at` alone (the one write in either DAO that does), writing the label a row already has is a no-op, and the bulk statement counts only the rows whose colour moved; the repositories raise `NoteChangeType.labelled` / `FolderChangeType.labelled`, which `FolderSearchService` (no re-index) and `FolderNameIndex` (no rebuild) ignore while the blocs still refresh the folder. **Not a pin and not a tag**, but since 2026-09-13 labels do sort and filter: **`NotesSortOrder.labelAsc` / `FoldersSortOrder.labelAsc`** (both enums are **append-only** — the member `name` is what `folders.noteSortOrder` / `subfolderSortOrder` persist, and an older build parses an unknown name as the default) map to `NoteSortField.label` / `FolderSortField.label`, ordering `CASE WHEN label = 0 THEN 1 ELSE 0 END, label, updated_at DESC, id` (folders: `name` in place of `updated_at DESC`) — labelled first in palette order, unlabelled last, **always ending on `id`**; there is no `labelDesc`, `ascending` is not consulted for the field, and there is **no index**: the plan (`SEARCH … idx_notes_position` + temp b-tree) is exactly the `title`/`updated_at` sorts' plan, and `query_plan_test.dart` pins that the two stay alike. Both sort sheets scroll (seven note rows overflow the modal cap on a 360×800 phone). **Search filters by label through dot chips** (see the search bullet below). **How a label is drawn is one preference** (`SettingsKeys.labelStyle` = `label_style`, a `LabelStyle` name, default `dot`, carried in `BackupService._exportSettings`'s allow-list with no version bump): `dot` is the trailing dot above, `stripe` is a 3 dp bar on the row's **leading** edge (`RowMetrics.labelStripeWidth/Inset/Radius` = 3 / 8 / 3) — flush left so the group's own 14 dp clip rounds it on an end row, rounded 3 dp on its right only, drawn by `ContentRowShell.edgeStripe`/`edgeStripeSemantics`, which wraps **only the row's child** (never the divider) in a `Stack` and builds no `Stack` at all when null. Rows never read settings per build: `LabelAppearanceService` (the `DatabaseLifecycle` reset contract, modelled on `CalendarPaletteService`) publishes into `LabelAppearance.style`, a `ValueNotifier<LabelStyle>` primed in `main()` right after `configureDependencies()` and re-primed from `OptimizedFolderContentPage._loadSettings`, from `AllNotesPage._loadSettings` and by `BackupService.importFromJson` after a restore after a database switch; `NoteRow`, `FolderRow` and `SearchResultRow` subscribe through a `ValueListenableBuilder` **only when the row is labelled**, and resolve colour/semantics/dot through the one `LabelRowDecoration` helper in `label_dot.dart`. The settings row (Browsing section) writes through the service, not `SettingsService`, so the browser under the page repaints live. Named labels (roadmap Slice D) were dropped by the owner on 2026-09-13; the feature is complete, and `docs/colour-labels-roadmap.md` holds the per-slice "Shipped" blocks.
- **Search filters by colour label (Slice A, 2026-09-13).** `SearchState.labels` (`Set<ItemLabel>`, OR, empty = no filter) and `labelsInUse` (palette order, the colours at least one live note in the scope carries — `NoteDao.labelsInUse` is one `SELECT DISTINCT` with the folder subtree inlined as `IN (…)`, empty set → no statement); event `SearchLabelsChanged(Set)` carries the whole set, never a delta. `SearchScopeChips` is **one fixed-height horizontal scroller** (`preferredHeight` = 48 + `AppSpacing.md`, the row pinned at 48 so the sliver bar's `bottom` is honest at any chip count) — the scope pair, a 1 px `rowDivider` separator, then a dot `FilterChip` per colour in use (12 dp `LabelDot`, semantics = the colour name alone, `showCheckmark: false`, a selected chip wears the swatch strip's 2 dp `primary` ring because the dot on `secondaryContainer` falls below 3:1 for yellow/orange/green); `folderScope` is nullable and **`SearchScopeChips.shows(folderScope:, labelsInUse:)` is the one root rule** for both hosts: the root shows dots alone iff a colour is in use, and `SearchLabelsPrimed` (dispatched by `InPlaceSearchController`'s constructor, never by `SearchPage`) reads `labelsInUse` at page mount so the row is there on the first frame search opens rather than growing the bar under a visible field. Semantics: a label set **filters whatever pass is showing** (`SearchFilter.labels` on the indexed pass, `quickSearch(labels:)` on the quick one — both before the `limit` cut) and **makes the empty query meaningful**: with colours picked and nothing typed the bloc runs `_runLabelled` → `FolderSearchService.labelledNotes` → `NoteDao.labelledNotes` (`WHERE is_deleted = 0 AND label IN (…) [AND folder_id IN (…)] ORDER BY updated_at DESC, id LIMIT 50`, walking `idx_notes_updated` unscoped) plus `countLabelledNotes` → `SearchState.labelledTotal`, rows land in `titleHits` with no matches, and the header reads `labelledNotesHeader` (names joined ", ", then " · N notes" with the true count; ro has `few`). **`quickSearch('')` still returns `[]` unconditionally** — the listing never goes through the 300-row in-memory page. Two ordering rules: `SearchLabelsChanged` is handled at once and **does not** null `_pendingQuery` (the scope-change rule) — `_onLabelsChanged` runs `_pendingQuery ?? state.query` and then nulls it, so a chip tapped inside the 200 ms debounce filters the text on screen in one pass; and `labelsInUse` is applied only while `state.scope` still equals the scope it was read for (an idle scope change deliberately does not bump `_generation`). `SearchOpened({keepLabels})`: `open()` clears the colours with the query, while `refresh()` / `SearchPage.didPopNext` pass `keepLabels: true` so a colour set in the editor a moment ago is both offered and still applied on the way back; `SearchCleared` (field emptied) keeps them — that is how "everything red" is asked. **The selection follows the offer**: wherever `labelsInUse` is applied, `_dropColoursNoLongerOffered` intersects the selected set with it and sends the pruned set through `SearchLabelsChanged` — a colour whose last note was relabelled elsewhere, or which nothing in a newly picked folder scope wears, must not stay selected under a row that no longer shows its chip (found on the emulator: "no results" with nothing to clear). The row's `SizedBox` takes `double.infinity` width because a Material 3 `AppBar` centres a `bottom` narrower than itself, which floated the root's few dot chips to the middle. `labelsInUse` reloads on open, clear, submit, scope change and the way-back refresh, **never on a fresh keystroke**; the independent reads of a pass run under `Future.wait`. Label-only rows show path · date (`showDate: state.isLabelOnly`), like the recents they replace.
- **The folder bloc reloads in place, and both blocs coalesce refreshes (2026-09-13).** `OptimizedFolderBloc._onRefreshFolders` re-reads `pageSize × loadedPages` in one statement through `_loadLoadedPages` (the note bloc's shape) and emits `Loaded` directly — **no `Loading` state, no snap to page 1** — unless the refresh targets a parent other than the one on screen, which still takes the full load. That is what stopped bulk label/move/delete flashing the browser's spinner and losing the offset (leaving selection drops `_localMixed`, and a `Loading` frame then had nothing to draw). `_onLoadMoreFolders` / `_onLoadMoreNotes` read at the list's own page size, advance the counter only after a successful read, and **bail if a refresh moved the state under them** (bloc 9 runs handlers concurrently). Every `add(RefreshFolders)` / `add(RefreshNotes)` — the handlers' own and `_onExternalChange`'s — goes through `_scheduleRefresh(id)`, which collects ids and flushes one event per distinct parent on a `Timer(Duration.zero)` (a microtask flushes between broadcast-stream events and coalesces nothing); a bulk write over N rows is one reload. On the browser page, bulk move, drop-on-folder, pull-to-refresh, the post-import reload and the return from a created note call `_refreshData()` (the two refresh events); `_loadData()` is for a first load or a sort change.

- **Search is hosted in the browser in place, and it is screen state (Slice 5, 2026-09-06).** The browser's search icon no longer pushes a route: it sets `_searching`, opens the page's own `SearchBloc` on `FolderScope(folderId, name)` (root: `everywhere`, and the scope chips are hidden there because there is no second scope to offer — since Slice A the row still appears at the root with colour chips alone when a label is in use), and **swaps the whole first sliver** for a plain `SliverAppBar(pinned: true)` whose `title` is the `TextField`, whose `bottom` is `SearchScopeChips` at its `preferredHeight`, and whose body slivers are `SearchSurface.resultSlivers` — the same static both hosts render, so the standalone route and the in-place surface cannot drift. The field goes in the plain bar and never in `FolderSliverAppBar`: `.large` builds `title` twice, so a `TextField` there would be duplicated and two of them would fight over one `FocusNode`. **One `CustomScrollView` across both modes** (only its `slivers` change) — a second one would be a different element and the scroll position, the whole point of the exercise, would go with it; for the same reason `RefreshIndicator` stays in the tree while searching and is disabled through `notificationPredicate` rather than being lifted out. The **bar swap is paid for the way selection's is**, by the same `_compensateBarSwap` generalized over a `_BarMode`: entering saves the folder offset and jumps to 0 (results open at their own top), leaving jumps back to the saved offset, both in the same synchronous tick as the `setState`. `keyboardDismissBehavior: manual` is what keeps the keyboard up while results scroll. Search and selection are **mutually exclusive by construction**: the overflow menu is the only door into selection and it is off screen while searching, and entering selection calls `_leaveSearch()` first, which pays for search → normal **explicitly** (`_compensateBarSwap(_BarMode.normal)`) so the folder list gets its offset back before the selection swap measures from it — by then selection is already active and `_barMode` would report it, which is why the target is passed rather than derived; `_openSearch` does the mirror image for a live selection. The bottom bar and the drawer are both off while searching. `didPopNext` deliberately does **not** reset any of it — the page was never unmounted, so query, scope and scroll are simply still there; it re-reads the settings as before and re-runs whichever pass is on screen so an edited note comes back with a fresh snippet. `didPushNext` unfocuses the field while searching: a route regaining focus hands it back to the child that had it, and a field regaining focus reopens the keyboard, which would cover the very results the user came back to. **Nothing on the page may drop focus from `didChangeDependencies`**: on Android the keyboard opening changes `MediaQuery.padding` (the navigation-bar inset vanishes under it), the page depends on that aspect through the refresh spinner's `edgeOffset`, so the hook fires the moment the keyboard is up — a legacy `primaryFocus?.unfocus()` there closed the search keyboard as soon as it opened (found on the emulator 2026-09-07; guarded by the browser test "the keyboard opening does not take the focus it was opened for", which fakes the keyboard through `tester.view.viewInsets`/`padding`).
- **The root has two smart rows, and they open one page in two modes (Slice 6, 2026-09-07).** Above the `FOLDERS` label — which the root now always draws, since the label is what separates the smart rows from the folders rather than folders from notes — sit **All notes** (with the global live count as a bare trailing number) and **Recent**, both 48 dp with a chevron and 22 dp outline glyphs, and both kept mounted but inert while selecting. Both push `AllNotesPage` (`lib/pages/all_notes_page.dart`), one page with an `AllNotesMode`: `all` is every note paginated, `recent` is the same list capped at `AppConstants.recentNotesLimit` (50 — the same cap the search surface's idle recents use) and never loading more. Every reload re-reads `pageSize × loadedPages`, so Back from a note never shrinks a paginated list to one page; `getNotesPaginated` orders with the id as a final tiebreaker so a page boundary never re-serves a row. It is a `NoteRow` list off the shared `OptimizedNoteBloc` with `LoadNotesPaginated(folderId: null)` — no folders, no reorder, no create bar — and each row carries the **folder path it lives under** as an eyebrow above its second line (`NoteRow.pathLabel`, batched and deduplicated through `FolderStorageService.folderPathSegments`, the same call the search surface uses). An **empty** `pathLabel` is not the same as a null one: it reserves the lane while the ancestor walk runs, so a late answer fills it in rather than resizing the row — the same reason `FolderRow` reserves its trailing count width, and the same reason the All-notes count rides the **trailing** slot, where a late arrival changes a width and not a height. `NoteRow.folderId` is each row's **own** folder, so move, the rename-uniqueness check and the push all address the right place. Three things about the shared bloc are load-bearing: `NoteBlocFilters.forFolder(null)` does match a null-folder state, but `NoteStateHelper.getNotesForFolder`/`hasMoreForFolder` answer **null/false** for a null folder id (they read it as "no context", not "everything") so the page reads `paginatedNotes` itself; and `_onExternalChange` compares against `_currentFolderId`, which a null id never matches, so the page reloads off `NoteStorageService.changes` on a 120 ms debounce of its own — which is also what keeps the recent mode's page size instead of the bloc's default. No new SQL: `NoteDao.getNoteCount(null)` is the global count and `NoteStorageService.getNoteCount` simply took a nullable id; `NoteRepository._invalidateFolderCache` now always drops the `null` key with the folder's, because any write in any folder changes the total.
- **Two additive `NavDestinationKind` members, `allNotes` and `recentNotes` (Slice 6).** They carry no params, are `isNoteSubstrate` (so a note opened from either is still restored under the "folders and notes" mode, which takes a *prefix*), and are `reopensDrawerOnPop` false. **No `stackVersion` bump**: an unknown kind already truncates by design, so an older build reading a newer build's stack degrades on its own — the bump is only for a change in the *list's* semantics. Reverting the slice therefore truncates a parked user's stack at that entry and no worse. `AllNotesPage` registers with `DrawerHostRegistry` and hosts the drawer like every other full-page screen, and its `⋮` carries the one row the convention requires — Settings, opened through the page's own `_scaffoldKey`.
- **In-place search is shared, not copied (Slice 6).** `InPlaceSearchController` (`lib/controllers/`) owns the half that is identical on every host — the `SearchBloc`, the field's controller and focus node, the `isSearching` flag and the open/leave/type/refresh events — and `SearchFieldAppBar` (`lib/widgets/`) is the plain `SliverAppBar` both hosts swap in. What is deliberately **not** shared is the scroll compensation: the browser pays for a three-way swap it shares with selection mode, the note lists for a two-way one. The controller is a plain class and not a `ChangeNotifier` on purpose — every transition is already inside a host's `setState` for its own bar swap, and a second notification would rebuild the page twice per tap. `open()` still dispatches `SearchOpened` before flipping the flag, because both hosts guard their `BlocBuilder` with `buildWhen: (_, __) => isSearching` and that is only safe while the bloc's open handler emits before its first await.
- **Three meanings of Back, one `PopScope`.** A route calls **every** registered `PopEntry`'s callback, so nesting a `PopScope` per mode would run two handlers for one gesture; and swapping between sibling `PopScope`s changes the tree shape above the `Scaffold`, which rebuilds it and drops the scroll position. The browser therefore has exactly one, whose `canPop` is false while any of the three apply and whose handler runs them in priority order: **selection** (clear it), then **search** (leave it), then the nested-folder case (`AppNavigator.pop`, which exists so the iOS swipe-back gesture does not steal the drawer's edge drag). Back at the root while searching leaves search; a second back is the app's.
