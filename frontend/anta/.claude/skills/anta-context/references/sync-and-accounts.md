## Sync And Accounts (Phase 01 — identity and pairing)
- Cloud sync is being added in phases on top of the CRDT columns already present on folders/notes/chunks. **Phases 00 (identity) and 01 (pairing) are shipped.** A user can sign in with Google and link one other account into a pair; no note, folder or event data crosses the wire yet, there is no schema change, and no `sync_metadata` / `HybridLogicalClock.receive()` usage.
- **Local SQLite stays the source of truth.** Firestore is a transport, never the primary store. Any later phase that inverts this is wrong.
- **One platform gate**: `SyncAvailability.isSupported` (`lib/services/sync_availability.dart`) is `!kIsWeb && (Platform.isAndroid || Platform.isIOS)`. `kIsWeb` is checked first because `dart:io`'s `Platform` throws on web. Every sync entry point routes through it — never test the platform directly. Windows/Linux/macOS stay local-only because `google_sign_in` ships no implementation there, regardless of what the Firebase plugins now claim to support.
- `main.dart` calls `Firebase.initializeApp` only when the gate passes, wrapped in try/catch: a checkout without `google-services.json` must still launch, just without sync.
- **`AuthService` is an interface** (`lib/services/auth_service.dart`) with two bindings chosen in `injection.dart`: `FirebaseAuthService` when the gate passes **and** `Firebase.apps` is non-empty, `NoOpAuthService` otherwise (unsupported platform *or* failed Firebase init). Blocs/UI consult `AuthService.isAvailable` — the bound service, never the platform gate — so a degraded binding reads as "unavailable" instead of a sign-in button that can only fail. This keeps `firebase_auth` types out of the bloc/UI layers and off the desktop path. `AppUser` (`lib/models/app_user.dart`) is the layer boundary — never surface Firebase's `User`. `SyncBloc` is covered by `test/bloc/sync_bloc_test.dart` against a fake `AuthService`.
- **`AuthService` is deliberately NOT on the `DatabaseLifecycle` reset contract.** That contract exists for singletons caching a `late AppDatabase`; the Firebase identity is *global*, so tearing it down on a database switch would drop the auth stream for nothing. Pairing state *is* per-database — it lands in `user_settings` via `SettingsService`/`SettingsKeys`, and `PairingService` is on the reset contract so its cache and its snapshot listeners follow the active database.
- **Pairing (Phase 01)**: `PairingGateway` (`lib/services/pairing_gateway.dart`) hides `cloud_firestore` exactly as `AuthService` hides `firebase_auth` — only `PairRecord`/`InviteRecord`/`PairProfile` cross the boundary, and `FirestorePairingGateway` maps every `FirebaseException` onto a `PairingError`. `PairingService` owns the workflow; `PairingBloc` (`lib/bloc/pairing/`) is separate from `SyncBloc` because pairing is orthogonal to auth. `firestore.rules` is committed at the package root.
- **The locally stored `pairId` is a cache, not the truth.** The server answers "which active pair contains my uid" (`findActivePairs`), reconciled on load and on every auth change. Without that inversion, a second device, a second local database, or two people redeeming each other's codes fork into two pairs that never converge. When a uid *is* in two active pairs, **the earliest `createdAt` wins and the rest are tombstoned** — both devices compute that independently, so it converges with no conflict UI. Rules cannot enforce one-active-pair-per-uid (it needs a query); this is a client invariant that only holds because reconciliation runs.
- **Unpairing tombstones the pair, never deletes it** (`status: 'ended'`, `endedBy`, `endedAt`; `members` never shrinks). Both sides keep read access, so the passive partner can still learn who ended it, and the doc survives to anchor the Phase 02+ subcollections — Firestore has no recursive delete without Cloud Functions, which Spark does not include. Re-pairing always mints a fresh `pairId`.
- **Pairing is online-only on purpose.** Firestore's offline queue would accept every write and resolve nothing, so writes go through `runTransaction`, authoritative reads use `Source.server`, and every gateway call is bounded by a timeout that surfaces as `PairingError.offline` rather than a spinner that never ends. A failed reconcile never clears the cache — opening the Sharing page offline must not read as "not paired".
- **The pairing settings keys are deliberately absent from `BackupService._exportSettings`**: restoring a backup onto a third device must not clone a pair membership. `pairing_pending_code` is persisted so an app restart between generating and redeeming cannot strand the creator.
- Invite codes are 8 characters over `23456789ABCDEFGHJKMNPQRSTVWXYZ` — no `0/O/1/I/L/U`, because the code gets read aloud. Invites are create-only with a 10-minute lifetime bounded in the rules against `request.time` (a skewed device clock must not mint a year-long invite), and `list` on the collection is denied so codes cannot be enumerated.
- **A pair carries the `inviteCode` it was born from, and the rules `get()` that invite to authorise the create.** Membership alone is not proof of consent: uid is not secret (the Sharing page prints it), so without this clause anyone could force a pair on anyone, and a planted pair with an earlier `createdAt` would win reconciliation and evict the victim's real one. The invite exists before the pair, so a rules `get()` can see it — the same-batch limitation only blocks the reverse direction. `permissions` is seeded closed at create and each member may only ever rewrite its own entry.
- **Firestore rules treat a missing document as `resource == null`**, so `resource.data.x` errors and denies. The `invites` `get` rule allows `resource == null` explicitly and `redeem` re-raises `permissionDenied` as `codeInvalid`; without both, a one-character typo — the most common failure in the flow — tells the user "permission denied".
- `firestore.rules` **and** `firestore.indexes.json` are committed and deploy together. The composite index (`members` array-contains + `status`) is not optional: without it every reconcile fails `failed-precondition`, silently in release builds.
- Errors carry the `PairingAction` that produced them. The code field only renders redemption failures — a failed "create a code" must not put a red border on a field the user never touched.
- Google Sign-In 7.x is a breaking rewrite from 6.x: `initialize()` must complete once before any other call, `authenticate()` **throws** `GoogleSignInException(code: canceled)` on user dismissal rather than returning null (mapped to `null`, not an error), and `authentication` carries only `idToken`. No `serverClientId` is passed in Dart — Android resolves it from `google-services.json`'s `client_type: 3` entry via the Gradle plugin, iOS from `Info.plist`.
- Firebase config files (`google-services.json`, `GoogleService-Info.plist`, `lib/firebase_options.dart`, `firebase.json`) are **gitignored**; regenerate with `flutterfire configure --platforms=android,ios`. The generated options intentionally cover android+ios only, so a stray desktop call throws `UnsupportedError` loudly instead of half-working.
