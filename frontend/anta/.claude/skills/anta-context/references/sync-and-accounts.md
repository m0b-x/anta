## Sync And Accounts (Phase 01 — identity and pairing)
- Cloud sync is being added in phases on top of the CRDT columns already present on folders/notes/chunks. **Phases 00 (identity) and 01 (pairing) are shipped.** A user can sign in with Google and link one other account into a pair; no note, folder or event data crosses the wire yet, there is no schema change, and no `sync_metadata` / `HybridLogicalClock.receive()` usage.
- **Local SQLite stays the source of truth.** Firestore is a transport, never the primary store. Any later phase that inverts this is wrong.
- **One platform gate**: `SyncAvailability.isSupported` (`lib/services/sync_availability.dart`) is `!kIsWeb && (Platform.isAndroid || Platform.isIOS)`. `kIsWeb` is checked first because `dart:io`'s `Platform` throws on web. Every sync entry point routes through it — never test the platform directly. Windows/Linux/macOS stay local-only because `google_sign_in` ships no implementation there, regardless of what the Firebase plugins now claim to support.
- `main.dart` calls `Firebase.initializeApp` only when the gate passes, wrapped in try/catch: a checkout without `google-services.json` must still launch, just without sync.
- **`AuthService` is an interface** (`lib/services/auth_service.dart`) with two bindings chosen in `injection.dart`: `FirebaseAuthService` when the gate passes **and** `Firebase.apps` is non-empty, `NoOpAuthService` otherwise (unsupported platform *or* failed Firebase init). Blocs/UI consult `AuthService.isAvailable` — the bound service, never the platform gate — so a degraded binding reads as "unavailable" instead of a sign-in button that can only fail. This keeps `firebase_auth` types out of the bloc/UI layers and off the desktop path. `AppUser` (`lib/models/app_user.dart`) is the layer boundary — never surface Firebase's `User`. `SyncBloc` is covered by `test/bloc/sync_bloc_test.dart` against a fake `AuthService`.
- **`AuthService` is deliberately NOT on the `DatabaseLifecycle` reset contract.** That contract exists for singletons caching a `late AppDatabase`; the Firebase identity is *global*, so tearing it down on a database switch would drop the auth stream for nothing. Pairing state *is* per-database — it lands in `user_settings` via `SettingsService`/`SettingsKeys`, and `PairingService` is on the reset contract so its cache and its snapshot listeners follow the active database.
- **Pairing (Phase 01)**: `PairingGateway` (`lib/services/pairing_gateway.dart`) hides `cloud_firestore` exactly as `AuthService` hides `firebase_auth` — only `PairRecord`/`InviteRecord`/`PairProfile` cross the boundary, and `FirestorePairingGateway` maps every `FirebaseException` onto a `PairingError`. `PairingService` owns the workflow; `PairingBloc` (`lib/bloc/pairing/`) is separate from `SyncBloc` because pairing is orthogonal to auth. `firestore.rules` is committed at the package root.
- **The locally stored `pairId` is a cache, not the truth.** The server answers "which active pair contains my uid" (`findActivePairs`), reconciled on load and on every auth change. Without that inversion, a second device, a second local database, or two people redeeming each other's codes fork into two pairs that never converge. When a uid *is* in two active pairs, **the earliest `createdAt` wins and the rest are tombstoned** — both devices compute that independently, so it converges with no conflict UI. Rules cannot enforce one-active-pair-per-uid (it needs a query); this is a client invariant that only holds because reconciliation runs.
- **Unpairing tombstones the pair, never deletes it** (`status: 'ended'`, `endedBy`, `endedAt`; `members` never shrinks). Both sides keep read access, so the passive partner can still learn who ended it, and the doc survives to anchor the Phase 02+ subcollections — Firestore has no recursive delete without Cloud Functions, which Spark does not include. Re-pairing always mints a fresh `pairId`.
- **Pairing is online-only on purpose.** Firestore's offline queue would accept every write and resolve nothing, so writes go through `runTransaction`, authoritative reads use `Source.server`, and every gateway call is bounded by a timeout that surfaces as `PairingError.offline` rather than a spinner that never ends. A failed reconcile never clears the cache — opening the Sharing page offline must not read as "not paired".
- **The pairing settings keys are deliberately absent from `BackupService._exportSettings`**: restoring a backup onto a third device must not clone a pair membership. `pairing_pending_code` is persisted so an app restart between generating and redeeming cannot strand the creator.
- Invite codes are 8 characters over `23456789ABCDEFGHJKMNPQRSTVWXYZ` — no `0/O/1/I/L/U`, because the code gets read aloud. Invites are create-only with a 10-minute lifetime bounded in the rules against `request.time` (a skewed device clock must not mint a year-long invite), and `list` on the collection is denied so codes cannot be enumerated.
- **A pair carries the `inviteCode` it was born from, and the rules `get()` that invite to authorise the create.** Membership alone is not proof of consent: uid is not secret (the Sharing page prints it), so without this clause anyone could force a pair on anyone, and a planted pair with an earlier `createdAt` would win reconciliation and evict the victim's real one. The invite exists before the pair, so a rules `get()` can see it. **The pair and the claim of its invite are one write (2026-11-12, sharing record §4):** `PairingGateway.createPair` is a transaction that reads the invite (gone or claimed first → `codeInvalid`), creates the pair `<invite code>_<nonce>` (`pairIdFor`) and stamps `pairId` / `redeemedBy` on the invite; the rules hold each to the other with `getAfter` (`claimsInvite` on the pair's create, `claimsOwnPair` on the invite's update), so a code names one pair, once — shared documents name a pair by its id, and an id that could be created again would re-open what an ended pair closed. There is no separate `claimInvite` any more, and a lost race leaves no pair to end. `findActivePairs` throws for an active pair it cannot parse instead of leaving it out: "no pair" ends every share on the device. `permissions` is seeded closed at create and each member may only ever rewrite its own entry.
- **Firestore rules treat a missing document as `resource == null`**, so `resource.data.x` errors and denies. The `invites` `get` rule allows `resource == null` explicitly and `redeem` re-raises `permissionDenied` as `codeInvalid`; without both, a one-character typo — the most common failure in the flow — tells the user "permission denied".
- `firestore.rules` **and** `firestore.indexes.json` are committed and deploy together. The composite index (`members` array-contains + `status`) is not optional: without it every reconcile fails `failed-precondition`, silently in release builds.
- Errors carry the `PairingAction` that produced them. The code field only renders redemption failures — a failed "create a code" must not put a red border on a field the user never touched.
- Google Sign-In 7.x is a breaking rewrite from 6.x: `initialize()` must complete once before any other call, `authenticate()` **throws** `GoogleSignInException(code: canceled)` on user dismissal rather than returning null (mapped to `null`, not an error), and `authentication` carries only `idToken`. No `serverClientId` is passed in Dart — Android resolves it from `google-services.json`'s `client_type: 3` entry via the Gradle plugin, iOS from `Info.plist`.
- Firebase config files (`google-services.json`, `GoogleService-Info.plist`, `lib/firebase_options.dart`, `firebase.json`) are **gitignored**; regenerate with `flutterfire configure --platforms=android,ios`. The generated options intentionally cover android+ios only, so a stray desktop call throws `UnsupportedError` loudly instead of half-working.

## Readiness phase (local prep before transport) — record `docs/cloud-sync-readiness-roadmap.md`
- **The line:** nothing in this phase talks to Firestore. Local SQLite stays the source of truth; the phase makes every synced table CRDT-shaped and gives the future engine a change feed, so Phase 02 can be built against a fake gateway first. Every decision D1–D19 is taken (record §2, all A; D15 amended on 2026-10-23: the bind floor is the clock at unbind, not the row maximum).
- **v43 (R2, 2026-10-23):** `calendar_categories`, `counters`, `counter_values` gained the five CRDT columns (`hlc_timestamp`/`device_id` declared `withDefault('')` and backfilled in the step, the v27 idiom); `owner_id TEXT NULL` on all eighteen synced tables (NULL = "mine, not yet signed in"; the first sign-in backfills it in Phase 02); the `sync_outbox(table_name, row_key, hlc, op, enqueued_at)` table keyed `(table_name, row_key)` — created in v43, written only from R3's helper; partial indexes `WHERE is_deleted = 0` on the three tables; a repair dividing `deleted_at`/`updated_at` values above 10^12 by 1000 on folders and notes (the folder cascade had bound milliseconds where Drift stores seconds; the binding is fixed in the same step). Backup format stays 7: exports live rows only, imports wipe-then-insert with fresh HLCs.
- **Counter and category semantics after v43:** deletes are tombstones (`CounterDao.deleteCounter` tombstones the counter and its values under one HLC; `CalendarCategoryDao.softDeleteById` tombstones and **refuses built-in ids** — built-ins are only ever hidden); `upsertValue` is read-then-write, a no-op when the value is unchanged, resurrects a tombstoned value and drops the write when the parent counter is tombstoned; `seedMissing` resurrects a tombstoned built-in; import normalises `isBuiltIn` from the seed list regardless of the archive flag; every read path filters `is_deleted = 0`; no-op edits and reorders of unmoved rows do not bump versions. Nothing above the DAO sees a tombstone.
- **rowKey convention (record §3):** text ids as they are; composite keys joined with `|`, days as epoch-ms (`eventId|dayEpochMs`, `counterId|noteId` with `noteId == ''` for the global value). The rowKey is also the future remote document id. `lib/database/crdt/synced_tables.dart` is the registry: the eighteen tables with the SQL that reproduces each key (`event_id || '|' || (day * 1000)` — drift stores `day` as unix seconds), `travelsWithParent` for `content_chunks` (never queued, a note is one document under D14), and `ownedRowsWhere(ownerUid)` = `owner_id IS NULL OR owner_id = ?` (D17's "mine").
- **The clock is persisted (R5, 2026-10-23):** `sync_metadata['last_hlc']` is written forward-only (`WHERE excluded.value > value`) by the `CrdtWrite.enqueue*` helpers — always `hlc.last`, the highest stamp minted, deduped in-process by `persistedUpTo` (a claim), so one action persists once — and by `persistClock()` (the engine calls it once per applied pull batch; the merges do not persist). `AppDatabase.seedClockFromStore()` seeds in `getInstance` before the instance is handed out and at the start of `onUpgrade`; with no stored value it seeds from the rows (`SyncOutboxDao.maxHlc()`) and persists; `onUpgrade` persists in a `finally`. The seed is never capped: a far-ahead stored clock is honoured and reported through `AppDatabase.clockSeedAhead` → `SyncStatus.clockAhead`. `HybridLogicalClock.maxDrift` (1 h) holds a remote further ahead than `wall + maxDrift` and above the local clock (`clampedRemotes`); the counter is clamped at `0xFFFF` (one more tick advances the millisecond). `getInstance` memoises the opening future — there is no `_instance`; concurrent callers share one open, a switch awaits the in-flight open before closing.
- **Engine seams (R6, 2026-10-23), all under `lib/services/sync/`:** `SyncGateway` (Phase 02 S1 amended it: `pushBatch(space, batch, {pushedBy, schema})` ≤ `maxBatch`, `pullPage(space, table, {after, limit})` in arrival order behind an opaque `SyncCursor` — an HLC cursor loses a row pushed late with a lower stamp —, `createSpace`/`listSpaces`/`readSpace`, `watchSpace` → `SyncSpaceSignal`; the space document is the change signal), `SyncEnvelope` (the backup serializer's map is the wire payload), `SyncSpaceRef`, `SyncGatewayFailure`; `FakeSyncGateway` in `test/support/`; no Firestore type outside `pairing_gateway.dart`. `SyncStatus` (its fields under the engine below) read by `SyncStatusService` and carried by `SyncSignedIn`/`SyncSignedOut` (the account state is emitted first, the status as a second emit; `RefreshSyncStatus`; 3 s timeout). The binding: `SettingsKeys.syncSpace*` (`sync_space_*`, per database, never in a backup — the export pin is `test/services/backup_service_sync_keys_test.dart` and the import skips `pairing_`/`sync_space_` keys), `SettingsService.getSyncBinding/setSyncBinding`, `SyncBindingService.read/bindFloor/writeBindFloor/unbind`. `SyncOutboxDao.requeueAll({required boundUid})` re-seeds the outbox from every live row and tombstone for the initial merge; `maxHlc()`. `CalendarEventService.externalChanges` + `notifyExternalChange()` → `CalendarBloc` `ExternalCalendarChange` (in-place reload, no loading state); `AlertReconcileReason.sync`.
- **Wipes and restores (R4, 2026-10-23):** "Delete all events" is `CalendarEventService.tombstoneAll()` → `CalendarEventDao.tombstoneAll(ownerUid:)` — one HLC across the five event tables, live rows only, `owner_id IS NULL OR owner_id = boundUid` (every row is NULL today), every row enqueued as a tombstone, the DAO returns the tombstoned ids and only their `alert_registrations` are hard-deleted (`deleteForEvents`, device-local, rebuilt by the next reconcile), the service reloads its cache rather than blanking it so a surviving foreign event stays shown; `CalendarEventDao.deleteAll()` survives for `importData` alone. `BackupService.importFromJson` runs inside `SyncSuspension.run` (`lib/services/sync/sync_suspension.dart`, a depth-counted static scope the engine checks before push/pull/bind): after the parse it `unbind()`s (binding keys, outbox, floor), performs today's hard wipes and inserts unchanged, then — on success and on failure alike, once the unbind has run — clears the outbox again (the inserts enqueued), writes the floor (`persistClock()` then `bind_floor := last_hlc`) and calls `notifyExternalChange()` once; a malformed file fails at the parse and never unbinds. The folder-archive import appends copies and does not unbind. **`owner_id` travels in backups (D16):** key `ownerId`, emitted only when non-null (a database with no foreign row exports exactly what it did before), imported verbatim (`Value(null)` when absent), format still 7; `createFolder`/`createNote` take `ownerId` so the fresh-id copies keep the archived ownership; counter values carry it inside `noteValueExtras` (`counterId::noteId`, `counterId::` for the global value) because `globalValues`/`noteValues` are bare ints older importers read with `as int`. Nothing reads `owner_id` yet; the backfill is Phase 02's bind.

- **The chunked wire (S6, wire 46; `docs/scalability-roadmap.md` §8.2 S6).** `content_chunks` is a push-only, content-addressed synced table (`SyncedTable(contentAddressed: true, rowKeySql: content_hash)`, `ContentChunksBinding` with `pulls => false`): every inserted hash that no row of a note of ours held before gets one outbox entry at the note write's stamp (`CrdtWrite.queueChunksIn`; the hashes a pulled manifest names are not re-queued; a hash whose last live row a save deletes loses its entry), never a tombstone — the space keeps chunks (no GC this round). The pusher sends a manifest only after every chunk it names (chunks encoded one at a time up to the part's byte budget, the manifest in the part of its last chunk; the refusal bisect works in units of a manifest plus its chunks and parks a manifest whose chunk was refused), so the space never holds a manifest without its chunks; a chunk entry acks at its own stamp. The puller never pulls `content_chunks`: for a `notes` page it fetches the hashes no live local row holds through `readRows` in batches of `rowReadBatch` (30), outside the transaction, verifies each (`textOf`) and the `bodyHash`, and hands the assembled text to the unchanged `mergeNoteDocument`; a chunk the space lacks or fails parks the note durably (S8) with the reason naming the count; a chunk row a local save replaced between fetch and merge retries the page (`ChunkRowsMoved`, no park); a page whose missing hashes × 16,384 code units exceed `SyncEngine.chunkFetchBudget` (16 MiB) is halved for that page only. The body is skipped only for an equal stamp or our own newer local row above the bind floor (under the floor the older remote wins and must be fetched). - **Runs and their cost** (scalability record S9, `sync_puller.dart`):

- **Deleting a cloud copy (D1, 2026-11-10, its debt pass 2026-11-11; record `docs/cloud-multi-user-roadmap.md` — §5.1–5.8 the design as built, §5.9 the history).** "Delete cloud copy" is the bound Sync section's last row (`SemanticsIds.sharingSyncDelete`, a destructive title, `AppDialogs.confirm(isDestructive: true)` under `sharingSyncDeleteConfirm`): the space is removed from the account for good, this database unbinds, nothing local is touched. **The protocol.** The local phase is awaited by the page's short step (`SyncSpaceService.deleteCloudCopy()`, the caller stops the engine first): read the space (gone → unbind and return; its `schema` above `syncSchemaVersion` → `SyncBindFailure.appOutdated`, nothing changed) → `markSpaceDeleted` (the space document gains `deletedAt` = the server's time; a failure changes nothing) → read again (the schema is final once marked; a newer one there leaves the mark standing, the database bound and paused) → record the pending deletion install-wide (`SyncPendingDeletion {space, spaceName}` under `SettingsKeys.syncPendingDeletions`, kept by `SyncSpaceRegistry`, never in a backup) → `unbind()` as "Stop syncing" does, where the call returns. The remote phase belongs to the service's background run, one at a time for the whole process (the debt pass): `deleteRows` for every table of `syncedTables`, `content_chunks` included, in pages of `SyncGateway.rowDeleteBatch` (20: each deleted row costs the rules one `get()` of the space, and Firestore documents twenty access calls per multi-document request; a timed-out page halves) until each reads empty → `deleteSpace` → the record cleared. A page refused while emptying is followed by a read of the space: gone means another device finished it. **The rules:** a marked space refuses every update of its document, so every push to it fails whole (a push writes that document in the rows' own transaction); only a marked space lets its rows and then its document be deleted (`spaceMarked()`); a live space's rows still leave by tombstone alone; the space document goes last because a row under a missing space can never be deleted. **The run and its status:** `SyncDeletionStatus {accountUid, pending, running, removed, failure}` through `deletionStatus(uid)` and the broadcast `deletionStatusOf(uid)` (the current value first, then every change; running from the instant a deletion is recorded). A record whose space is gone or reads unmarked is cleared, only a marked space is emptied, and the run never marks; a record whose space a newer build wrote to is passed over and the run ends `appOutdated`; a failure of the link or of the account stops it and leaves the records. The run is requested by the delete, by `finishPendingDeletions({accountUid})` ("Finish deleting"), by `start()` meeting a marked space (recorded, never offered, the bind decided at once) and by `followAccounts` — the account stream followed from `configureDependencies` for the life of the process, so an interrupted deletion resumes when the account becomes known: once per process and account, and again after a run that ended on a refusal or offline; `bindExisting` and the download read the space and answer `spaceGone` for a missing or marked one. **Other devices:** `SyncPause.spaceDeleted` ("Paused — the cloud copy was deleted") for a space that is marked or gone — from the signal, from the diagnosis of a denied push (every denied batch, and before a fresh row is parked as refused; a retried park is not read for again), from `_regainsAccess`'s one read — while a refusal stays `noAccess`; nothing runs, the outbox and the parks stay, the engine never unbinds, and "Stop syncing" is the way out with its own confirmation body. **Bloc and page:** `DeleteCloudCopyRequested` is a short step through `_step` (`SyncBindDeleting`), `FinishDeletingRequested` a request and no step; every state that carries the signed-in account (`SyncSignedIn`, a failed sign-out's `SyncFailure`) carries its `deletion` status, followed from the service, and a status that arrives during a status read never costs that read (the guard compares the states' origins). The page shows a deletion in a section of its own, last on the page after Pairing and the held-back section (`syncDeletionSection`; the one row `sharingSyncFinishDelete` is running — "Deleting cloud copy" with a count —, waiting — "Finish deleting" —, failed with the failure as its value, held with "Update ANTA to finish" after `appOutdated`, or ended — "Cloud copy deleted", kept in place until the page is opened again), so nothing above it ever moves; one rule, `SyncStatus.canDeleteCloudCopy` (bound, and not under `accountMismatch`, `appOutdated` or `spaceDeleted`), serves the page and the bloc. **The owner's steps and the limits:** the rules deploy before the build installs; D1 on every device before the first delete (an older build parks a marked space's rows as refused and still offers the space for binding); a deletion has no cancel and no undo. - **Deleting the account (D2, 2026-11-11; record `docs/cloud-multi-user-roadmap.md` §6.1 — the design as built, its last block the history).** "Delete account" is the Account section's second row (`SemanticsIds.sharingDeleteAccount`, a destructive title; rendered everywhere but where sync is unavailable, held while nobody is signed in, while another step runs and while the account's deletion runs; its confirmation under `sharingDeleteAccountConfirm`): every cloud copy of the account, its pairs and invites and the sign-in account itself are removed, nothing local is touched. **The flow.** `DeleteAccountRequested` asks Google again first, outside any step (`AuthService.reauthenticate()`; the flow reads `SyncAccountDeleting`; dismissed → idle; another account chosen → `OtherAccountException` → `SyncBindFailure.otherAccount`; a failure here is the account row's, `SyncBindFailed.account`), then — only for the account the prompt confirmed and a bloc still open — one short step with the engine stopped, `SyncSpaceService.deleteAccount(accountUid:)`: refused without an `AccountCloser` or while a restore runs; the account's spaces listed (a failure, or a space a newer build wrote to, changes nothing); the account's deletion recorded install-wide (`SettingsKeys.syncPendingAccountDeletion`, kept by `SyncSpaceRegistry`); each space marked and recorded one by one, this database's own first and unbound at once; the account's run requested and handed a licence dated at the call. **The end.** D1's run empties and removes the spaces, then closes the account only when it holds a licence no older than `SyncSpaceService.accountCloseWindow` (four minutes, under the roughly five the server is observed to give a sign-in — its documentation names no figure), no call is still marking and a listing of the account's spaces reads empty: `AccountCloser.close(uid, stillWanted:)` — `PairedAccountCloser` (`lib/services/sync/account_closer.dart`) forgets the open database's pairing (`PairingService.forget()`), ends (a refusal read back) and deletes every pair, deletes every invite the account created or redeemed, asks `stillWanted()` once (no when the deletion was given up, the window passed or a space of the account was recorded meanwhile → `withdrawn`, a wait) and calls `AuthService.deleteAccount()` (bounded at 30 s → offline; `RecentSignInRequiredException` → a wait) — then the record is cleared and the uid named on `accountsDeleted`, which the bloc turns into `SyncSignedOut(accountDeleted: true)` and the page into "Account deleted", said once. A run without a licence — resumed at a start-up, asked by "Finish deleting", started by a later cloud copy's deletion — finishes the copies and waits (`SyncDeletionStatus.account`, the row "Finish deleting account", whose tap asks Google again); an attempt takes back only the licence it began under, never a later call's. **Invariants.** No bind of an account whose deletion is recorded (`SyncBindFailure.accountDeleting` from `start`, `createAndBind`, `bindExisting` and `downloadIntoNewDatabase`; the page holds the bind row); a sign-out gives the deletion up before it signs out (`abandonAccountDeletion`, whether or not the sign-out then lands) and another account signing in drops the record; the copies already marked are removed either way; the done row says "Account deleted" only after a run that was deleting the account. **Ownership.** An unbind sets `owner_id` back to NULL for the rows of the account that bound; a bind owns every row not already that account's (`owner_id IS NOT ?`) — an unbound database holds only this device's own rows, so a person back under a new uid uploads everything. **Pairing and rules.** `PairingGateway.findPairs` / `deletePair` / `findOwnInvites`; a pair that reads gone raises the ended notice — at a reconcile, or when the listener hears "no document" after a live one, never before; the rules let a member delete an ended pair, read a missing pair as "not found", let an account list and delete its own invites, and let a delete of what is already gone through. **The owner's steps:** the rules deploy before the build (without it the end stops as "permission denied" at the pairs, the copies already gone); once, on the phone, with a throw-away Google account — the fresh-sign-in window is the one thing no emulator proves. - **Sharing, the owner's side (F1 and its review's fix pass, 2026-11-12; record `docs/cloud-sharing-foundations.md` — §2 decisions k, m, n; §3 the grant, §4 the wire and rules, §12 as built).** Nothing in the app shares yet; what exists is everything a share switch will stand on. **The grant** is the pair id, stored on the root alone (`shared_pair` with its own `shared_stamp` on `calendar_events` and `folders`, v52–v53, merged as a register apart from the row — `CrdtMerge.mergeMark`) and derived for what hangs under it; `sharedTables` (`synced_tables.dart`) names the five tables that can be shared, parent first. **Wire 47:** an event and a folder carry their mark in `data.sharedPair` and its stamp in `data.sharedStamp`; a shared row's document carries the grant in effect at its top level (`SyncEnvelope.sharedPair`, stamped by the pusher after `encode` from `SyncTableBinding.sharedPairs`) with `wire`, the pushing build's wire version; the space document carries `sharedPair`, the pair its notes are shared into, written by every push and removed when none (`SyncGateway.pushBatch(sharedPair:)`, `FolderDao.sharedPairOfNotes`). `_cutOverWire` re-sends notes only for a database that last ran below `DatabaseSchema.bodyWireVersion` (46); one that ran below `shareWireVersion` (47) reads `calendar_events` and `folders` again from the start once (`_WireCutover.marks`), so a mark an older build could not read is taken at the row's own stamp. **Who re-says a document** (`_Puller._resayShares`, after each merged part of a shareable table): a document that names a pair while the row is private here is queued again always; one that is private while the row is shared here only by the device that pushed it, or by one whose deciding write is newer than that push (`SyncTableBinding.shareStamps` against `SyncPullPage.pushed[key].at`) — private always, shared only on proof, and the same for the space's own `sharedPair` (`SyncGateway.writeSpaceShare`, `_settleSpaceShare`). **The push** sends real writes before re-sends (`SyncOutboxDao.pending(unpushedOnly:)`), so a mark is in the space before the rows under it, and leaves queued a row whose share changed while its push was in flight (`_Pusher._regranted`). **Rules:** a member of the active pair a document names, when that pair also holds the document's owner, may `get`/`list` it through the collection-group matches of the five tables — a query must pin `sharedPair` and `ownerId` — and may `get` a chunk of a space that names their pair; ending or removing the pair revokes both at once; a new pair's id is `<invite code>_<nonce>` (`PairingGateway.pairIdFor`, `namedAfterInvite`), so an id never comes round again for the same two people; the owner's writes are checked for shape (`validShare`). Indexes: `sharedPair, ownerId, pushedAt` per shareable table, collection-group scope. **Every device of an account updates together:** a build before 47 pauses as `appOutdated` once a 47 build has pushed. Suites: `test/database/shared_pair_test.dart`, `sync_share_push_test.dart`, `share_mark_service_test.dart`, the rules suite's group "sharing".
- **Sharing, the reader's side (F2, 2026-11-12; record `docs/cloud-sharing-foundations.md` §5, §6, §11).** A second, smaller pull after a run's own pull and drain (`_SharedReader`, `sync_shared_reader.dart`), which must never fail or pause the account's own sync. **Whose row is whose:** `sync_metadata['shared_owner']` names the account whose rows this database reads (`shared_pair` beside it); a row is another person's exactly when its `owner_id` is that value — never "any owner but mine", because a row from before the bind carries the account's uid, one written since carries NULL, and an old binding may have left a third (`SyncDao.mineSql`; `SharedRowDao.begin` adopts and queues such strays before the first shared row lands, and the push adopts one it meets queued, `_Pusher._adopted`). **When:** an account that never paired, shares nothing and holds no shared row makes no call; otherwise a poll, unasked at most once per `SyncEngine.sharedReadInterval` (five minutes), at once on "Sync now". **Who:** the active pair asked of the server (`SharePartnerSource.activePartner`; "could not be asked" throws and nothing is removed) — and that answer also clears this account's own marks of any other pair (`FolderDao.clearSharesExcept`) and removes every shared row when the pair ended or changed. **What:** per shareable table `SyncGateway.sharedPage` (a collection-group query pinned to pair and owner, its cursor under `shared_cursor.<table>`), then `sharedCount` — fewer on the server than held means rows left, so the table is read from the start and what is not returned is hard-deleted (`SharedRowDao.removeAbsent`); once a day from the start whatever the count says. **Merge:** `SyncTableBinding.mergeShared` — the owner's copy wins whatever the stamps say (`CrdtMerge.everyStamp`), nothing queued, repaired or stamped, the owner's own mark not stored, the clock not moved; refused (`SharedRowRefused`) over, or under, a row this device holds as its own. A note's text comes from the owner's space by hash (`readSharedChunks`); a shared folder whose parent is not shared stands at the top level with the real parent kept under `shared_root.<id>` (`SharedRowDao.placeFolders`). **Stop syncing** removes the shared rows in the unbind's transaction, and `SyncBindingService.onSharedRowsRemoved` (set by DI) reloads the screens. A new path that hard-deletes or rewrites rows of the five tables has to leave the shared ones alone. Suites: `sync_shared_reader_test.dart` over `SharePair` (two accounts, `support/sync_pair.dart`), `share_partner_source_test.dart`.
- **Sharing, as hardened by F3 and the F2 review (2026-11-12; record §5–§8, §12).** **The reader is not the run's:** it runs after the own pull and drain even when a table of the account's own failed (only the bind's first merge waits for a complete pull, and never after a pull a leave cut), its calls do not go into the run's tally — a read of the pair must not end a back-off or lift a quota pause — its rows are not in `SyncRunReport`, and its whole body, local reads and final stamp included, sits inside one guard; only a halt goes through. **The count** is ordered by `pushedAt` like the page query, or the one collection-group index would not serve it in production (the emulator needs no index and cannot show this); a count that fails ends only that table's look for rows that left. **A note waiting for its text** (the owner's space did not name the pair) is kept under `shared_waiting.<note id>` = `<tries>|<owner uid>/<space id>` and asked for alone (`SyncGateway.readSharedRows`, one `get`) at most twelve times, then left to the daily read from the start — never the whole table from its start per poll. **Read-only lives in the database:** `SharedRowFences` (v54, `drift-migrations/references/persistence-rules.md`) skips every write of another account's row, so a write of one does nothing rather than fail — ask `SharedRowDao.isShared(table, id)` before offering an edit; `createNote` / `createFolder` under a shared folder throw `SharedRowException`; only `SharedRowDao.writing` (the reader, the removals) gets past. **The person's own row comes first in both orders:** a shared row is refused over one (`SharedRowRefused`), and the own pull evicts a shared row under a key it is about to merge (`sharedAmong` / `evict` in `_Puller._applyPart`). **Backups:** an import stores every row as the importer's own (`JsonKeys.ownerIdOf` is null — this replaced readiness D16 A), the calendar `exportData` lists leave shared rows out, and a database-file copy keeps `shared_owner`, so its cached rows stay fenced and go at the unbind. Known limit: a device no run reaches keeps showing shared rows after the grant ended (record §11).
