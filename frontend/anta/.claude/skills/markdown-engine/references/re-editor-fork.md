## Generated And Local Package Notes
- `packages/re_editor/` is a local editor fork, perf-tuned for this app. Key optimizations to preserve:
  - `CodeLines.asString` uses a 2-slot round-robin cache (LF+trimNewlines vs LF-only calls alternate without thrashing).
  - `_CodeLineSegmentQuckLineCount` sub-counts with a `_hashCache` field; `==` short-circuits on length/dirty/lineCount/charCount before deep comparison. Its `add`/`[]=`/`length=` maintain `_lineCount`/`_charCount` by delta (every other `ListMixin` mutator routes through those three) and its full-range `clone` carries the cached counts — never reintroduce a `fold` on a mutation path; `test/utils/code_lines_sharing_test.dart` pins the counts against a naive fold and `code_lines_benchmark_test.dart` measures it.
  - `findDisplayParagraphByLineIndex` and `_findDisplayRenderParagraph` in `_code_field.dart` use binary search on the sorted paragraph array.
  - `_CodeParagraphProvider`'s paragraph cache (`_kMaxCacheSize`) is a bounded LRU (equality map + identity L1, both capped). Eviction is CLOCK-style since the 2026-09-05 Session 5 review: an identity hit sets `_recentlyUsed` on the paragraph, a flagged L2 head gets one lap's second chance, and only an unflagged head leaves both maps — L2 is never touched on the identity hits that serve every stable line, so a plain head-eviction walked through the still-visible lines once per 128 fresh caret-line spans (`test/re_editor/paragraph_cache_identity_test.dart` pins the hot lines surviving and the 128 bound). A paint-only `textStyle` change (the light/dark `textColor` flip) clears the highlighter cache and relays out — the colour is baked into the cached `ui.Paragraph`s and `updateBaseStyle` runs only during layout (`text_style_repaint_test.dart`). Lowered 512 → **128** on 2026-09-04 after `dumpsys meminfo` on a 10k-line list note showed the 384 extra entries cost ≈15 MB native heap (≈39 KB per retained paragraph); 128 covers 3–5 phone viewports and a list-line miss re-lays out in ~40 µs, so scrolling back past the cache costs 1–2 ms a page. Numbers and harness in `docs/live-editor-review-and-slices-2026-09.md` §5 — re-measure before changing it again.
  - Hanging-indent paragraphs (`_buildHanging`, 2026-09-04): the laid-out marker `_ParagraphImpl` and its indent are memoized in `_markerMeasurements` (128-entry LRU keyed by the marker `TextSpan` by value — the marker span carries the root style, so equal keys imply the same scaled paragraph style; cleared by `clearCache()`), which cut a cold 40-list-line layout by ~25 % (`test/re_editor/hanging_paragraph_benchmark_test.dart`). The indent is the marker's advance **floored**, and the marker/content boundary offset is answered by the content side for both affinities, so the seam resolves to exactly the indent and the marker's rects overlap the content's by under a pixel instead of leaving a gap. `height`/`lineCount` are the max over marker and content (the identity `height == lineCount * preferredLineHeight` holds). Word wrap off (infinite width) never builds a hanging paragraph. Two debug asserts guard the couplings the app relies on: a root span that scales `fontSize` keeps the base style's strut inputs (`fontFamily`, `height`), and every `CodeInlinePaintSpan` box fits under the line's preferred height — plus, since the 2026-09-05 Session 5 review, a post-layout check (`_debugLaidOutLineFitsStrut`, only for trees holding a paint span) that no laid-out row grew past the strut, because a middle-aligned box at exactly the strut height passes the declared-height check and can still grow the line. The marker split is rejected by `lineCount > 1` on the built marker paragraph (not a 1.5× height gate, which disagreed with the `ceil` line count and could report a phantom second row); `CodeHangingTextSpan.hangingChars` must fall on a word boundary (`getWord` never crosses the seam); a `CodeDecoratedTextSpan` cut by either split keeps its decoration through `_rebuildSplit` (a hanging root's tag is deliberately dropped). The scroll helpers `makePositionVisible` / `makePositionCenterIfInvisible` measure the target line by `lineHeightOfLine` (the caret is painted the paragraph's own height, so the flat base height left a scaled line half clipped), and the off-window centring jump measures from the last displayed line and subtracts half a viewport (`test/re_editor/scroll_to_position_test.dart`). `CodeScrollController.revealInAncestors(position, {margin, duration, curve})` (2026-09-30) is the other direction: `_CodeFieldRender.showPositionOnScreen` hands the caret line's rect — clipped to the editor's box, so a line the editor has not scrolled to reveals nothing and returns false — to `RenderObject.showOnScreen`, for an editor embedded in a scroll view (the event editor's description cell); it reads the last layout, so callers run it post-frame, and it is opt-in — the note editor never calls it (`test/re_editor/reveal_in_ancestors_test.dart`). Since 2026-09-07 that arithmetic lives once in `_verticalCenteringTarget`, shared with the layout-time variant `CodeScrollController.makeCenterIfInvisibleOnLayout` → `_CodeFieldRender._centerIfInvisibleInLayout`: the request parks on the scroll controller (which `_CodeField` now hands to the render), `performLayout` consumes it right after `_updateDisplayRenderParagraphs` and corrects the viewport with `correctBy` in a bounded loop (estimate while the line is off-window, exact once laid out), so the frame that comes out of that layout — the editor's first frame when armed before the mount — already shows the line, and nothing is painted at the top first. It is how the note editor opens at its stored position; the post-layout `makeCenterIfInvisible` stays for the after-preview restore, which must wait out the keyboard animation. `correctBy` notifies no scroll listener — the app's `ScrollProgressIndicator` catches up through the `ScrollMetricsNotification` tick the editor wrapper hands it as `repaint` (its periodic metrics check is only the fallback for callers without one), and since 2026-09-08 it takes such a corrected offset as one step: its jitter filter smooths only small, continuous changes, seeds itself from the first real reading, follows a dragged thumb 1:1, and after a smoothed step requests frames until it has settled, so the thumb rests on the true position without waiting for the next scroll. Its geometry is pure layout (`CustomSingleChildLayout`, thumb = 15 % of the live track, clamped) — nothing about the track or thumb is cached across builds, which is what once left a keyboard-sized thumb behind after the keyboard closed. `CodeParagraphProviderForTesting` (`code_paragraph_testing.dart`, `@visibleForTesting`) is the only way to drive the provider outside the render and `CodeFieldRenderForTesting` (`code_field_testing.dart`) the only way to read the render's line-height getters and its `displayedLineIndices` (the laid-out window); `test/re_editor/hanging_paragraph_test.dart` and `line_height_contract_test.dart` pin all of the above.
  - `_CodeHighlighter.clearCache()` clears the plain-span memo together with the paragraph cache (the memo hands out the span instances the identity cache is keyed on).
  - `_CodeHighlight` debounces highlight requests at 50 ms to avoid per-keystroke re-highlight.
  - `_kInitialCodeLines` uses `List.unmodifiable` on both levels for write-protection (no `const` because sub-objects aren't `const`).
  - When adding new mutation paths to `CodeLines`, call `cloneShallowDirty()` (not the public constructor) to preserve the `_segmentEnds` / `_asStringCache` reset contract.
  - App code never rebuilds a document with `CodeLines.of([...])` (2026-09-03): a single-line edit goes through `CodeLines.replaceLine(index, line)` (`from` + `[]=`, so exactly one segment re-owns its backing list and every other segment stays shared by identity — the dirty flag `MarkdownEditorLineIndex` relies on) and a single-line removal through `CodeLines.removeLine(index)` (`sublines` + `addFrom`; an empty result is fine — since 2026-09-05 the controller's `value` setter maps an empty document onto the initial blank line exactly like its `codeLines` setter always did). The page's Enter continuation (`_handleTextChange`), the wrapper's checkbox toggle and Tab/Shift-Tab indent are the three callers; `CodeLines.of` over a whole document breaks every segment's identity, forces a full index rescan and pins a whole-document undo node. `[]=` invalidates only what a same-length replacement can change (line/char counts, `asString` slots), locates the segment with the same binary search as `operator []` and leaves the last-hit window on that segment. `CodeLines.hashCode` is structural (`Object.hashAll(segments)`, each segment's hash cached) so it agrees with `==` (2026-09-05 — it was the segment list's identity hash); a segment never grows through its length setter (assert), `sublines`/`replaceLine`/`removeLine` validate their ranges with the SDK's `RangeError` helpers.
  - Undo history (`_CodeLineEditingCache` in `_code_line.dart`) is capped at `_kMaxUndoHistory` (200) nodes behind the current one; the oldest survivor's `pre` is cut so `canUndo` turns false there. It is a hard bound, not a coalescing window — `edit()`'s one-node-per-line heuristic and `runRevocableOp` are unchanged. `test/re_editor/undo_history_cap_test.dart` pins it (that folder is the home for fork tests). **The undo baseline is a load, never an edit (2026-09-05):** a controller is constructed around the empty document, and `set text` is a revocable op, so seeding through it left every freshly opened note with one undo step whose target was that empty document — pressing undo before typing wiped the note and auto-save persisted the wipe. `CodeLineEditingController.loadText(text)` is the load operation: it publishes the document and resets the history to it (`canUndo`/`canRedo` both false, the first undo a later edit allows lands on the loaded text), and `fromTextAsync` clears its history the same way once the async parse lands. Every seeding or wholesale swap — the note page's content load, the event editor's scope swaps / reset / expand-return, the description sheet's seed — goes through `loadText`; `set text` is only for a change the user should be able to take back, and the old `text = …; clearHistory();` pair is gone. Alongside it, `_CodeLineEditingCache` folds a **selection-only or composing-only change into the current node** instead of recording it: a tap after a load no longer flips `canUndo` (the old initial-node rule appended a node for any change, caret moves included), and a caret move after an undo keeps the redo chain. The page rebuilds its toolbar only when `(canUndo, canRedo)` actually differs from what the bar was built with (`_syncHistoryButtons`, deferred past the frame when the controller notifies mid-build) — never per keystroke. `test/re_editor/undo_baseline_test.dart` and the page suite's "undo baseline" group pin all of it.
  - On Android/iOS the editor mounts a bare `Focus.onKeyEvent` instead of the `Shortcuts`/`Actions` layer; it handles Backspace, Enter and (2026-09-03) Tab/Shift-Tab — all three respecting `readOnly`, on `KeyDownEvent` and (2026-09-05) `KeyRepeatEvent` so a held key repeats as it does on desktop — routing Tab through `shortcutOverrideActions` when the app supplies one (the wrapper's list-aware indent) and `applyIndent`/`applyOutdent` otherwise, so a physical keyboard never moves focus out of the editor. Since the 2026-09-05 Session 6 review `readOnly` is checked *before* the override lookup on that path, and the desktop `Shortcuts` path filters override actions by the same editable-intent rule, so a read-only editor never runs the app's indent (`test/re_editor/readonly_shortcut_override*_test.dart`). Widget tests run as Android by default; the desktop `Shortcuts` path needs `debugDefaultTargetPlatformOverride` set in `setUpAll` before `kIsAndroid`/`kIsIOS` (top-level finals) resolve.
  - `CodeInlinePaintSpan` (`code_paragraph.dart`): a placeholder span that reserves a box in the line layout and custom-paints onto the canvas after `drawParagraph` (used by the editor's task checkboxes). It occupies exactly one U+FFFC code unit, so span builders must substitute it 1:1 for a single source character; keep its height under the strut height (placeholders ignore `forceStrutHeight`) or the line grows. `_ParagraphImpl` pairs paint spans with `getBoxesForPlaceholders()` boxes lazily on first draw.
  - `CodeDecoratedTextSpan` + `CodeTextDecoration` (`code_paragraph.dart`): a text run that paints a rounded chip BEHIND itself (before `drawParagraph`) — used for the editor's `#tag` pills and inline-code chips. Unlike `CodeInlinePaintSpan` it reserves no layout space; the text stays ordinary editable text.
  - `trucate` / `_dropPrefix` keep untouched subtrees by identity (no rebuild) — required so decorated/placeholder subclass spans survive the hanging-indent marker/content split; don't regress this to unconditional copies. Neither emits empty `TextSpan('')` nodes (a fully consumed text becomes `null`, childless leftovers are dropped) — plain text and placeholder alignment are unchanged, pinned per split point.
  - **Screen-reader surface (Session 7c, 2026-09-05).** `_CodeFieldRender.describeSemanticsConfiguration` announces a boundary multiline text-field node whose `value` is the **visible window only** — `_displayParagraphs`' lines joined by `\n`, read straight from `_codes` after layout (never `asString`; `CodeLines.debugAsStringCalls` pins that the semantics path never rebuilds the document string — the old whole-document value was P11's per-keystroke stall). The node carries `onTap` (focus + keyboard, collapsing an out-of-document selection to 0/0 first), `onDidGainAccessibilityFocus` **on macOS only** (focus **without** the keyboard: `requestFocus()` then `consumeKeyboardToken()` — the token is what would open the IME; `code_editor.dart` passes `null` on every other platform, mirroring `material/text_field.dart`, which sets this action and its lose twin only under macOS — on Android a TalkBack sweep across the editor would take keyboard focus and, with no lose handler, never give it back), `onSetSelection` and, only while both ends are on screen, `textSelection` — flat offsets into the announced string, mapped through `positionForWindowOffset` / `windowOffsetForPosition` on the render (a separator offset resolves to the end of the line before it; an off-screen caret is **omitted, never clamped**). The handlers live in `code_editor.dart` and reach the render through explicit callbacks plumbed `_CodeEditable` → `_CodeField` → render: on this SDK a `Semantics` widget above a boundary render never merges into it (configs merge child → node-forming ancestor only), so the actions must be declared on the render's own config. No `onDidLoseAccessibilityFocus` — it would unfocus the editor the moment TalkBack steps onto a zone child. Zones: when the interceptor supplies `zonesOf`, the node sets `explicitChildNodes` and `assembleSemanticsNode` hangs one child per zone per visible line (label, `tap`, rect = `getRangeRects` union shifted by the paint transform and clipped to the viewport, `OrdinalSortKey` in line order, nodes kept in a keyed cache so ids are stable across frames — keyed by **line index**, so an edit that shifts a zone's line renumbers its node, an accepted TalkBack focus-continuity cost pinned as the contract); a child's tap calls `shouldIntercept(pos)` then `onTap(pos)` at the zone's start, which the wrapper's claim memo accepts unchanged. The zone-node cache is nulled in the render's `clearSemantics()` override (plus an `attached`/`parent` guard on reuse, defensive, no known trigger) — without it a second platform semantics enable reuses nodes of a disposed owner; `test/re_editor/semantics_zones_test.dart` drives `clearSemantics()` directly because no test harness tears the owner down. `codes`/`hasFocus`/`readOnly` and the callback setters call `markNeedsSemanticsUpdate()`; layout already re-marks semantics (which is why the `selection` setter does not), so scrolling refreshes the window and the children. The app side of `zonesOf` runs once per visible line on every semantics flush, so `ModernEditorWrapper` answers the three pass-through rules (reveal, fence, over-long) before touching a grammar and memoises the rest per line text (`LruCache`, 256 entries, dropped when the enabled-zone set or any of the five labels changes; `debugZoneResolveCount` counts misses). The fork's `set semanticsZonesOf` never receives the app's function — `CodeEditor` forwards its own bound method — so any app-side cache of labelled zones must invalidate itself. `CodeLines.debugAsStringCalls` increments inside an `assert` block, so it is debug-only. Pinned by `test/re_editor/semantics_value_test.dart`, `semantics_actions_test.dart`, `semantics_selection_test.dart`, `semantics_zones_test.dart` and `test/widgets/modern_editor_wrapper_semantics_test.dart`.
  - `CodeFindController.goToMatch(int index)` is an app-added method: it clamps the index, pushes exactly one new `CodeFindValue` when the target differs from the current match, and always centers the match — re-targeting the current match pushes nothing but still scrolls it back into view (2026-09-04). It exists so the note search bar's match list can jump to an arbitrary hit without stepping `nextMatch()` (each step pushes a value, and every push costs a selection write plus a scroll).
  - `CodeEditorTapInterceptor` claims (`_code_selection.dart`, hardened 2026-09-04, Session 7b): a claim is taken at tap-down and consumed at tap-up within slop; **exactly one claim is live at a time** — a press arriving while one is live is never intercepted and takes the plain path, and the live claim dies only with its own pointer's up/cancel — except that a new primary press from the *same mouse device* (`_interceptedTapDevice`) drops the claim first, since one mouse cannot hold two primary presses, so a claim whose up/cancel never reached the `Listener` (capture steal, `PointerRemovedEvent`) cannot strand the interceptor. On desktop the claiming pointer moving past the slop releases the claim into an ordinary drag selection: the fork replays `_onDesktopTapDown` at the original down offset first, so the replay produces the caret and pairing state a plain press there would have produced (when the down cell lies inside an existing selection, `_selectPosition` takes its `_handleByNextEvent` early return and the drag extends from that selection, exactly like a plain press), flips `_tapping`, and schedules the same deferred `ensureInput` a plain press does — `mounted`-guarded, like the plain-press one. The slop test is **per axis**, through `computeHitSlop(kind, MediaQuery.maybeGestureSettingsOf(context))` (the private `_withinHitSlop`), at both the move-release rule and `_finishInterceptedTap`, so a claimed press either fires or becomes a drag exactly where the drag recognizers would accept it — a euclidean test is stricter on a diagonal and leaves a window (mouse jitter under 1 px per axis) that releases the claim, moves the caret and fires nothing (2026-09-05 review). Pinned by `test/re_editor/tap_interceptor_test.dart` (Android path) and `tap_interceptor_desktop_test.dart`; the desktop suite sets `debugDefaultTargetPlatformOverride` in `setUpAll` before the first editor builds because `kIsAndroid`/`kIsIOS` are process-wide finals.
  - **The controller handoff tells only the editor's own listeners (2026-10-01).** `_CodeLineEditingControllerDelegate`'s `delegate =` setter used to end in `notifyListeners()` on the host's controller unconditionally, and `_CodeEditorState.initState` assigns the delegate before anything has subscribed through it — so every editor **mount** announced a change that never happened to every listener the app holds on that controller, from inside `initState`, i.e. mid-build. Three things followed: the note editor read each mount as an edit (the unsaved dot for five seconds after every open, until the debounce found nothing to write); any builder above the editor that listened to app state driven by that notification was dirtied while the framework was building — "setState() or markNeedsBuild() called during build", reported on `ValueListenableBuilder<SaveStatus>` when a Live Markdown Rendering toggle remounted the editor of a note whose status had settled on `saved`; and on such a remount the *outgoing* editor's listeners, still attached until the frame ended, ran deactivated ("Looking up a deactivated widget's ancestor is unsafe", raised while the same notification was being dispatched). The setter now notifies only when the delegate has listeners of its own (`_listeners.isNotEmpty`), which is exactly the controller-swap case the notification exists for; a first attach tells nobody. A swap into a mounted editor still notifies from `didUpdateWidget`, mid-build — nothing in the app swaps controllers, and the sheets' build-safe relays and the page's deferred `_syncHistoryButtons` stay as the guard for that. `test/re_editor/controller_handoff_test.dart` pins all four shapes.
- Rule (2026-09-03): no nested `.git` under `packages/re_editor/` — ANTA's repo is the fork's only history. A fifth candidate, `10fdbc1`, was already present in the fork's own delta (`_code_input.dart`'s `onFocusReceived`) before 7a — the pick was a no-op, dropped as a duplicate. Reproducing the patch needs `dart format` (Dart 3.12) on BOTH the base and fork trees before diffing, or formatting-only reflow swamps the real delta; the full per-file patch list and the upstream-commit disposition table live in `docs/re-editor-performance-2026-07.md`.
