# Calendar & Events

Read [docs/calendar-events-feature.md](../../../docs/calendar-events-feature.md) — the deep, implementation-aware reference for this subsystem (domain model, recurrence semantics, persistence, editor layout). This skill lists the hard rules and the change-set recipes; the doc has the details.

Fasting specifically: §4.5 of that doc is the behaviour of record; [docs/fasting-schedule-roadmap.md](../../../docs/fasting-schedule-roadmap.md) is the **design record** behind the shipped personal schedule (weekdays + months + month scope + exception dates in one `calendar_fasting_schedule` JSON key) — it carries the rationale and the deferred ideas. Hard rules that outlive both: the schedule may **subtract** from a tradition's own weekly rule but never **invent** days it lacks — that covers the **weekday scope** (`FastingWeekdayScope`, 2026-08-22), the exact mirror of the month scope: `weeklyOnly` (default, pre-existing behaviour) gates only the year-round weekly rule, `allFasts` gates every mark from the same `_buildYear` `merge` probe, and either way it only removes days (`forceDates` still wins on a weekday turned off, and the JSON field decodes to `weeklyOnly` when absent or unknown); `calendar_fasting_weekdays` is read as a seed and never written again, and its absent-vs-empty-string distinction must stay alive in `SettingsService.getFastingSchedule` + `FastingSchedule.decode`; The sheet's scope hint must follow the **selected** scope, never the section (`_weekdayScopeHint`/`_monthScopeHint`): a flat "a day you turn off is never marked" describes only `allFasts` and is false under the default, which is what made a Wed/Fri practice look broken every August (the Dormition fast owns Aug 1-14 whatever the weekday set says — 19 of 31 days marked under `weeklyOnly`, 8 under `allFasts`). `FastingCalendar.resetConfiguration()` belongs to `SettingsService.reset`, never to a direct `DatabaseLifecycle` registration (that registry self-clears after each switch).

Schema lineage (current: **v31**). Latest: **v31** `idx_calendar_event_skips_active` + `idx_calendar_event_absences_active` (partial covering indexes on the delta tables; index-only — no table, column or backup change — created by `DatabaseIndexes.createCalendarDeltaIndexes()`, which is **separate from** `createCalendarIndexes()` because the latter runs inside the v9→v10 migration where neither delta table exists yet) → **v29** `calendar_event_templates` (reusable event presets — CRDT-shaped from birth, additive backup key `eventTemplates`, no version bump, strand rule keyed to *categories*) → **v30** `calendar_event_skips` (cancelled occurrences — additive backup key `eventSkips`, no version bump, standard event-keyed strand rule). Earlier: **v26** `tracks_presence` + `calendar_event_absences`, **v27** `calendar_events` CRDT, **v28** `per_occurrence_descriptions` + occurrence CRDT. **v24** sparse `calendar_event_occurrences` (per-occurrence description overrides — see the hard rules below; additive backup key `eventOccurrences`, **no** version bump, but an absent key alongside a present `calendarEvents` must *clear* the table). v10 calendar tables → v11 `end_date` + time-of-day → v12 `description` → v13 holiday profiles → v14 `note_id` event↔note link → v15 data-driven `calendar_categories` → v16 `color_value`/`tint_icon`/`priority` → v17 `suppressed` holidays → v18 **priority scale inverted** (data-only `p -> 6 - p`; backup version bumped to 7, older backups flip priorities on import) → v19 `retroactive` (additive, default 0 — **no** backup bump; old backups import as forward-only, which is what they were) → v22 **computed holidays** (no column change: deletes seeded built-in rows from `public_holidays`, leaving only custom + suppressed — see the hard rule below) → v23 **yearly counts from zero** (data-only: `count_style` `numbered` → `elapsed` for counting yearly events, repairing v21's flat default) → v20 `count_occurrences` + v21 `count_style` (both additive, defaults 0/`'numbered'`, **no** backup bump — display-only occurrence labels via `RecurrenceRule.elapsedPeriods` + the single `RecurrenceFormatter.countLabel(event, day, l10n)` entry point, never touching `occursOn`: the two styles differ in **exactly one thing, the counting origin**, and the chips say so ("Count from 1" / "Count from 0"): `numbered` = count from 1 ("Day 1", "Week 3" — start day is occurrence one, all sessions of a week share "Week N"); `elapsed` = count from 0 ("0 years", "26 years" — a birth-date anchor yields the age). **Both render on the start day**; both suppress only pre-start retroactive days — keep that symmetry or the chip labels stop being true. The editor default is **frequency-dependent** (`_defaultCountStyleFor`: yearly → `elapsed`, shorter → `numbered`) — counting a yearly event from 1 is off by one against a birthday's reading (born 2000 → 27th occurrence in 2026, but age 26), so never make `numbered` the flat default again; `_countStyleTouched` re-resolves it on frequency change only until the user taps a chip, a saved counting event counts as an explicit choice, and the rows written under the old flat default were repaired by the **v23** data migration (yearly only). The live example renders the first three occurrences, so it must start at 0 for `elapsed` and 1 for `numbered`. the label leads the row subtitle and suffixes the detail sheet's occurrence chips; editor guard mirrors `retroactive`'s — `recurring && _kindSupportsInterval && _countOccurrences` — with style chips + a live three-sample example line; the birthday built-in pre-fills counting with the **elapsed** style alongside the yearly rule). The recurrence **interval** rides inside `rule_payload` JSON with no migration — keep it that way (write only when `> 1`, decode with clamped fallback to `1`; never add an `interval` column).

## Hard rules

- `TableCalendar.eventLoader` stays a pure O(1) lookup through `CalendarBloc.eventsForDay` (memoized per-day cache, cap 512). Never dispatch events, call services, or expand recurrences inside the loader. If you add a bloc handler that mutates events or the category filter, call `_invalidateDayCache()`; never invalidate from day/focus/format handlers. **Holidays are the exception no handler can see**: `WorkdaysRecurrence` and `PublicHolidaysOnlyRecurrence` read `PublicHolidays.isHoliday` from inside `occursOn`, and `PublicHolidayService` publishes straight into the static facade, so backup restore and a database switch change membership with nothing dispatched. `PublicHolidays.revision` (bumped in **both** `configure` and `resetCache`, mirroring `EventSkips`) is folded in as a **generation** by `_syncHolidayGeneration()`, called at the top of `eventsForDay` *and* `monthNetFor` — the latter also calls `occursOn`, so it must not rely on the former running first. A generation, never a cache key: the point is to drop the cache, not grow it.
- **The seven calendar services are constructed lazily, not at app start.** `PublicHolidayService`, `CategoryService`, `CalendarEventService`, `EventOccurrenceService`, `EventPresenceService`, `EventSkipService` and `EventTemplateService` are **not** in `injection.dart` — resolve them with `await X.getInstance()`, never `GetIt.I<>` (GetIt holds the *object*, so after a database switch it hands back one bound to the closed database; `getInstance()` is self-healing). `CalendarBloc._onLoad` resolves all seven through one `Future.wait` — each wrapped so a single failure cannot reject the batch — and **never emits `CalendarPageLoaded` before they resolve**. That invariant is the safety argument for the whole arrangement: the facades are read synchronously from render paths and from `occursOn`, and an unconfigured read is *silent* — cancelled occurrences reappear, every category goes grey, and `PublicHolidays` falls back to fixed dates, which changes **which days a `Workdays` event occurs on**. A new surface that reads any facade must either live under `CalendarPageLoaded` or await the owning service itself. Anything outside the body builder needs its own guard (the FAB is inert while `selectedDay` is null for exactly this reason). `CalendarPageLoading` exists but is **deliberately never emitted** — `Initial` already renders the spinner, and emitting it on a re-load would flash one over a populated calendar.
- **`CalendarEventService.externalRevision` is bumped in exactly two places** — the end of `importData()` and `reset()` — because a backup restore and a database switch are the only mutations no dispatch can observe. Never bump it from `upsert`/`deleteById`/`deleteAll`/`reload`; the bloc drives those and already emits. `CalendarBloc.isStale` compares it, `_CalendarViewState` re-dispatches on `didChangeDependencies`/`didPopNext` via the existing `AppNavigator.routeObserver`, and `_openSettings` dispatches **unconditionally** because a category delete reassigns events behind the cache without bumping anything. `RouteObserver<PageRoute>` never fires for the sheets (`PopupRoute`), which is what keeps a sheet dismissal from triggering a reload.
- **`_didInitialLoad` guards the reload, and the guard is "first load only", not "cache is warm."** After lazy registration the first `_onLoad` *is* the first read, so `reload()` there would read `calendar_events` twice; every later dispatch must still re-read.
- **Batch note content through `NoteRepository.loadContentForNotes`**, never a loop — the money ledger's fan-out runs on every event create and edit, not just on load. In its result **an absent key means "unreadable" and `''` means "no content"**: a note whose chunks fail to decode is dropped so callers can skip it rather than fold `''` and claim a balance of zero. Never paper over a missing key with `?? ''`.
- **The grid and the day panel subscribe separately.** `CalendarPageLoaded.sameGridInputs` drives the grid's `buildWhen` and is every prop **except** `occurrenceRevision`. It is *not* "everything except the overlay revision": `DayBarsResolver` and `CellTintResolver` both read `EventPresence.isMissed`, so presence is a grid input, which is why **`presenceRevision`** exists and is bumped by the two presence handlers *alongside* `occurrenceRevision` (additive — no existing consumer's semantics changed). Descriptions bump `occurrenceRevision` only; no grid surface reads `OccurrenceDescriptions`. A new presence write path that forgets the bump ships a permanently stale marker — `test/bloc/calendar_grid_rebuild_test.dart` is the guard. `sameGridInputs` compares `allEvents`/`hiddenCategoryIds` by **identity**, which is sound only because every handler that changes either builds a fresh instance: it may over-rebuild, never under-rebuild.
- **Narrowing a `buildWhen` makes a captured state stale.** The app-bar filter icon, the export menu and the FAB each have one now, so their callbacks read `context.read<CalendarBloc>().state` at press time — the filter sheet needs `format`, which its `buildWhen` deliberately ignores.
- **`CalendarPage._loadSettings` is one statement**, via `SettingsService.getCalendarPageSettings()` (previously 16-18 sequential single-row reads, 11 inside `getCalendarAppearance` alone). Every setting has a pure decoder taking the raw stored string, shared by the single-row getter and the bulk path so the two cannot drift — add new calendar settings the same way, and add the key to `_calendarAppearanceKeys` / `_calendarPageKeys`. **Use `UserSettingsDao.getValuesFor(keys)`, never `getAllSettings()`**: `user_settings` also holds a `note_position_<id>` row per note, so a full-table read scales with the note count (measured 56 ms vs 2 ms at 10k notes) on the one path that runs before the first frame. `UserSettings.value` is non-nullable, so `map[key] == null` **is** "row absent" and `containsKey` is unnecessary; but the absent-vs-empty distinction still lives in the decoders for `getFastingSchedule` *and* `getFastingAppearance`.
- **Outside-month days are faded through colours, not `Opacity`** — with one deliberate exception. `CalendarDayCell._fade` and `CalendarDayBars.opacity` **multiply** alpha (tint colours already carry their own) against the shared `CalendarDayCell.outsideAlpha`. `_onAccent` must keep estimating brightness on the **un-faded** accent or the day number inverts on a pale one. **The `isSelected || filledToday` branch keeps a composite `Opacity`**: the number is painted on top of an opaque chip, and fading the two independently destroys their contrast and washes the digit out. Every other branch paints on transparency, where per-colour alpha and `Opacity` are equivalent — never reintroduce a whole-cell wrapper there, it allocated an offscreen layer per outside day, twice per cell.
- **Marker contrast is a ratio, never a luminance delta (fixed 2026-08-23).** `CalendarDayBars` outlines a marker whose contrast against `colorScheme.surface` falls below `_minContrastRatio` (1.6:1, WCAG `(L+0.05)/(L'+0.05)`, matching `MarkdownColorPalette._contrastRatio`). It previously compared raw luminance *deltas* against a 0.22 threshold, which means opposite things at the two ends of the scale — against white (lum 0.948) a 0.09 gap is an invisible 1.05:1, against a near-black surface (lum 0.007) the same gap is a readable 2.06:1 — so, tuned on white, it outlined **six of the twelve** built-in marker colours in dark mode and none in light, exactly backwards from the pale-colour case it exists for. The stroke is **1px `strokeAlignCenter`**, never the old `width: 0.5` inset: half a logical pixel is half a *device* pixel at dpr 1.0 (desktop), which paints as a grey smear rather than a line, and an inset border ate a third of a 3px bar's fill; centred keeps the fill and its 0.5px overhang per side still fits the 1.5px inter-bar gap, so `stripHeight` is unchanged. `computeLuminance()` is memoized per colour (bounded 64, cleared wholesale) because the grid asks for one per marker per cell on every rebuild — the same "static probes only" rule the 42-cell path lives under.
- The `CalendarRecurrence` enum and `event.recurrence` field are gone — always use `event.rule` (sealed `RecurrenceRule`).
- `event.allDay` is derived (`time == null`); check `event.time != null` to render time rows — the persisted `all_day` column is a write-only mirror.
- Categories are **data-driven (v15), not an enum**: `CalendarEvent.categoryId` is a `String`. Resolve icon via `CalendarCategories.iconFor(event)` (per-event override wins, else category icon) and tint via `CalendarCategories.resolve(event.categoryId).color`. Unknown ids fall back to `other` — never throw. Built-ins keep stable ids equal to the old enum names (`'gym'`, …) and cannot be deleted; `CategoryService.deleteCategory` reassigns events to `other` in a transaction.
- The calendar filter is a hidden-id set (`CalendarPageLoaded.hiddenCategoryIds`, empty = show all) via `ChangeHiddenCategories` — new categories are visible by default.
- Never mutate `public_holidays` outside `PublicHolidayService` — the static `PublicHolidays` state is only republished by `_load()`; direct DAO writes desync the sync facade.
- **Built-in holidays are computed, never stored (v22).** `HolidaySeeds.forYear(profile, year)` (pure, in `lib/constants/public_holidays.dart`) is the single generator; `PublicHolidays` memoizes a year on first touch (bounded 12, cleared wholesale) exactly like `FastingCalendar`. Resolution order is overrides (custom rows) → computed-unless-suppressed → fixed-date fallback *only* while uninitialized. The table holds **only user deltas**: custom rows + `suppressed` rows. Never reintroduce a seeding pass or a "years covered" window — that was the v22 removal, and it is what made past-year Easter feasts resolve at all. `removeOn` **writes** a suppression row for the computed holiday (nothing else can persist "not on this date"); `restoreSuppressed` **deletes** it (clearing the flag would leave stored derived data). `importData` skips plain built-in rows from old backups for the same reason; backup stays version 7.
- **Holiday accuracy lives in the builders, not in config.** Legislatively dated holidays carry an inline `if (year >= NNNN)` guard (Juneteenth 2021, US Uniform Monday Holiday Act 1971, MLK 1986, UK New Year 1974 / bank holidays 1971 / early May 1978, German Unity Day 1990, Romania 1990/2008/2012/2016/2017/2018) so past years show no anachronisms; `generic`/`europe` stay unguarded on purpose (curated sets, not jurisdictions). Weekend **substitute days** are applied per profile in `forYear` *after* the base set: UK walks forward to the next weekday not already a bank holiday (order matters — Christmas then Boxing Day), US shifts Saturday→Friday and Sunday→Monday plus a Saturday New Year onto 31 Dec of the prior year; Germany/Romania/generic/europe have none. Both the real and substitute dates are emitted, distinguished by `HolidayOccurrence.observed` → `PublicHolidayInfo.observed` → the `publicHolidayObserved` ARB suffix — never emit a bare duplicate.
- Date normalization anywhere in calendar code: `DateTime.utc(y, m, d)` to match `CalendarEvent.occursOn`. All occurrence math is O(1) modular arithmetic on date-only UTC — no per-day allocation, no DST-sensitive math. **Hot callers that already hold a normalized day call `occursOnUtcDay` (cached `startDateUtc`/`endDateUtc`, no re-normalization); `occursOn` is the normalizing public wrapper.** `EventSkips.isSkipped` and `EventPresence.isMissed` **require** a date-only UTC day (debug-asserted, allocation-free) — never hand them a raw `DateTime`. The `CalendarEvent` constructor is **non-`const`** (the cached UTC fields are `late final`); do not re-add `const`.
- Resolve a linked note (`event.noteId`) via `NoteRepository.getNotesByIds([id])`, **not** `getNoteById` — the former filters soft deletes so you show `eventLinkedNoteMissing` instead of a ghost note.
- **The add button is `CalendarAddFab`, and scroll content clears it rather than the button hiding.** `AppSpacing.fabClearance` (88 = 56 button + 16 Scaffold margin + 16 gap) is added to the bottom padding of **every** panel-mode scrollable (agenda / day panel / timeline) — a new panel mode must do the same, or its last row's trailing actions sit under the FAB and cannot be tapped (the 2026-08-23 report). Collapsing on scroll alone is not a fix: it only moves the problem to the moment the user stops. The button is **extended and day-aware** because it targets `selectedDay`, not today — the label (`AgendaListView.shortDayLabel`: Today / Tomorrow / "Aug 23") is the only thing on screen saying where a new event lands; it renders **collapsed and disabled** while `selectedDay` is null. Colour is `appearance.accentOr(colorScheme.primary)` with the foreground picked by `ThemeData.estimateBrightnessForColor` — the same guard `CalendarDayCell._onAccent` uses, because a user-picked accent makes `onPrimary` wrong. The collapse rides a **`ValueNotifier` on `_CalendarViewState`, never `setState`**: a page-level rebuild per scroll tick would dirty the 42-cell grid and the whole panel, defeating `sameGridInputs`/`samePanelInputs`. The page's `NotificationListener<UserScrollNotification>` delegates to the pure `fabExtendedFor`, which **ignores horizontal scrollables** — the agenda's summary-chip row and the timeline's hour track scroll sideways and hide nothing.
- Navigation: `AppNavigator.toCalendar` stays a normal `push` (previous page remains on the stack). Calendar options live on `CalendarSettingsPage` (gear in the calendar app bar), never on `ControlsSettingsPage`.
- No generic `AppLocalizations.byKey` — pick localized strings via sealed `switch` on the enum/rule type.
- **Priorities read P1..P5 — 1 is highest** (since v18). Display (icon + label) comes only from `EventPriorities` (`lib/constants/event_priorities.dart`); ranking sites map `event.priority - kMinEventPriority` into the 0-is-top bar/summary band and sort ascending via `EventAgenda.compareWithinDay` — the **single same-day comparator** (the day panel's `EventSummaryProvider` emits through it; `DaySummaryResolver.resolve` is a stable sort so that order survives). Never reintroduce a numeric +/- stepper for priority.
- The bottom panel (`CalendarBottomPanel`) owns panel mode + agenda filters **below the page** so agenda keystrokes never rebuild the grid; keep new panel-local state there, not on `CalendarPage`. Agenda scans live in `EventAgenda` (pure, range clamped to 366 days) — never inside `eventLoader`, never in the bloc. Agenda filter persistence: `UpcomingAgendaFilters` ↔ `SettingsService` (empty priority set = "all"; query debounced + flushed on dispose; elapsed custom ranges dropped on load). **The upcoming window starts on today unless `followSelectedDay` is on** (default off, 2026-08-22 redesign). The anchor is **panel-owned state** (`_CalendarBottomPanelState._agendaAnchor` → `UpcomingAgendaView.anchorDay`), *not* `selectedDay`: `_syncAnchor` returns it to today while following is off, adopts the selection when resolving from scratch, and **never** re-anchors on a `CalendarSelectionSource.agendaRow` selection — a row tap must not truncate the list it was tapped in. `SelectCalendarDay` carries a required `CalendarSelectionSource` (`grid` / `agendaRow` / `navigation`); `CalendarPageLoaded.selectionSource` is in `props` but excluded from **both** `sameGridInputs` and `samePanelInputs` (nothing renders from it). A custom range overrides the anchor, and the rescan is guarded (`!hasCustomRange && anchor moved`) so a pinned range ignores anchor moves. The anchor is **not** persisted (reopens on today); the header's `from <date>` chip resets it. The Custom chip is an `InputChip` whose `onDeleted` clears the range back to the anchored preset — only while a range is active. Leave the three surviving `now()` reads alone (picker initial range, Today/Tomorrow row headers, `withoutElapsedRange`). **Perf (2026-08 anchor regression fix):** the panel `BlocBuilder` gates on `CalendarPageLoaded.samePanelInputs` (every input **except** `focusedDay`/`format`) and `_onChangeFocusedDay` has a no-op guard, so grid month-paging no longer rebuilds the panel or re-runs the scan; a query-only change debounces the rescan ~200 ms while an anchor rescan is synchronous and scrolls the agenda to top; the scan prunes candidates by span and buckets one-time events (exempting `SpecificDatesRecurrence`). Agenda row formatters (`DateFormat.Hm`/`.E`/`.MMMMEEEEd`/`.MMMd`) are cached per locale and `dayHeaderLabel` takes `today` as a parameter — never reintroduce a per-row `DateFormat(...)` or `DateTime.now()`. **Agenda layers (2026-08):** events carry one mutually-exclusive `AgendaEventType` (all/recurring/oneTime/**none**; `none` = holidays/fasting only, i.e. "holidays without events"), applied in `occurrencesInRange`'s candidate pre-filter (`recurring` = `rule is! OneTimeRecurrence`, so specific-dates counts as recurring); holidays + fasting are independent day-annotation toggles interleaved by `buildAgendaRows`' three-cursor merge (`EventAgenda.fastingDaysInRange` reuses `FastingSummaryProvider`). The fasting chip is hidden unless `FastingCalendar.isEnabled`; the priority row hides when eventType is `none`; both annotation scans respect the query. **Category allowlist (2026-08):** `UpcomingAgendaFilters.categoryIds` (empty = all, sorted-CSV codec like `priorities`) narrows events in `occurrencesInRange`'s candidate pre-filter **on top of** the inherited `hiddenCategoryIds` (both apply); it is a chip section inside the filters sheet, with an "All categories" reset. A stale allowlisted id (deleted category) is harmless. **Collapse recurring (2026-08):** `UpcomingAgendaFilters.collapseRecurring` (off by default) applies a **post-filter** in `occurrencesInRange` — two passes: tally per recurring id, then keep the first-seen occurrence carrying that tally as `EventOccurrence.occurrenceCountInWindow` (rendered as a "N× in window" badge); one-time events untouched — so `occursOn` counts stay put. Post-filter, never a scan short-circuit (that would break the occursOn-budget/anchor tests). **Event presentation (2026-08-23):** `UpcomingAgendaFilters.eventDisplay` — an `AgendaEventDisplay` of `everyOccurrence`/`perEvent`/`summary`, default **`everyOccurrence`** — replaced the `collapseRecurring` bool (three mutually exclusive presentations; a second flag would encode "collapse *and* summarize"). Persisted under `calendar_upcoming_event_display` with the same **read-time** fallback shape as the fasting key (`collapse_recurring` `true` → `perEvent`, `false` → `everyOccurrence`, never rewritten). Condensing events is **opt-in**: the default is the rows that always shipped. `summary` is one card per **category**, built by `EventAgenda.categorySummariesOf` — a **post-pass over the scan's own output**, so it costs **zero `occursOn` calls** and can only describe occurrences the scan produced; the scan runs uncollapsed in that mode because the card prints distinct events *and* their occurrence tally. `AgendaEventSummaryRow` is never an `AgendaEntryRow`, and `buildAgendaRows` walks an **empty occurrence cursor** in summary mode — the cards fold the same list, so keeping the rows would show everything twice. **Summary cards sort on `(priority, insertion index)`: `List.sort` is not stable in Dart** and cards share bands (event categories all at 0, fasting traditions all at 160), so a bare priority sort reshuffles identical input between rebuilds. **The drill-down edits:** `AgendaDayListEntry.onEdit` is optional (event rows set it; a holiday or fasting day has nothing to open), and the sheet **resolves an intent rather than running it** — `({DateTime? focusDay, VoidCallback? edit})` — so the editor opens after the sheet closes instead of stacked on it, matching `EventDetailSheet`.
 **Fasting presentation (2026-08-23):** `UpcomingAgendaFilters.fastingDisplay` — an `AgendaFastingDisplay` of `everyDay` / `periods` / `summary`, default **`periods`** — replaced the `collapseFasting` bool; it is a `SegmentedButton` in the sheet's Display section, shown only when `FastingCalendar.isEnabled`, and is persisted by name under `calendar_upcoming_fasting_display` with a **read-time** fallback to the retired `calendar_upcoming_collapse_fasting` bool when the new key is absent (`true` → `periods`, `false` → `everyDay`, never written again — no migration pass). It stays out of `restrictiveFilterCount` and the summary chips for the same reason `collapseRecurring` does. **`periods`** is structurally *different* from collapse-recurring: fasting days never enter the event scan and a fast is a **run of one period**, not a repeated id. `EventAgenda.fastingRunsInRange` groups in-window days **per (tradition, period)**, never by the boolean `isFastingDay`: only span periods (`greatLent`, `apostlesFast`, `dormitionFast`, `nativityFast`, `cheesefareWeek`, `lent`, `advent`, `ramadan`) bridge a gap of ≤ 7 days — so a Wed/Fri-sparsified Lent stays one run — while every other period, the year-round weekly fasts included, keeps strict contiguity (bridging those would fuse the window into one meaningless span). Each run's edges are walked outward past the window under the same gap rule (capped at `maxRangeDays` *steps* per direction, through the memoized `FastingCalendar.on` — never `occursOn`) so a clipped period reports its true extent, and `FastingRun.dayCount` counts **marked** days, not the distance between the edges. `buildAgendaRows` emits one row per run on its first in-window day — consuming **every** run that shares that day and taking the provider entry keyed `fasting:<tradition>` — swapping only the subtitle for the span ("Nov 15 – Dec 24 · 40 days") while leaving `FastingSummaryProvider` — shared with the day panel — untouched. A run of one marked day keeps its regime subtitle. **`summary`** is one card for the whole window **per enabled tradition** (never per fast — Lent plus the weekly rule in one window would be right back at several cards): `EventAgenda.fastingSummariesInRange` walks the window once into one `FastingSummary` per tradition (weekday set, first/last marked day, marked-day count, distinct span periods in first-seen order), ordered by `FastingTradition` declaration order and **never calling `occursOn`**. Its numbers are **window-scoped** — a run reports a period's true extent because it *is* the period, while a summary describes "fasting in this window", and claiming days outside it would make the card disagree with the list it summarizes. The cards are emitted **before the first month/day header** as `AgendaFastingSummaryRow` — deliberately *not* `AgendaEntryRow`, so `_entryCount` (and the panel's "N entries") excludes them with no extra logic. The entry is synthesized in the agenda layer from the tradition's `FastingTraditionStyle` (title: `titleOverride` > the window's single named fast > tradition name; subtitle: weekday pattern · span · `upcomingFastingSpanDays`, where the span is the exact `rangeLabel` up to 62 days and `monthRangeLabel` beyond it); tapping focuses `summary.first`. The query filter is passed into the run walk **and** the summary scan so neither can claim days the search excluded. **Holiday presentation (2026-08-23):** `UpcomingAgendaFilters.holidayDisplay` — an `AgendaHolidayDisplay` of `everyDay` / `summary`, default **`everyDay`** — is the two-value twin (no `periods`: a holiday is one day, with no run to collapse into), a second `SegmentedButton` under the fasting one and **ungated** because holidays are always available. Persisted under `calendar_upcoming_holiday_display`; a new axis, so no legacy fallback and no migration. It needs **no scan**: `_recomputeHolidays` already produced the query-filtered ascending list, so `summary` is a pure re-render and `holidayDisplay` in the view's `_rowsFor` memo key is the entire mechanism — `didUpdateWidget` gets no branch, and flipping it must stay at **zero `occursOn` calls**. In `summary` mode `buildAgendaRows` walks an **empty** holiday cursor (no header, no entry row for a holiday-only day) and emits one `AgendaHolidaySummaryRow` from the same list, mirroring `PublicHolidaySummaryProvider`'s icon/colour/key/priority. **Summary cards sort by `DaySummaryEntry.priority`, never a hardcoded order** — holiday 150 vs fasting's default 160, so the holiday card leads unless the user placed a tradition `first` (10), matching the day panel. **The drill-down (`agenda_day_list_sheet.dart`)** is shared by both cards: the card's right-hand `IconButton` (`onShowAll`, `upcomingShowAllDays`) opens `AgendaDayListSheet`, which pops the tapped day; the view routes it through `onDaySelected`, already tagged `agendaRow`, so picking a day never re-anchors the list. Hard rules: **the sheet's scope is the card's scope** (the agenda window) — reaching further would contradict the number just tapped, and it is why `FastingSummary` carries `days` (re-walking would drop the scan's `dayFilter`; `days.length` **is** `dayCount`); **the sheet reads no facade and localizes nothing**, it renders a pre-resolved `AgendaDayList` built in the agenda layer **on press**, never per frame; holiday rows lead with the **name** and fasting rows with the **date**, both dated through `AgendaListView.dayHeaderLabel` and fasting subtitles reusing `FastingSummaryProvider` filtered to the tradition.


**Agenda filter IA (2026-08-22):** all filter chrome lives in `agenda_filters_sheet.dart` (Period / Show / Priority / Categories / Display), which edits a local draft and returns it on Apply — never live-applies, and its Reset preserves `query`. Inline the panel keeps only the search field, a `Badge.count` on the tune button, a row of removable **summary chips**, and the header line. Summary chips (and the badge) come from the single `UpcomingAgendaFilters.restrictiveFilterCount` definition and cover **only restrictions** — window, event type, priorities, categories. Layer toggles and collapse switches are deliberately excluded: they add or condense rows, never hide them. `filtersExpanded` and its settings key are retired. Results gained `AgendaMonthHeaderRow` (only when the rows span ≥ 2 months); **every entry row stays an `_AgendaCard`** — the roomier `Card` + `ListTile` + `CircleAvatar` layout, holidays and fasting included (`trailing: null`). A denser card interior and slim annotation rows were both tried on 2026-08-22 and both reverted; do not restyle these rows without asking.
- Agenda text search folds through the note search's `normalizeForSearch` (case + diacritics) — never `toLowerCase().contains`.
- `.ics` export goes `IcsSerializer` → `ImportExportService.exportCalendar` → `ExportCalendarRequested`; do not add an `ics` `ExportFormat` variant (it would appear in note-format pickers).

## Descriptions, pickers, detail sheet (v19 surfaces)

- Event descriptions are **raw markdown source**, rendered on demand — never pre-rendered, never a derived column. Rows (`DaySummaryPanel`, `AgendaListView` — both fed by `EventSummaryProvider`, keep it that way) use `MarkdownInlineText`: same `LineBasedMarkdownBuilder`, `flattenHeadings: true`, blank lines dropped, ≤3 lines, clamped to 2 with an ellipsis. **All tap callbacks must stay null** there — that is what stops the builder allocating `TapGestureRecognizer`s and makes the memo-cached spans inert. Full-fidelity `SimpleMarkdownPreview` renders the detail sheet (and the editor's fallback preview).
- **The editor sheet's description is a real re_editor surface**, not a `TextField`: `ListAwarePasteController` → `CodeLineEditingController(spanBuilder:)` → a sheet-owned `MarkdownEditorSpanBuilder`, hosted in `ModernEditorWrapper` (`showScrollIndicator: false`). Never fork the span builder or add a second live-rendering path — reuse is the whole point. Honour the global live-markdown-rendering setting, apply a late-resolving setting with `configureColors` + `forceRepaint()` and **never by remounting the editor** (that crashes re_editor's controller-delegate handoff mid-init — the same rule the note editor documents for money config). The box stays height-bounded (a `CodeEditor` owns its own scroller and cannot go unbounded inside the sheet's `SingleChildScrollView`), and focus scroll-into-view is manual because a `CodeEditor` is not an `EditableText`.
- The **markdown bar** shows on description focus, below the sheet's scroll view so the form never shifts: `splitEnabled: false`, no settings/reorder, undo+redo+paste only, shortcuts from the app-wide `MarkdownBarBloc` active profile with **counter-bound shortcuts filtered out** (`{c1}` resolves against a note context an event does not have — never wire it to the global counters). Ghost / colour-slot shortcuts go through `MarkdownShortcutInserter` (`lib/controllers/`), shared with the note editor; do not re-inline them.
- **Description length is `SettingsKeys.eventDescriptionLimit`** (default 2000, slider 500–10000 step 500, Calendar Settings → Events, in reset-to-defaults), enforced by **disabling Save** — never by truncation, and never re-hardcode a `maxLength`. Keep the grandfather rule (`_initialDescriptionLength`): a description is always saveable at a length it already had, so lowering the limit blocks growth instead of locking the user out of an existing event. Keep the clamps in the getter *and* setter. Counter/Save track the controller via `ListenableBuilder` — do not add a keystroke-wide `setState` to this sheet.
- **Per-occurrence descriptions (v24) are opted into per event since v28** — `CalendarEvent.perOccurrenceDescriptions`, an editor switch above the description field. The v24 global setting and its `SettingsKeys` constant are **gone**; the v28 migration read the stored key one last time (frozen literal `'event_per_occurrence_descriptions'`) to flip every live repeating event for a global-ON user. The event's `description` is the **template**; `calendar_event_occurrences` (PK `{event_id, day}`) holds **only user deltas**, materialised copy-on-write on the first edit/tick. Hard rules:
  - **`OccurrenceDescriptions.descriptionFor(event, day)` is the one entry point.** Never resolve a day's description any other way.
  - **The gate is `rule is OneTimeRecurrence`, nothing else** — so `SpecificDatesRecurrence` participates. Never gate on the editor's `_RepeatMode` (it files specific-dates under `oneTime`).
  - **A present row always wins, including when empty.** `''` is a deliberately blanked day; only a missing row falls back. "Reset this day" **tombstones** the row (since v28) — never write `''` to mean reset.
  - **Never delete rows to "clean up".** Disabling the setting, changing the rule, or moving `endDate` all leave rows dormant; only deleting the event cascades (one transaction in `CalendarEventService`).
  - **`EventAgenda._matches` is in the pre-filter, before the day is known** — keep it a *superset* (title OR template OR any override) and narrow per day with `_matchesOnDay` inside the scan. Superset-only emits every occurrence of an event whose hit lives on one day.
  - **Occurrence writes must not call `_invalidateDayCache()`** (that cache answers "which events occur on a day"; text is not an input) and must bump `occurrenceRevision` — the state is `Equatable`, so a no-op copy is dropped, and `AgendaListView`'s identity memo would serve stale text. `UpcomingAgendaView` forwards the revision but must never rescan on it.
  - **Editor scope control: one controller, swap only its text**, inactive scope buffered in a `String`. A second controller orphans `ModernEditorWrapper`'s listener (bound in `initState`, no `didUpdateWidget`), the span builder and the search controller. **`clearHistory()` after every swap** or undo pulls the other scope's text into the active one. Each scope keeps its own length budget + grandfather. Flipping to one-time parks the day text unwritten — never merge it into the template. The sheet reports `(occurrenceDay, occurrenceDescription)`; the page dispatches.
  - **Never put a `ListenableBuilder` directly on a re_editor controller.** `_CodeEditorState.initState` wraps it in its own delegate and the `delegate =` setter calls `notifyListeners()` **synchronously while the framework is building**, so any builder mounted above the editor throws "setState() called during build" on the first frame. The sheet relays through `_descriptionRevision` (a `ValueNotifier<int>` that defers a mid-frame notification to a post-frame callback); route new listeners through it.
  - **Service copies `PublicHolidayService`, not `FastingCalendar`**: read the flag at `getInstance()` and publish it with the data, or a cold start renders templates for one frame then flips every row. `reset()` clears the singleton **and** the facade.
- **Skips (v30) are not presence (v26).** A *missed* occurrence still occurs — rendering only, never invalidate the day cache, rides `occurrenceRevision`. A *skipped* occurrence does not exist — `occursOn` returns false, the day cache **must** be invalidated, and it rides the separate **`membershipRevision`**. Hard rules:
  - **`CalendarEvent.occursOn` is the only place the skip filter lives.** Every surface already goes through it, so a skip reaches the grid, the day panel, the agenda, the timeline, `monthNetFor` and the date pickers for free. Never add a second skip check to a render path.
  - **This is the deliberate inverse of the hidden-category filter** ("render-time only, forever"). Hiding a category changes what you look at; cancelling an occurrence changes what is there. Keep both rules stated together whenever either is documented.
  - **The gate is `rule is OneTimeRecurrence`, nothing else** (`EventSkips.appliesTo`) — no per-event opt-in, unlike presence. The gate is also what stops a stale row from ever hiding a one-time event.
  - **Never route a skip through `occurrenceRevision`.** `UpcomingAgendaView` forwards that revision into its row memo but never rescans on it; a skip must rescan, so it is `membershipRevision` that appears in the widget's `didUpdateWidget` scan test.
  - **Counts must not change.** `RecurrenceFormatter.countLabel` is elapsed-*period* math from `startDate`, so a cancelled Week 3 leaves Week 4 as Week 4 — the same decision presence took.
  - **`.ics` needs explicit handling** — `IcsSerializer` queries `event.rule` directly (to drop `retroactive`), bypassing the model filter. Three sites: `_firstOccurrenceOf`, `_exceptionDates` (EXDATE only for rules that emit an `RRULE`, via `_hasRrule`), `_additionalDates` (filter, do not exclude).
  - **`markSkipped` clears that day's absence mark.** An occurrence that does not exist cannot have been missed.
- **Event templates (v29)** are a separate entity from categories — a category is a taxonomy, a template is a prefilled event, and a user wants several templates inside one category. Hard rules:
  - **`RecurrenceCodec` is the one rule encoding.** Never hand-write a second `rule_kind`/`rule_payload` switch; `CalendarEventService` delegates to it too.
  - **Two entry points, and only two**: long-press a day cell (immediate create + Undo) and "Save as template" at the bottom of the editor's scroll body. The editor's inline header stays `close | title | Save` — a secondary whole-form action goes at the bottom, beside Delete.
  - **`buildEvent` clears the repeat-only flags for a one-time rule**, mirroring the editor's save guards, so a template captured while recurring cannot stamp out an event carrying flags its rule cannot honour.
  - Backup strand rule is keyed to **categories**, not events: an absent `eventTemplates` key alongside a present `calendarCategories` clears the table.
- **Day-cell tints go through `CellTintProvider`/`CellTintResolver`**, never a new field on `CalendarDayCell`. Same purity contract as `DayBarProvider` — 42 cells × every rebuild, static probes only. Exactly one event supplies a day's wash (top by `EventAgenda.compareWithinDay`); alpha encodes priority and the ramp must stay monotonic; two washes are never stacked (winner washes, runner-up gets the edge stripe under the `both` setting). The cell stays a dumb painter receiving pre-resolved colours.
- **`CalendarDatePickerSheet.pickMulti` collapses an empty result to `null` by default** so the one-time date set always keeps at least one date. Pass `allowEmpty: true` only where empty is a real state (the skipped-days editor, where clearing restores every occurrence).
- **`CalendarBloc.monthNetFor` is memoized and paired with `NoteMoneyLedgerService.revision`.** The ledger's per-note change stream rewrites entries outside every handler that invalidates the day cache, so the event set alone cannot keep a cached sum honest. Never inline that scan into `headerTitleBuilder` again.
- **Checkbox toggling is gated on unambiguous meaning.** In the editor sheet it is free (persisted on Save). In the read-only `EventDetailSheet` it needs either `event.rule is OneTimeRecurrence` (the tick edits the event) or per-occurrence descriptions on (the tick materialises `widget.day` and leaves every other day alone). With the setting off, a repeating event still keeps inert boxes — one shared string would read as ticked on every occurrence. Shared-scope toggles coalesce into one `UpdateCalendarEvent` (600 ms; flushed on close, before routing to edit, and in `dispose`); per-occurrence toggles go through `onOccurrenceChanged`, which is **deliberately a separate callback** — `onEventChanged` feeds `initialEvent` into the editor, so routing a day's text through it would hand the editor a template field holding one occurrence's text. Render and rewrite the **same trimmed string** — the builder reports absolute source offsets. `SimpleMarkdownPreview.onCheckboxTap` must stay null on read-only surfaces or they start allocating recognizers.
- **Money is always disabled in descriptions** (`MoneyDisplayConfig.disabled`) — the ledger is per note, so a `$+ 50` row would compute a balance from nothing.
- The navigable date domain is **`CalendarBounds` (1900–2100, `lib/constants/calendar_bounds.dart`)**, shared by the grid, both day pickers and the month/year wheel — never re-derive a per-field window (a ±20-year slide around the event date made birth years unreachable). The 1900 floor is the computus domain floor: `LiturgicalComputus.julianToGregorianOffset` is only correct from 1900 (13-day lag) and degrades to a flat 13 below it. Width is free — lazy month pages, lazy wheel rows, memoized per-year fasting maps, and `PublicHolidays.holidayOn` falling back to a static fixed-date map outside the seeded window (current year + 5).
- Date entry goes through `CalendarDatePickerSheet.pickSingle` / `.pickMulti` — never `showDatePicker`. It renders with `CalendarDayCell`/`CalendarDayBars` and takes an optional `dayLoad` fed by `CalendarBloc.eventsForDay` (memoized O(1) — never a fresh query). `pickMulti` is intentionally semantics-free (set in, set out) so it can later serve skip-dates; it never returns empty. `_setOneTimeDates` stays the single funnel that re-derives the anchor. Its enum is `CalendarDatePickerMode`, **not** `DatePickerMode` — material.dart exports that name and a collision makes any file importing both fail.
- `CalendarAppearance` and the colour palette are **passed down from `CalendarPage`** (page → editor sheet → picker; page → bottom panel → rows), never re-read in the leaf. Resolving `getCalendarAppearance()` after first frame visibly re-lays-out the grid; the page also already refreshes both on settings return, so a leaf-local load would go stale. (It is **one** statement over 11 keys since the bulk-read change — it was eleven sequential reads before, never the "seven" older comments claimed.)
- Day-panel **and timeline** row taps open the read-only `EventDetailSheet` (`onShowEvent`), which returns an `EventDetailAction`; the page routes edit/open-note. Both render the same day, so they must agree. The agenda keeps tap = jump-to-day, pencil = edit.

## Recurrence semantics (keep consistent)

One-time = start only. Daily/weekly/monthly/yearly carry `interval` (weekly uses a fixed Monday-aligned week grid, `_weekEpoch = 2000-01-03`); short months and non-leap Feb 29 are silently skipped. Workdays = Mon–Fri AND not a public holiday (semantic — do not relax). Weekends = Sat–Sun. Holidays-only = `PublicHolidays.isHoliday(day)`. `endDate` is enforced at the model layer in `occursOn`.

Every rule guards `day.isBefore(start)` first **unless the event is `retroactive`** (v19): `occursOn(day, start, {retroactive})` and each guard is the shared `_beforeStart(day, start, retroactive)`. The flag lives on `CalendarEvent`, is written as `recurring && _retroactive` (an exact-membership rule can never carry it — `supportsRetroactive` is false for one-time/specific-dates, which is what hides the editor chips), and `endDate` still clamps the forward side. **Never** implement it by back-projecting the anchor instead: rebuilding a day-31 or Feb-29 `start` in a shorter month rolls over and corrupts the phase. The guard is safe because Dart's `%` is Euclidean and `_weekIndex` floors toward −∞. `.ics` export queries the rules *without* the flag on purpose (RFC 5545 has no pre-`DTSTART` occurrences).
