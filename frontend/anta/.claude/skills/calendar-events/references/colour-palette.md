## Calendar Colour Palette (unified 2026-09-02)
One palette and one picker behind every colour choice in the calendar. Not to be confused with `MarkdownColorPalette` above — that is name→colour pairs for `{name:text}` syntax and shares nothing with this.

- **Two halves, one list.** `CalendarColors.swatchPalette` stays const and is **never stored**, so editing it reaches existing installs; the user's own swatches live in `SettingsKeys.calendarCustomColors` (comma-separated ARGB, insertion order, capped at `maxCustomCalendarColors` = 24). `CalendarPalette` (lib/constants/calendar_palette.dart) is the synchronous facade — `defaults` / `custom` / `all` / `isDefault` / `contains` — following the `CalendarCategories` pattern, plus a `ValueNotifier<int> listenable` that is both the revision counter and the repaint signal, which is what makes a colour added inside a sheet appear in every picker already on screen with no caller plumbing a reload.
- **`CalendarPaletteService` holds no database reference** — it writes through `SettingsService`, which is what keeps it correct across a database switch (the `NavigationHistoryService` shape), serializes every mutation onto one chain, and republishes the facade after each. `add`/`update`/`remove`/`resetToDefaults` return whether anything changed so a refusal (duplicate, built-in, full) can be explained rather than swallowed.
- **Deleting a swatch removes it from the palette, never from what is painted with it.** Events, categories, templates and fasting styles store raw ARGB ints; the deleted colour keeps rendering where it was chosen and the picker still shows it, selected, as an orphan dot.
- `recent_event_colors` is **retired**: `_foldLegacyRecents` reads it once, folds the non-built-ins into the palette, and clears the row — so the fold cannot resurrect a colour the user then deleted.
- **`ColorSwatchPicker` (lib/widgets/color_swatch_picker.dart) is the only colour row.** It replaced five private `_ColorDot` clones and five copies of the swatch loop across the accent row, category editor, fasting style sheet, template editor and event editor (the last two now through `EventLookSheet`). Since Tier 3 (2026-10-03) every sheet that embeds it — the Look sheet, the category editor, the fasting style sheet — draws it in a `FormSwatchRow` with one geometry (`FormMetrics.swatchSpacing`, `collapsible: false`, every colour shown); only the appearance page's accent row keeps its own spacing and its collapse. An optional `ColorSwatchDefault` describes what "no colour of my own" means on that surface, and its dot always draws a glyph (`format_color_reset_rounded` when the caller passes none) so it is never mistaken for a swatch of the same colour; the picker dot **adds what it picks to the palette permanently**; a long press on a *custom* swatch opens a popup of `FormMenuItemRow`s hung from the dot (Edit color · Delete color · Manage colors, at the preset ⋮'s floor), whose delete asks first like the palette's; the strip drops the focus before every sheet and menu it opens and raises its two refusals (palette full, already in the palette) through `OverlaySnackbar` at the error duration, over whichever sheet embeds it; the default, add and manage dots carry `swatch-default` / `-add` / `-manage`; `onChanged` reports the result, never which affordance produced it. `ColorPaletteSheet` is the management surface (add / recolour / delete / reorder / *Reset colors*), a live-applying sub-sheet like the other settings sheets, reached from any picker's manage dot or long-press menu and from the **Colors** row under the accent picker.
- Calendar settings' own *Reset to defaults* deliberately does **not** touch the palette — those swatches are shared with categories, templates and events, so a page-scoped reset must not delete them. The palette resets from its own sheet.
- The key rides the backup settings allow-list (beside `markdown_custom_colors`); `importFromJson` resets **and immediately re-initialises** the service after writing the settings map, the way it already resets `MarkdownBarService`, so an open picker repaints with the restored palette instead of the built-ins.
- **`ColorPickerSheet` (lib/widgets/color_picker_sheet.dart) replaced `ColorWheelDialog`** — same `show(context, {initialColor})` contract, used by the swatch picker, the palette sheet and `markdown_colors_page.dart`. Two geometries in one sheet — a saturation/brightness **square** (the default) plus a hue **`Slider`** over a spectrum track shape, and the hue/saturation **wheel** as an opt-in (see the bullet below): on a wheel hue and saturation are polar-coupled (dragging toward "less saturated" drifts the hue) and full saturation is a thin rim, while a real `Slider` also buys keyboard arrows, focus and slider semantics for free. It is a **sheet**, so it rises with the keyboard the hex field summons and no longer needs the `IntrinsicWidth`/`LayoutBuilder` workaround the dialog did. Since Tier 3 (2026-10-03) it wears the sub-sheet's chrome over an untouched picking body: ✕ · Custom color · Select in the header (the Cancel/Select bar gone), then the Square / Wheel chips → the geometry → its slider → (before · after · hex · copy); the before/after pair exists only when replacing a colour, its dots on 48 dp targets, and the "current" dot reverts; "Copied" is raised over the sheet through `OverlaySnackbar`. **The hex field's `maxLength` is 9 on purpose** — the length formatter rejects an over-long paste wholesale with no keystroke and no explanation, so it must be long enough to accept a pasted 8-digit ARGB in order to refuse it with a reason. **No alpha** on any path (six digits in, `0xFF` out): every calendar surface applies its own `withValues(alpha:)`, so a user opacity would multiply into those.
- **Two framework traps the picker/palette tests caught**: a `Semantics` node with `onIncrease` must declare `increasedValue` **and** `decreasedValue` or it asserts every frame; and a `Tooltip` on a drag handle adds a long-press recognizer that beats the immediate drag listener in the arena — hold still, then drag, and the reorder silently dies. Drag handles carry `Semantics(label:)` instead, which is why the app's reorderable lists all have bare handles.
- **The wheel is back as an opt-in second geometry (2026-09-02)**, square still the default: one chip row at the top of the body (Square / Wheel, `color-mode-square` / `-wheel`, since Tier 3 — an icon-only `SegmentedButton` trailing the title row before) switches `ColorPickerMode` (lib/models), persisted in `SettingsKeys.colorPickerMode` and carried by the backup allow-list. `show()` resolves the mode **before** presenting so the sheet can never open square and flip a frame later; both the read and the write are totally guarded, since no settings failure should turn a colour pick into a sheet that will not open. The wheel owns hue, so **its slider carries brightness** (track `black → HSV(hue,sat,1)`, percent formatter) while the square's carries hue (spectrum track, degree formatter) — one `_GradientTrackShape(colors)` serves both, with identical metrics so the row cannot shift. `_GeometryBox` gives both shapes **one height** (the square's `(width/1.5).clamp(140,240)`, disc on the short side, centred), so a switch moves nothing below it — pinned by comparing rects in the test. Only the geometry cross-fades (150 ms, stacking `layoutBuilder` so no size interpolates); the slider swaps instantly, because animating a control someone is reaching for is disorientation. Wheel gestures clamp past the rim (an overshooting finger still points at a hue) and leave the hue alone within half a pixel of the centre (`atan2` is undefined there; a snap to 0° would jump the track and the hex). Its semantic increase/decrease step **saturation, not hue** — hue wraps, and 359 → 0 reads as broken.
- **Invariants the 2026-09-02 review pinned down.** `CalendarPaletteService` distinguishes "unknown" from "empty": a failed read sets `_loaded = false`, every mutation refuses while it is false and `_commit` asserts on it, because `_commit` rewrites the whole settings row from memory and the next colour picked would otherwise persist an empty palette over the user's swatches (the load and the legacy fold are guarded separately, so a failing fold cannot discard a successful read; and the fold writes the destination *before* clearing the source). `getInstance()` holds an in-flight future — two racing first callers each publishing a service means lost colours here, not a merely stale cache, since each one rewrites the full row. **No widget may hold the service**: a backup restore and a database switch both replace it, and writes through a held instance target a closed database or overwrite the restored palette — so the picker row and the management sheet resolve it per use, and `DatabaseLifecycle.registerResetHandler` is idempotent so a restore's reset-and-re-init cannot stack duplicates. `CalendarPalette.updateCache` publishes an optional `(previous, next)` as `lastRecolor` for that one revision, which is how a picker follows a swatch recoloured in the management sheet instead of stranding the event on a shade the palette no longer offers.
- **`Slider` resolves `widget.thumbColor ?? widget.activeColor ?? theme.thumbColor`** — passing an `activeColor` alongside a themed thumb colour silently shadows it, which is what painted the picker's thumb in the app accent over its own spectrum track. Tint the thumb on the widget. Two more picker rules: the hex field is validated by an anchored `^#?[0-9a-fA-F]{6}$` (stripping a `#` and trusting `int.tryParse` accepts a sign, so `-12345` applied a colour), and typing an achromatic value keeps the hue in force, since `HSVColor.fromColor` reports hue 0 for any grey and would swing the wheel to red. A geometry drag takes focus from the hex field on `onPanStart` as well as `onTapDown` — the latter only fires past the 100 ms tap deadline, so a quick flick left the field mirroring a stale colour.
- **`ColorSwatchDot` lays out at 48 with a 44 circle centred in it** (`FormMetrics.swatchDiameter`; a 44 target is under Material's floor, and a colour row is a field of small round things where a near-miss picks the wrong colour) — the bare, untappable dot too since Tier 3 (the palette's built-ins, each a plain node named by its hex) — every swatch carries its hex as an accessible name, and the per-call `dotSize` is gone so every surface matches. Where `collapsible` (only the appearance page's row since Tier 3; never inside a sheet) the row **measures its width and collapses to three runs** with a "show the rest" dot when the palette outgrows them — 18 built-ins plus 24 custom is nine runs — always keeping the selected swatch visible, and never collapsing when everything fits.
- The palette sheet's custom rows are a **`SliverReorderableList` inside one `CustomScrollView`** — itself shrink-wrapped under the sub-sheet's clamp, so the sheet stays content-tall while the list is still the one scrollable (never a `shrinkWrap` list nested in another scroll view — that kills drag auto-scroll) — persisted by `CalendarPaletteService.move`. Since Tier 3 each row is a `FormRowShell` over `FormPickerRow(handle:, leading:)` — drag handle, swatch, hex, a delete button as the second target — that recolours on a tap and lifts on a long press anywhere; one Add color action row closes the run, disabled in place at the cap; the built-ins are a read-only `FormSwatchRow` strip and Reset colors the last, destructive row (dimmed while nothing is custom, `colorPaletteResetDone` once it has run). Order is the CSV order, so reordering is not a format change and cannot breach the cap; the YOUR COLORS label carries an "n of 24" count (`FormSectionLabel(trailing:)`), since the cap used to be invisible until it refused an add.
