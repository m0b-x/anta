## Data And Persistence Rules
- The database uses Drift with a singleton active database and background `LazyDatabase` connection.
- Folder, note, content chunk, calendar-event, calendar-event-occurrence, calendar-event-absence, calendar-event-template (v29), calendar-event-skip (v30) and vocabulary/vocabulary-item (v32) tables include CRDT-style metadata for future sync: `hlcTimestamp`, `deviceId`, `version`, `isDeleted`, and optional `deletedAt` where supported. On `calendar_events` (v27), `calendar_event_occurrences` (v28) and, since v43 (2026-10-23, `docs/cloud-sync-readiness-roadmap.md` R2), `calendar_categories`, `counters` and `counter_values` `hlc_timestamp`/`device_id` carry `DEFAULT ''` (the v29/v30/v32 tables were born with the block and carry none) — an `ALTER TABLE` on a populated table demands a default; the migrations backfilled real identity and every write path stamps, so `''` after that means something skipped the DAO. v43 also added `owner_id TEXT NULL` to all eighteen synced tables (NULL = not yet signed in; nothing reads it before Phase 02), the `sync_outbox` change-feed table (written only by the R3 write helper, never by hand), partial `is_deleted = 0` indexes on the three converted tables, and a repair that divides `deleted_at`/`updated_at` values above 10^12 by 1000 on folders and notes — the folder cascade had bound milliseconds into DateTime columns Drift stores as seconds. Deletes on counters and categories are tombstones from v43 on; built-in categories can only be hidden, never tombstoned.
- Notes store metadata separately from content. Content is chunked and may be compressed; avoid unnecessary full-content copies in hot editor paths.
- Reorder operations should be transactional and preserve user-defined positions.
- **A migration step is frozen at the shape it shipped with (fixed 2026-09-20).** A step must never call a definition that follows the *live* schema — a `DatabaseIndexes` helper, `m.createTable`, a DAO — once that definition can name something a **later** step introduces. v31 called `createCalendarDeltaIndexes()`, v37 widened that index to `(event_id, day, status)`, and from then on every upgrade from v30 or older died with `no such column: status`; v10 had the same trap with `is_deleted` (v27). The rule: the **newest** step that defines an index shares the helper with `createAllIndexes`; every **older** step that touches the same name spells its own frozen DDL, and the newer step drops and recreates. When you change an index or table shape, freeze the older callers in the same change.
- **Each migration step is atomic.** Drift does **not** wrap `onUpgrade` in a transaction and only writes `user_version` after the whole chain — so one failing step used to leave every earlier step applied under the old version, and the next launch re-ran them. `DatabaseMigrations.runMigrations` therefore runs each step in its own transaction together with `PRAGMA user_version = <step>`: a failure rolls that step back whole and the next launch resumes exactly there. Steps stay idempotent anyway (guard every `ALTER` with `PRAGMA table_info`), because databases half-upgraded by an older build exist; data steps that are their own inverse (v18's `6 - p`) additionally key off a marker the following step leaves behind. No statement in a step may need to run outside a transaction (`VACUUM`, `journal_mode`).
- `test/database/upgrade_chain_test.dart` is the guard for both rules: it takes a fresh database back to the oldest reconstructible shape (every table but the four original ones dropped, every later column dropped — derived, so a new table or column is covered without touching the test), walks it up one step at a time, compares columns and index SQL with a fresh install, re-runs the chain, and reopens a real v30 file through the production connection (`LazyDatabase` → `createInBackground` → `LoadingQueryInterceptor`).
- Search uses both SQLite/FTS and an app-level index; keep indexes in sync when notes are created, updated, deleted, or moved. **One normalization for all search surfaces**: `normalizeForSearch` / `searchTokens` / `tokenizeForSearch` in `lib/services/folder_search_service.dart` (diacritics map in `SearchConstants`, incl. Romanian comma-below ș/ț) are shared by the isolate bulk indexer, the incremental index, the query side, and the calendar agenda search — never reintroduce a local fold or tokenizer (the isolate once had its own map, it drifted, and bulk-indexed Romanian words became unfindable). `removeDiacritics` iterates **code units**, not one-character substrings, and consults `_diacriticsByCodeUnit` — which is **derived from `SearchConstants.diacriticsMap` by comprehension**, so it is a re-keying of the canonical table and not the second table the warning above forbids; every key is a single UTF-16 code unit, units `<= 0xBF` skip the lookup, and a string needing no fold returns itself unallocated. `searchTokens` keeps duplicates on purpose: the index counts them as real term frequency.
- **`SearchBloc` (`lib/bloc/search/`) owns search state, and nothing else does** (Slice 4, 2026-09-06). It holds the scope, the query, the phase (idle / quick / full), the recents shown while idle, the hits split into `titleHits` / `contentHits`, and a folder-id → path-segments map for the rows. It is page-scoped — built from `GetIt` and provided by whichever page hosts it, the way `CounterPerNotePage` does — never registered app-wide, so leaving the surface disposes the query with it. Two hosts since Slice 5: the browser owns one for the life of the page (created in `initState`, closed in `dispose`) and the standalone `SearchPage` route, which tag taps still use, builds its own. `OptimizedNoteBloc` has **no** search events or state any more: it fed the folder list at the same time, so a search replaced the very list the page underneath was rendering, and the browser had to reload itself on the way back from search. Do not add search back to it. `AppNavigator.toSearch` stays **unstamped** (no `NavDestination`): search is a query surface, not a place, and launch restore must never reopen someone's half-typed search. In-place search is not even a route — it is screen state on the browser, so opening and closing it leaves the recorded location stack untouched. The editor's search icon is unrelated and stays find-in-note. Two ordering guards, since `SearchQueryChanged` is the only debounced event and every other event (`SearchCleared` on an emptied field, `SearchSubmitted`, `SearchOpened`) is handled at once: `_generation` decides which *handler* may still emit after its await, and `_pendingQuery` (2026-09-07) decides which *event* may run at all — recorded in `onEvent`, ahead of the transformer, so a keystroke delivered 200 ms after a clear/submit/open is dropped rather than searched (backspacing "pr" to empty used to search "p" under a blank field). A scope change deliberately does not cancel the pending keystroke. Pinned in `test/bloc/search_bloc_test.dart` ("races between event types") and, for the phone gesture, `test/widgets/optimized_folder_content_page_test.dart`.
- **Folder search scope is recursive.** `SearchFilter.folderIds` is a whole subtree — `FolderStorageService.subtreeIds(folderId)` = `FolderDao.getAllDescendantIds` (the `WITH RECURSIVE` CTE) plus the folder itself — and `quickSearch` takes the same set. `null` searches everywhere; an **empty** set matches nothing, which is what a scope pointing at a deleted folder must do. Never reintroduce a single-`folderId` comparison: the folder row's count already includes descendants, so a non-recursive search made the row above and the results below disagree. `quickSearch` reads its page unscoped and filters in memory (the DAO can page by one folder id, not by a set), capped at 300 rows.
- **`search()` ranks before it loads.** Relevance comes off the in-memory index, so the hit set is scored, filtered, sorted and cut to `limit` *before* a single note body is read — `test/services/folder_search_service_limit_test.dart` guards it by counting `loadNoteContent` calls. It used to load the content of every hit and then discard all but `limit` after sorting, so one common word pulled the whole collection through memory to show ten rows.
- Counters use `noteId == ''` for global values in `counter_values`; per-note values use the real note id.
- Custom markdown shortcuts can bind up to two counters via `CustomMarkdownShortcut.counters` (`List<CounterBinding>`). Each binding has a `counterId` and a `CounterOp` (`increment` / `decrement`). The `{c1}` / `{c2}` tokens in `beforeText` / `afterText` / repeat wrapper text expand to the matching binding's post-mutation value at insertion time. Each token occurrence triggers exactly one mutation per repeat iteration. Token expansion runs through `ShortcutApplier` via the `CounterMutator` callback, which routes to `CounterBloc` (`IncrementCounter` / `DecrementCounter`) and respects the global vs per-note scope contract. The legacy `counterId` field is preserved for backwards compatibility — when `counters` is empty but `counterId` is set, `effectiveCounters` synthesises a single increment binding so applier logic stays uniform.
- `CustomMarkdownShortcut.category` is an optional free-text grouping label (`null`/empty = uncategorised). It is settings-only organisational metadata: it never affects toolbar order or rendering, has no separate persisted registry (the category set is derived from the shortcuts themselves), and is additive in the profile JSON, so older profiles and backups load unchanged.
- Settings are stored through `UserSettingsDao`, `SettingsService`, and `SettingsKeys`. Do not scatter raw string keys.
- **Settings pages are searchable through one matcher**: `lib/utils/settings_search.dart` (`SettingsQuery`, `matchSettingsEntry`, `matchesSettingsQuery`) rendered by `lib/widgets/settings_section_list.dart` (`SettingsEntry` / `SettingsSectionData` / `SettingsSectionList`). Never filter with a local `toLowerCase().contains()` — that is a second fold and it silently breaks `ro`/`de` (`evidentieri` must find `evidențieri`, `schriftgrosse` must find `Schriftgröße`). `FoldedText` exists because the shared fold is **not** length preserving (`ß`→`ss`, `æ`→`ae`), so highlight spans must be mapped back through its index table rather than applied to the source directly. Matching is deliberately exact-substring with multi-token AND and no fuzzy/ranking: rows keep their declaration order so sections and learned positions survive filtering. A page declares rows as `SettingsEntry`s whose `builder` receives the pre-highlighted title/description, so each row keeps its own widget type; hidden `keywords` (localized, comma-separated ARB strings) are matched but never rendered. **Sections can fold, opt-in (2026-09-01)**: a `SettingsSectionData.id` plus `SettingsSectionList.collapsedSections` + `onToggleSection` — a section without both stays permanently open, which is how the developer and sync pages are untouched. Three rules: a fold **may never swallow a search hit** (while the query is non-empty every surviving section renders open and loses its chevron, without touching the stored fold), a folded section **builds nothing below its header** (not `Offstage`, not `AnimatedCrossFade` — which builds both children and would keep a page's live preview and every slider alive), and the `id` is **persisted, so it is frozen** — never derived from the localized title or the list index. Two pages wire it, each with its own CSV key so they fold independently: the calendar settings page through `SettingsKeys.calendarSettingsCollapsedSections` (deliberately outside `_calendarPageKeys`/`_calendarAppearanceKeys` because it changes nothing the calendar draws), and the app settings page through `SettingsKeys.appSettingsCollapsedSections`. Both clear the set on "reset to defaults" — the page ships open, and leaving a section folded hides rows the user just asked to see restored. Note `markdown_settings_page.dart` folds too but predates this and hand-rolls its own mechanism; do not copy that shape.

## Generated files and local packages
- Generated localization Dart files are outputs from ARB files.
- `lib/database/database.g.dart` is generated by Drift.
- Android/iOS/macOS/Linux/Windows/web folders are platform shells; prefer app-level fixes in `lib/` unless the issue is platform-specific.
