# Data and persistence rules

Reference, not rules — moved verbatim from `COPILOT_CONTEXT.md` on 2026-10-11 (sections: Data And Persistence Rules; and the generated-file and platform-shell lines of Generated And Local Package Notes, under `## Generated files and local packages`). Read only the part the task needs.

## Data And Persistence Rules
- The database uses Drift with a singleton active database and background `LazyDatabase` connection.
- Folder, note, content chunk, calendar-event, calendar-event-occurrence, calendar-event-absence, calendar-event-template (v29), calendar-event-skip (v30) and vocabulary/vocabulary-item (v32) tables include CRDT-style metadata for future sync: `hlcTimestamp`, `deviceId`, `version`, `isDeleted`, and optional `deletedAt` where supported. On `calendar_events` (v27), `calendar_event_occurrences` (v28) and, since v43 (2026-10-23, `docs/cloud-sync-readiness-roadmap.md` R2), `calendar_categories`, `counters` and `counter_values` `hlc_timestamp`/`device_id` carry `DEFAULT ''` (the v29/v30/v32 tables were born with the block and carry none) — an `ALTER TABLE` on a populated table demands a default; the migrations backfilled real identity and every write path stamps, so `''` after that means something skipped the DAO. v43 also added `owner_id TEXT NULL` to all eighteen synced tables (NULL = not yet signed in; nothing reads it before Phase 02), the `sync_outbox` change-feed table (written only by the R3 write helper, never by hand), partial `is_deleted = 0` indexes on the three converted tables, and a repair that divides `deleted_at`/`updated_at` values above 10^12 by 1000 on folders and notes — the folder cascade had bound milliseconds into DateTime columns Drift stores as seconds. v43 also rebuilds `notes_fts` once (guarded on the table's existence): `notes_fts` is an external-content FTS5 table and the old `updateNote` ran `INSERT OR REPLACE` after writing the row, so every install carried stale tokens for renamed notes; the write path now issues the FTS5 `'delete'` with the old title/preview before inserting the new ones (R3a, `test/database/note_fts_test.dart`). Deletes on counters and categories are tombstones from v43 on; built-in categories can only be hidden, never tombstoned. **Every write to a synced table goes through the `CrdtWrite` helper (`lib/database/crdt/crdt_write.dart`)**: it stamps and upserts the `sync_outbox` entry in the same transaction or batch, the stamp is taken inside the transaction, an outbox entry is never lowered (`WHERE excluded.hlc > sync_outbox.hlc`), set-based writes learn their keys from `UPDATE … RETURNING` (SQLite ≥ 3.35, bundled via `sqlite3_flutter_libs`), and remote-origin merges never enqueue. A write that reaches a synced table without the helper is the silent-divergence bug the readiness record's risk register names.
- **The clock, the floor and the outbox re-seed (2026-10-23, readiness R5/R6/R4).** `sync_metadata` is a key/value table that has had the same shape since v1, so new keys need no migration: `last_hlc` (the highest stamp this database has minted or persisted — written forward-only by the `CrdtWrite.enqueue*` helpers as `hlc.last`, once per action, and by `persistClock()`; `AppDatabase.seedClockFromStore()` seeds the clock from it in `getInstance` and at the start of `onUpgrade`, from the rows' maximum when it is absent, and `onUpgrade` persists in a `finally` so migration backfills are covered), `bind_floor` (the clock at the last unbind — `persistClock()` then `last_hlc` — the initial merge at bind lets the space win rows at or below it), `last_push_at` (reserved for the engine). The migrations' own mint stays `migrationBackfillHlc()`; a future step that backfills stamps needs nothing more — the `finally` stores the clock. `SyncOutboxDao.requeueAll(boundUid:)` can rebuild the outbox from every synced table through `lib/database/crdt/synced_tables.dart` — a new synced table must be added to that registry (a test fails otherwise) with the SQL that reproduces its row key. A backup restore runs inside `SyncSuspension.run`, unbinds the database first and writes the floor after its last insert; "Delete all events" tombstones (`CalendarEventDao.tombstoneAll`) and only `importData` still hard-wipes.
- Notes store metadata separately from content. Content is chunked and may be compressed; avoid unnecessary full-content copies in hot editor paths. **Chunks are cut on content since v46 (S4)**: `lib/database/chunking/` cuts at 4,096–16,384 code units (target 8,192, a frozen Gear-hash table) and never after a high surrogate (S2 — SQLite binds text as UTF-8, so a split pair stores U+FFFD, compressed or not); `ChunkHasher` fills `content_chunks.content_hash` (SHA-256 over the UTF-16 code units as 2-byte little-endian, 64 lowercase hex; `idx_content_chunks_hash`) — frozen, because it becomes the chunk's remote document id. A body write is planned, never rewritten whole: `ContentChunkDao.prepareBody` cuts and hashes before the transaction (`BodyCut`, in `Isolate.run` above 65,536 code units), `planWrite(prepared:)` reuses that only while the live rows' `id|index|hash|hlc` signature is unchanged — so every chunk write must move its row's HLC — and `ChunkPlanner` keeps the common prefix and suffix by hash, shifts `chunk_index` arithmetically and writes only the changed middle; `writeChunks` compares hashes and never decompresses, `replaceChunks` (the pull) runs the same planner; gzip above `ContentChunkDao.compressionThreshold` (5,000 chars). `NoteDao.updateNote` stamps and queues only when the text or a passed column changed — a no-op save writes nothing; `chunk_count` comes from the cut (the parameter is ignored when content is given) and a stale one is corrected without a stamp; `mergeNoteDocument` cuts only in its insert and overwrite branches; the empty body stores zero chunks. A one-character insert changes one chunk, a deletion can cascade a few more; a legacy chunk (no hash) is re-cut on the next save and an undecodable one counts as changed.
- Reorder operations should be transactional and preserve user-defined positions. **Positions are gapped int64 (S17)**: a new row appends at `nextPosition(max)` — 0 in an empty group, else `max + AppConstants.positionStride` (1 << 20), a tie rather than a wrap past ±2^61 — on every create, import and move path; a reorder is `NoteDao.applyOrder` / `FolderDao.applyOrder`, one transaction per kind that writes only the rows `planGappedPositions` moved, under one stamp; a position-only write leaves `updatedAt` alone. Never renumber a whole group densely (the `reorderNotes`/`setNotePositions` chains are gone). The planner's rules: `anta-context/references/feature-areas.md`.
- **A migration step is frozen at the shape it shipped with (fixed 2026-09-20).** A step must never call a definition that follows the *live* schema — a `DatabaseIndexes` helper, `m.createTable`, a DAO — once that definition can name something a **later** step introduces. v31 called `createCalendarDeltaIndexes()`, v37 widened that index to `(event_id, day, status)`, and from then on every upgrade from v30 or older died with `no such column: status`; v10 had the same trap with `is_deleted` (v27). The rule: the **newest** step that defines an index shares the helper with `createAllIndexes`; every **older** step that touches the same name spells its own frozen DDL, and the newer step drops and recreates. When you change an index or table shape, freeze the older callers in the same change.
- **Each migration step is atomic.** Drift does **not** wrap `onUpgrade` in a transaction and only writes `user_version` after the whole chain — so one failing step used to leave every earlier step applied under the old version, and the next launch re-ran them. `DatabaseMigrations.runMigrations` therefore runs each step in its own transaction together with `PRAGMA user_version = <step>`: a failure rolls that step back whole and the next launch resumes exactly there. Steps stay idempotent anyway (guard every `ALTER` with `PRAGMA table_info`), because databases half-upgraded by an older build exist; data steps that are their own inverse (v18's `6 - p`) additionally key off a marker the following step leaves behind. No statement in a step may need to run outside a transaction (`VACUUM`, `journal_mode`).
- `test/database/upgrade_chain_test.dart` is the guard for both rules: it takes a fresh database back to the oldest reconstructible shape (every table but the four original ones dropped, every later column dropped — derived, so a new table or column is covered without touching the test), walks it up one step at a time, compares columns and index SQL with a fresh install, re-runs the chain, and reopens a real v30 file through the production connection (`LazyDatabase` → `createInBackground` → `LoadingQueryInterceptor`).
- **The outbox's `republish` flag (v51, scalability record §8.5).** `sync_outbox.republish` marks an entry the wire cutover re-queued for a version the space already holds (`SyncOutboxDao.requeueBodies`, and the S9 equal-stamp branch in `NotesBinding.mergeRemote`); every real write's upsert resets it to 0 (`crdt_write.dart`, MIN(old, new)); `CrdtMerge.mergeRemoteRow` learns `localHadPendingPush` through `ackUnpushedThrough`, which ignores republish entries — so a re-queue never files a conflict copy and a real unpushed edit always does. Never set it from a save or bind path. The flag is local only; the wire stays 46.
- **The share mark (v52, wire 47; record `docs/cloud-sharing-foundations.md` §3, §12).** `calendar_events.shared_pair` and `folders.shared_pair` name the pair a root is shared into, NULL for every other row. One writer per table (`setSharedPair`, reached through `CalendarEventService.setShared` / `FolderStorageService.setFolderShared`): a stamped write that leaves `updated_at` alone, clears the marks its folder covers and every mark of another pair. **A dependant stores no mark**: a skipped day and a per-day text are shared as their event is, a folder and a note as the nearest marked folder above them (`sharedPairsOf`), read when the row is encoded — so any write that changes that answer without writing the dependants (a mark, a folder move, a merge of either) queues them again through `CrdtWrite.requeueRows`, at their own stamps, tombstones included. A new write path that moves a folder or changes a mark must do the same, or the documents under it keep saying who may read them as of the push before. An event's save and a folder's rename never touch the column (the companions leave it absent); a backup writes none and an import stores none. No index: the rows that carry a mark are found by reading the few that do.
- **Counter values are PN-counters and die with their note (v49, S20).** `counter_values` carries `epoch_hlc`, `epoch_value`, `shards`; `value` must always equal `epoch_value + Σ(p − n)` — every write goes through `CounterDao._writeValue` or the merge's join, never a raw `value` update. A local note delete is a soft-delete path for its values: single, selection and folder deletes tombstone them in the same transaction under the note's stamp (one set-based `UPDATE … RETURNING` + `enqueueMany`, never an `IN (?, …)` per note), served by `idx_counter_values_note` (partial, on both paths). A sweep of values under a tombstoned note (`sweepOrphanValues`, the v49 step) touches only values stamped below the note's tombstone and writes the note's own stamp, never a fresh one. `sync_metadata.replica_id` keys a database's taps: minted at bind, unbind, the first tap, and whenever `replica_id_device` names another install (a backup-restored or transferred file), dropped from an imported `.db`; never the install `device_id` itself.
- Search has one SQLite index, the body index (`note_body_fts` with `title`, `body` and `tags` columns since v50, which dropped `notes_fts`); both searches answer from it — the quick search merges in a scan of the 300 newest notes for what the index has not projected yet. The body index is **never** written on a note write: every write moves `hlc_timestamp`, and before a full search one statement compares the ledger's `indexed_hlc` with it (plus the orphan check) and drains what moved; the search surface starts a drain when it opens and a keystroke never does — so no write path, sync apply or import needs a hook, and `BodySearchIndexer.markActiveDirty()` is only a hint (call it after a `VACUUM`). **One normalization for all search surfaces**: `normalizeForSearch` / `searchTokens` / `tokenizeForSearch` in `lib/services/folder_search_service.dart` (diacritics map in `SearchConstants`, incl. Romanian comma-below ș/ț) are shared by the body index's projection, its scorer, the query side, and the calendar agenda search — never reintroduce a local fold or tokenizer (the isolate once had its own map, it drifted, and bulk-indexed Romanian words became unfindable). `removeDiacritics` iterates **code units**, not one-character substrings, and consults `_diacriticsByCodeUnit` — which is **derived from `SearchConstants.diacriticsMap` by comprehension**, so it is a re-keying of the canonical table and not the second table the warning above forbids; every key is a single UTF-16 code unit, units `<= 0xBF` skip the lookup, and a string needing no fold returns itself unallocated. `searchTokens` keeps duplicates on purpose: the index counts them as real term frequency.
- **`SearchBloc` (`lib/bloc/search/`) owns search state, and nothing else does** (Slice 4, 2026-09-06). It holds the scope, the query, the phase (idle / quick / full), the recents shown while idle, the hits split into `titleHits` / `contentHits`, and a folder-id → path-segments map for the rows. It is page-scoped — built from `GetIt` and provided by whichever page hosts it, the way `CounterPerNotePage` does — never registered app-wide, so leaving the surface disposes the query with it. Two hosts since Slice 5: the browser owns one for the life of the page (created in `initState`, closed in `dispose`) and the standalone `SearchPage` route, which tag taps still use, builds its own. `OptimizedNoteBloc` has **no** search events or state any more: it fed the folder list at the same time, so a search replaced the very list the page underneath was rendering, and the browser had to reload itself on the way back from search. Do not add search back to it. `AppNavigator.toSearch` stays **unstamped** (no `NavDestination`): search is a query surface, not a place, and launch restore must never reopen someone's half-typed search. In-place search is not even a route — it is screen state on the browser, so opening and closing it leaves the recorded location stack untouched. The editor's search icon is unrelated and stays find-in-note. Two ordering guards, since `SearchQueryChanged` is the only debounced event and every other event (`SearchCleared` on an emptied field, `SearchSubmitted`, `SearchOpened`) is handled at once: `_generation` decides which *handler* may still emit after its await, and `_pendingQuery` (2026-09-07) decides which *event* may run at all — recorded in `onEvent`, ahead of the transformer, so a keystroke delivered 200 ms after a clear/submit/open is dropped rather than searched (backspacing "pr" to empty used to search "p" under a blank field). A scope change deliberately does not cancel the pending keystroke. Pinned in `test/bloc/search_bloc_test.dart` ("races between event types") and, for the phone gesture, `test/widgets/optimized_folder_content_page_test.dart`.
- **Folder search scope is recursive.** `SearchFilter.folderIds` is a whole subtree — `FolderStorageService.subtreeIds(folderId)` = `FolderDao.getAllDescendantIds` (the `WITH RECURSIVE` CTE) plus the folder itself — and `quickSearch` takes the same set. `null` searches everywhere; an **empty** set matches nothing, which is what a scope pointing at a deleted folder must do. Never reintroduce a single-`folderId` comparison: the folder row's count already includes descendants, so a non-recursive search made the row above and the results below disagree. `quickSearch` reads its page unscoped and filters in memory (the DAO can page by one folder id, not by a set), capped at 300 rows.
- **The full search runs on a persistent body index (v47, S11, 2026-11-08).** `note_body_fts` (contentless FTS5, `trigram case_sensitive 1`, one `searchProjection` per note under its rowid) and `note_search_ledger` (`indexed_hlc` + fingerprint) are owned by `NoteSearchDao` and filled lazily by `BodySearchIndexer` (lifecycle singleton; drains after the first frame, after a switch, and before a full search when the change stream marked it dirty — never on a save). One MATCH statement gives the candidates with folder and colour in SQL; `searchScore` re-scores their bodies in byte pages (today's word-count rules, pinned by `test/services/body_search_parity_test.dart` against a copy of the old in-memory index), and only the `limit` survivors are read again via `loadNoteContent` for offsets — `folder_search_service_limit_test.dart` still counts that. Derived, never synced, never in a backup; without the trigram tokenizer the table is absent and every live note in scope is scored. A broad query scores every candidate body (5,000 × 15 KB: ~11 s on the Windows machine) until S12's bm25 lands.
- Counters use `noteId == ''` for global values in `counter_values`; per-note values use the real note id.
- Custom markdown shortcuts can bind up to two counters via `CustomMarkdownShortcut.counters` (`List<CounterBinding>`). Each binding has a `counterId` and a `CounterOp` (`increment` / `decrement`). The `{c1}` / `{c2}` tokens in `beforeText` / `afterText` / repeat wrapper text expand to the matching binding's post-mutation value at insertion time. Each token occurrence triggers exactly one mutation per repeat iteration. Token expansion runs through `ShortcutApplier` via the `CounterMutator` callback, which routes to `CounterBloc` (`IncrementCounter` / `DecrementCounter`) and respects the global vs per-note scope contract. The legacy `counterId` field is preserved for backwards compatibility — when `counters` is empty but `counterId` is set, `effectiveCounters` synthesises a single increment binding so applier logic stays uniform.
- `CustomMarkdownShortcut.category` is an optional free-text grouping label (`null`/empty = uncategorised). It is settings-only organisational metadata: it never affects toolbar order or rendering, has no separate persisted registry (the category set is derived from the shortcuts themselves), and is additive in the profile JSON, so older profiles and backups load unchanged.
- Settings are stored through `UserSettingsDao`, `SettingsService`, and `SettingsKeys`. Do not scatter raw string keys.
- **Settings pages are searchable through one matcher**: `lib/utils/settings_search.dart` (`SettingsQuery`, `matchSettingsEntry`, `matchesSettingsQuery`) rendered by `lib/widgets/settings_section_list.dart` (`SettingsEntry` / `SettingsSectionData` / `SettingsSectionList`). Never filter with a local `toLowerCase().contains()` — that is a second fold and it silently breaks `ro`/`de` (`evidentieri` must find `evidențieri`, `schriftgrosse` must find `Schriftgröße`). `FoldedText` exists because the shared fold is **not** length preserving (`ß`→`ss`, `æ`→`ae`), so highlight spans must be mapped back through its index table rather than applied to the source directly. Matching is deliberately exact-substring with multi-token AND and no fuzzy/ranking: rows keep their declaration order so sections and learned positions survive filtering. A page declares rows as `SettingsEntry`s whose `builder` receives the pre-highlighted title/description, so each row keeps its own widget type; hidden `keywords` (localized, comma-separated ARB strings) are matched but never rendered. **Sections can fold, opt-in (2026-09-01)**: a `SettingsSectionData.id` plus `SettingsSectionList.collapsedSections` + `onToggleSection` — a section without both stays permanently open, which is how the developer and sync pages are untouched. Three rules: a fold **may never swallow a search hit** (while the query is non-empty every surviving section renders open and loses its chevron, without touching the stored fold), a folded section **builds nothing below its header** (not `Offstage`, not `AnimatedCrossFade` — which builds both children and would keep a page's live preview and every slider alive), and the `id` is **persisted, so it is frozen** — never derived from the localized title or the list index. Two pages wire it, each with its own CSV key so they fold independently: the calendar settings page through `SettingsKeys.calendarSettingsCollapsedSections` (deliberately outside `_calendarPageKeys`/`_calendarAppearanceKeys` because it changes nothing the calendar draws), and the app settings page through `SettingsKeys.appSettingsCollapsedSections`. Both clear the set on "reset to defaults" — the page ships open, and leaving a section folded hides rows the user just asked to see restored. Note `markdown_settings_page.dart` folds too but predates this and hand-rolls its own mechanism; do not copy that shape.

## Generated files and local packages
- Generated localization Dart files are outputs from ARB files.
- `lib/database/database.g.dart` is generated by Drift.
- Android/iOS/macOS/Linux/Windows/web folders are platform shells; prefer app-level fixes in `lib/` unless the issue is platform-specific.
